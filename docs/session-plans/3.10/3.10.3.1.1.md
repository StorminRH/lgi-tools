## Bottom line (READ FIRST)

- **GOAL:** Every mutation, tool read, cron, and queued job carries a stable
  capability name and a recorded outcome; a five-indicator SLI set reads live from
  that record with a named owner and response action; and one registry states —
  under test — that no re-runnable unit of work in the tree duplicates or loses
  anything.
- **DONE =** SC-1 through SC-11 below, plus: a forced failure on a critical
  mutation is findable in `usage_logs` by its capability name, stable code,
  correlation id, total and per-dependency durations, retry outcome, and app

  `src/composition/idempotency-registry.ts` carries a verdict with evidence for
  every re-runnable unit of work, with an empty at-risk set as its recorded
  terminal outcome.

  - A shared executable retry primitive. Contract `OOS-3` excludes the general
    framework, and the operator resolved on 2026-07-25 to keep the three existing

    `logUsageEvent` remains the single insert path, and `FAILURE_CATEGORIES` /
    `AppFailure.code` remain the only outcome vocabulary.

## Why now

3.10.2.1 gave failures stable codes and 3.10.2.4 gave every outbound call a
declared bound, but neither made an operation *findable*: a user-reported failure
today has a correlation id printed in the response body that nothing on the server
ever wrote down, and the only durable per-operation record is the seven cron rows.
This session closes that loop — it names the operations, records their outcomes
against the existing code taxonomy, and defines the five indicators that say
whether users are fine. The idempotency inventory rides with it because the same
record is the evidence that decides whether an operation re-running is harmless:
3.10.2.4 declared what happens when *we* call *out*, and this registry is its
inbound mirror for what happens when our own work runs twice.

## Scope (the destination)

When this session finishes, three things are true.

**Named operations.** A closed catalogue in `src/data/telemetry/capability.ts`
names every instrumented unit of work as a `feature` plus an `operation`.
**Thirty-eight capabilities** are covered: **24 shell-owned** (17 mutation routes
through `runMutationRoute`, 7 cron routes through `defineCronRoute`) and **14
hand-instrumented** (7 direct mutation routes that deliberately sit outside the
mutation shell, 6 POST-bodied tool reads, and the queued ESI-refresh job runner).
Four POST surfaces are deliberately excluded and named: `auth/[...all]` (Better
Auth owns its own lifecycle), `internal/eve-characters` and `internal/eve-token`
(machine-to-machine, already accounted for by the calling capability), and
`telemetry` (the beacon that writes the table — instrumenting it would recurse).

Each completed unit writes at most one `usage_logs` row with
`action: 'capability_outcome'` and a typed metadata payload carrying feature,
operation, outcome, stable code, total duration, per-dependency durations, retry
and rate-limit outcome, correlation id, and app version. The write is scheduled
through the existing `after()`-based `emitCostMetric`, so it never extends the
response the user waits for. Cron capability rows obey the shell's existing
recording policy rather than firing per run: an `idle` or `busy` no-op writes
nothing, preserving the `idle-silent` wake-class contract that a healthy no-op run
touches zero Neon (`cron-gate.ts:15-19`, enforced by `src/app/api/cron/registry.test.ts`).

Coverage is enforced two ways: the shells take a required `capability` option, so
their 24 cannot be added unnamed, and a route census asserts every other
`src/app/api/**/route.ts` mutation or tool POST either uses a shell or calls
`recordCapabilityOutcome`, against a pinned four-entry exclusion allowlist. The
census walks all **34** POST-bearing route files — the 30 instrumented plus the 4
exclusions — so a census written against 30 fails.

One existing query is corrected so this session stays observationally neutral:
`getDailyCounts` (`queries.ts:97-118`) counts every `usage_logs` row with no action
filter and feeds the admin traffic panel, so capability rows would blend server
self-observation into user activity. It gains an `action <> 'capability_outcome'`
exclusion in its body — no new export, AF-006 unaffected — so the panel's output is
identical before and after this session.

**Live indicators.** `src/data/telemetry/sli.ts` declares five indicators — page
and tool success rate, mutation success rate excluding validation failures, p95
latency on critical reads and writes, ESI success and throttle rate, and job
backlog with terminal failures — each with one named owner and one written response
action. `src/data/telemetry/sli-queries.ts` returns each indicator's live value
from `usage_logs`, and the existing admin Ops section renders them in one new panel.
Nothing new is alerted on; `OOS-2` holds.

**One inventory, under test.** `src/composition/idempotency-registry.ts` is a third
test-only sibling to `data-ownership-registry.ts` and `vendor-resilience-registry.ts`.
It enumerates every re-runnable unit of work — 7 Vercel crons, 1 Convex cron, the
Workpool-retried Convex sync actions, the queued job runner with its stranded-worker
recovery and manual requeue, the outbound alert paths, and all 34 POST-bearing
mutation and tool routes (including the 4 uninstrumented exclusions) — and records
for each a redelivery source, a verdict of `inherently-idempotent`, `key-protected`,
`accepted-risk`, or `coordinated-elsewhere`, and its evidence.
`src/esi-datasets/idempotency.test.ts` fails when the registry and the tree
disagree. **No entry is at-risk**, and that empty set is the recorded terminal
outcome contract `DC-6` and `AC-5` accept.

Consequently **no application behavior changes in this session.** Every runtime
edit is a telemetry write, an SLI read, or a behavior-preserving relocation.

Contract §§3–6 are satisfied without widening: `DC-1`/`DC-2` by the capability
record and its cardinality gate, `DC-3` by the SLI set and panel, `DC-4` by the
extension-only seam and the two Watch rechecks, `DC-5` by the registry and census,
and `DC-6` by the recorded no-at-risk verdict.

## Resolved implementation decisions

- **Contract PD-1 — Where the SLI definitions live: a typed const in
  `src/data/telemetry/sli.ts`, owning both the owner and the response action.** The
  SLI set is data about the telemetry slice's own rows, so it belongs beside them;
  a typed const makes owner and response action non-optional at compile time and
  lets `sli-queries.ts` and the admin panel derive from one list rather than
  restating it. Owner values come from a closed `SLI_OWNERS` union — for a
  single-operator project the honest values are `operator` and `ccp-upstream`, the
  latter for the ESI indicator whose response action is "wait out CCP's budget
  window; do not raise call volume". **Rejected:** a prose document under `docs/`.
  It cannot be type-checked, cannot be joined to the query that produces the value,
  and would drift the moment an indicator's SQL changed — the exact failure
  `vendor-resilience-registry.ts` exists to prevent.

- **Contract PD-2 — Which admin panels absorb the readouts: one new `SliPanel` in
  the existing `OpsSection`, above `BudgetPanel`.** `OpsSection` already owns
  operational health (`BudgetPanel`, `QueuePanel`, cost lens, domain events),
  already uses the `loadSection` / `SECTION_LOAD_FAILED` degradation wrapper, and
  already renders through the `Card` + `SectionHeader` + `MetricsTable` idiom, so
  the SLI readout inherits its failure behavior for free. Derivation goes in
  `src/app/admin/ops-view.ts` as `deriveSliView`, matching `deriveBudgetView` and
  `deriveQueueView`. **Rejected:** a new top-level admin section or a
  `MetricsSection` addition. `MetricsSection` owns product KPIs with
  period-over-period deltas; an SLI is a health signal, not a KPI, and the
  dashboard's stated rule is every metric exactly once, no tabs.

- **Contract PD-3 — Inventory home: a third test-only registry at
  `src/composition/idempotency-registry.ts` with a census at
  `src/esi-datasets/idempotency.test.ts`.** Two siblings already prove the pattern:
  the growth registry answers "why is this table bounded", the ownership registry
  answers "who may write it", the vendor registry answers "what bounds our outbound
  calls". This one answers the remaining question — "when our own work re-runs, what
  breaks" — and its census makes the answer fail loudly when the tree moves. It
  imports nothing at runtime, exactly like its siblings. **Rejected:** extending the
  cron and dataset rails in place. The population spans crons, a Convex cron, a
  durable queue, outbound alerts, and 34 HTTP routes; no existing rail is crossed by
  all of them, and forcing them into `dataset-declarations.test.ts` would widen a
  table-shaped declaration into a work-shaped one. **Also rejected:** a standalone
  prose doc, for the PD-1 reason.

- **Contract PD-4 — The at-risk shortlist: empty, recorded as the DC-6 terminal
  outcome.** The planning sweep judged every redelivery source against live code and
  current primary documentation:
  - *Vercel crons* — Vercel does not automatically retry a failed cron job
    (`vercel.com/docs/cron-jobs`, fetched 2026-07-25). The only redelivery is
    schedule overlap on the two 15-minute jobs, and `defineCronRoute` already
    serializes with a Postgres advisory lock and short-circuits to a declared busy
    body. Verdict `key-protected`, the lock key as evidence.
  - *Convex `scan`, `sweep`, `onSyncComplete`* — all declared `internalMutation`.
    Convex scheduled mutations execute exactly once and retry transient errors
    inside a transaction (`docs.convex.dev/scheduling/scheduled-functions`, fetched
    2026-07-25). Verdict `inherently-idempotent`.
  - *Queue enqueue and manual requeue* — `esi_refresh_jobs_live_key_unique`, a
    partial unique index on `idempotency_key` across the live statuses, plus the
    single atomic CTE in `requeueDeadLetteredJob` returning
    `requeued` / `superseded` / `not_found`. Verdict `key-protected`.
  - *Queued job re-run after retry or stranded-worker recovery* — every runner
    writes replace-shaped: delete-then-insert per owner in `owned-assets`,
    `owned-blueprints`, and corp `industry-jobs`, and `onConflictDoUpdate` in
    `skill-queue` and character `industry-jobs`. A second run converges. Verdict
    `inherently-idempotent`.
  - *Convex Workpool-retried sync actions* — the third retry owner.
    `convex/convex.config.ts` runs the engine's sync actions with durable
    exponential-backoff retries, and `convex/engine.ts:86` dispatches
    `internal.onlineStatusSync.syncUser`, an `internalAction` that reaches Neon and
    ESI. A retry therefore re-runs those writes. `convex/engine.ts:84-85` declares
    the safety condition — the actions' error taxonomy reserves throwing for
    transient failures, and the generation guard makes a duplicate apply a no-op —
    and the online-status write is replace-shaped. Verdict `inherently-idempotent`,
    with the generation guard as evidence.
  - *Stranded-worker dead-letter alerting* — **already protected.**
    `drainEsiRefreshJobs` alerts on `recovery.deadLettered` at
    `src/composition/sync/esi-refresh-worker.ts:210-214`, originally landed in
    commit `f5b24a66` (PR #237, 2026-07-14); `eca3d994` (PR #296) only relocated the
    worker file. The two recovery `UPDATE ... WHERE status = 'running' ... RETURNING`
    statements move each job off `running` as they return it, and the drain runs
    under an advisory lock, so no interleaving double-alerts. Verdict
    `inherently-idempotent`.
  - *`insertEsiSnapshot` in `owned-assets-sync`* — the one append-shaped write, so a
    recovered re-run can leave a second row. Operator verdict on 2026-07-25:
    `accepted-risk`. No duplicate is observable — readers take the latest by
    `fetchedAt` — the table is retention-pruned, and a uniqueness constraint would
    also reject a legitimate re-pull of an unchanged etag, which `HC-4` forbids.
  - *User and admin mutations* — `src/transport/api-client.ts` contains no retry, so
    no platform redelivers them; a double submit is user-initiated, and both create
    routes already enforce a per-user cap. Verdict `accepted-risk` with the absence
    of a retry path as evidence.
  **Rejected:** adding client-supplied idempotency keys to the two create routes.
  Nothing redelivers them and `HC-4` bars a key where the risk is not real.
  **Rejected:** manufacturing an at-risk entry to avoid an empty set — `DC-6` and
  `AC-5` name the recorded no-at-risk verdict as an accepted terminal outcome.

- **Contract PD-5 — The exact field set and recording seam.** The record is one
  `usage_logs` row, `action: 'capability_outcome'`, whose jsonb metadata is the
  typed `CapabilityOutcomeRecord` in `capability.ts`:
  `{ feature, operation, outcome, code, durationMs, dependencies, retry, correlationId, appVersion }`.
  The write seam is `emitCostMetric` in the existing `src/data/telemetry/cost-metrics.ts`,
  which already schedules through `after()` and already swallows telemetry failure —
  so the write leaves the response path untouched and `queries.ts` gains no export,
  holding AF-006 at 25.

  Correlation and dependency accumulation live in `src/transport/correlation.ts` as
  an `AsyncLocalStorage` scope, the pattern `src/platform/auth/absorb-context.ts`
  already establishes. `capability.ts` reads it directly (`data → transport` is a
  permitted edge). `apiResponse` and the relocated `problemResponse` read the
  ambient id, so all 102 existing `apiResponse` call sites are untouched.

  The scope also carries the **failure stash**, because the stable code cannot be
  recovered from the response alone: `CATEGORY_STATUS` (`problem.ts:28-37`) maps
  category to status only, so a 409 recovers `'conflict'` but never
  `'template_limit'`. Both response builders already hold the `AppFailure`, so each
  writes `{ category, code }` into the active scope as it serializes, and the shell
  reads that stash when materializing the record. Status-only mapping remains the
  fallback for a response built outside any scope. This is the seam that makes
  `SC-1`'s `code: 'template_limit'` assertion satisfiable.

  Dependency timing cannot call into `transport` from its measurement points:
  Fallow allows `lib → ['config']`, `db → ['lib','config']`, and
  `platform/esi → ['lib','config']`, and both `src/platform/esi/index.ts` and
  `src/lib/upstash.ts` are inside the Convex bundle, where `node:async_hooks` would
  break the production push. So the hook is **`src/lib/dependency-timing.ts`**: an
  import-free, builtin-free module owning the `DependencyKind` union, an
  `addDependencyTiming(kind, ms)` function, and a settable sink that defaults to a
  no-op. The three measurement points import only that module.
  `withCorrelationScope` installs the ALS-backed sink idempotently on first use, so
  in the Convex isolate — where nothing installs it — the hook stays a no-op and
  the bundle stays builtin-free.

  The Neon measurement points are **`neonConfig.fetchFunction` plus a named
  `timedPostgres()` wrap at both `postgres()` construction sites in
  `src/db/index.ts`** (`getDb`'s `LOCAL_DB_DRIVER` client at line 63 and
  `getDirectClient` at line 117). `fetchFunction` covers only the neon-http driver;
  postgres-js exposes no query-completion hook, so the wrap must time query
  execution and `reserve()` — the latter because advisory-lock statements run on a
  `ReservedConnection` (`src/db/advisory-lock.ts:34`) that bypasses a wrapper on the
  client proxy alone. `timedPostgres()` is constructed lazily inside the existing
  factories, preserving the AGENTS.md import-side-effect-free invariant on
  `src/db/index.ts`. The two seams are disjoint by construction — neon-http never
  reaches `postgres()` and vice versa — so no path double-counts. Instrumenting only
  `fetchFunction` would leave `dependencies.neon` empty for advisory-lock and
  `ctx.client` cron work and across the entire documented local stack, where
  `.env.example` sets `LOCAL_DB_DRIVER=postgres-js`.

  **Rejected:** placing correlation in `src/lib/` beside `problem.ts` — that module
  is in the Convex bundle and `pnpm verify` and CI would both stay green while the
  post-merge Convex push failed. **Rejected:** importing `src/transport/correlation.ts`
  directly from the three seams — three live Fallow boundary violations and two
  Convex-bundle breaks. **Rejected:** threading an explicit correlation parameter
  through `apiResponse` — 102 call sites for a value two of them care about.

## Design pressure and baseline effect

### Hotspot proximity

- **Touched measured surfaces:** `Telemetry query breadth` (AF-006, 25 exports / 50
  fan-in files) and `ESI refresh-job query exports` (AF-007, 13). Both are read and
  extended around; neither is grown.
- **Live proximity evidence:** `src/data/telemetry/queries.ts` is 545 lines and 25

  hotspot and closed to additions in this session.
  `src/data/esi-refresh-jobs/queries.ts` is 13 exports against >15 and is
  *adjacent*; this session adds none. `src/data/telemetry/cost-metrics.ts` is 65

  extension seam. `src/app/admin/OpsSection.tsx` and `ops-view.ts` carry no trigger

  export counts so the version-close audit sees the slice's real breadth rather than
  discovering the displacement later.

```ts
/** Dependency kinds whose per-operation durations are accumulated. */
export type DependencyKind = 'neon' | 'esi' | 'redis';

/** One dependency's accumulated cost inside one operation. */
export interface DependencyTiming { ms: number; calls: number }

/**
 * Records one dependency call's elapsed milliseconds. A no-op until a host installs a sink, so
 * this module stays import-free and safe in the Convex isolate.
 */
export function addDependencyTiming(kind: DependencyKind, ms: number): void;

/** Installs the process's dependency-timing sink. Idempotent; the last installer wins. */
export function setDependencyTimingSink(
  sink: (kind: DependencyKind, ms: number) => void,
): void;
```

### Control and data flow

**Mutation request.** `runMutationRoute` opens a correlation scope, starts a cost
timer, then runs the existing `authorize → same-origin → parse → handle` order
unchanged. Any guard or parse failure maps through `problemResponse`, which now
reads the ambient correlation id instead of minting one and writes its
`{ category, code }` to the scope's failure stash; a handler's
`apiResponse(..., failure)` does the same, so the id in the response body is the id
recorded and the stable code survives. While the handler runs, `esiFetch`, both Neon
seams, and the Upstash client each add elapsed milliseconds through
`addDependencyTiming` into the scope's accumulator. On the way out the shell reads
the failure stash — falling back to `CATEGORY_STATUS` status-mapping when the
response was built outside the scope — and calls `recordCapabilityOutcome`, which
materializes the record synchronously inside the scope and hands it to `after()`.
The user's response is already sent.

**Cron run.** `defineCronRoute` wraps its existing body in a correlation scope; the
body is first extracted into a named function so the added nesting keeps the handler
under the cognitive-15 cap. Its current `emitRun` boundary line and
recording-policy-gated `UsageAction` row are untouched. The capability row follows
that **same recording policy**, not a per-run rule: an `idle` or `busy` no-op writes
none, so the `idle-silent` wake class still touches zero Neon on a healthy tick. A
run that completed work records `outcome: 'succeeded'`; a thrown stage records its
mapped `FailureCategory`. The cron's own outcome vocabulary (`'idle'`, `'busy'`,
`'refreshed'`, `'up-to-date'`) stays in the existing `UsageAction` row's metadata and
never enters `CapabilityOutcomeRecord.outcome`, which is closed to
`FailureCategory ∪ {'succeeded'}`. Dependency durations are non-empty for crons only
because the postgres-js path is instrumented.

**Queued job.** `processJob` runs inside a per-job correlation scope. Its existing
`ProcessJobOutcome` already carries `status`, `attemptCount`, and `failureCode`, so
the retry field is populated from values the worker already computes;
`deferred_for_budget` sets `rateLimited: true`. No retry, recovery, or alerting
behavior changes.

**SLI read.** The admin Ops section calls each `sli-queries` export inside
`loadSection`; a failed query renders `SectionUnavailable` for that panel only,
exactly as `BudgetPanel` and `QueuePanel` already behave.

### Edge and failure behavior

- Telemetry write fails → swallowed by `recordCostMetric`'s existing `try/catch`;
  the operation's own result is unaffected. Proven by a test that makes
  `logUsageEvent` reject and asserts the route still returns its normal response.
- `after()` unavailable (called outside a request scope) → `emitCostMetric`'s
  existing `try/catch` logs and returns; no throw. Under Vitest the established
  `cost-metrics.test.ts` pattern mocks `next/server`'s `after`.
- Code runs outside a correlation scope → `currentCorrelationId()` mints a fresh id
  and `currentDependencyTimings()` returns `{}`. Response shape is byte-identical to
  today's, which is what keeps the relocation behavior-preserving.
- Code runs in the Convex isolate → no sink is installed, so `addDependencyTiming`
  is a no-op and no `node:` builtin is reachable. `SC-8` gates this.
- A capability's operation throws before the shell records → the shell's `finally`
  records `outcome: 'unexpected'` with the thrown error's code, then rethrows.
- An SLI query returns no rows for the window → the value renders `—` through the
  existing `formatPct` empty convention, never `0%`, so an empty window is not
  misread as total failure.
- Neon unavailable when an SLI panel loads → `loadSection` returns
  `SECTION_LOAD_FAILED` and only that panel degrades.
