## Resolved implementation decisions

- **Contract PD-1 — Cache times, cadence floor, and registry shape: 5s floor pegged to the verified ESI cache, delivered by an in-engine chain-on-success policy.** Verified from the live ESI spec: location 5s, ship 5s, online 60s. The dataset registers as `characterLocation` in `SYNC_DATASETS` with `{ cadenceFloorMs: 5_000, tokenGroup: 'char-location' }` and an `entries.ts` live-dataset row (`character_location`, `verifiedCacheSeconds: 5`, both spec paths). Because the stock dispatcher ticks every 30s, the dataset opts into chain-on-success: when a run succeeds and the subject's presence is fresh, the completion path schedules the next dispatch at the response's `Expires` boundary; failed runs never chain and fall back to the 30s scan (retry owner unchanged); mount/visible heartbeats remain the instant-start path, so tracking begins within ~1s of opening the map. Dispatch rate-limiting for this dataset keys per subject (`char-location:<userId>`) instead of per group so concurrent tracked users cannot starve each other. Ship is fetched only when location changed (ship type matters at jump time — 4.0.4.2.2 mass arithmetic), and observed movement nudges the user's `onlineStatus` subject due-now so the online dot catches up without gating location on it. Steady-state cost per tracked pilot with an open map, in the engine's own billing terms (`convex/engine.ts` header cost block): ~11 marginal function calls plus Workpool main-loop overhead and one `chainDispatch` per run, at 12 runs/min — order of 10k–30k Convex calls per tracked watched-hour versus the canary's ~2.9k, an accepted order-of-magnitude multiple that exists only while a tracked pilot's map is open; zero payload writes and zero reactive fan-out while stationary. **Rejected:** speeding the shared 30s scan to 5s (12× baseline dispatcher cost for every dataset, forever); gating location polling on the 60s online signal (operator-rejected: a fresh login must not wait up to a minute); adaptive idle slow-down (operator-rejected: the cloaked-scout-then-jump case is the core use case and must not be late).
- **Contract PD-2 — Session-change, simultaneous-scout, and repeated-arrival classification: a pure SDE-driven decision table with a continuity rule.** One user-facing concept — a jump is a jump; the table only decides what kind of doorway and whether to trust the sample pair. Verdicts: `stationary` (same system, nothing changed — the 304 path), `same-system-state` (dock/undock/station change — stored as fact, never a jump), `gate-placement` (an SDE stargate links the two systems — movement only, nothing map-authorable), `hole-crossing` (no gate links them, including every transition touching wormhole space), `re-anchor` (no trustworthy previous sample). A jump verdict requires two consecutive fresh samples: continuity derives from the subject's bookkeeping (previous successful run covering this character within `JUMP_CONTINUITY_MS = 15_000`, three cadence floors); larger gaps re-anchor — a pilot who moved while unwatched reappears with no invented path (operator direction: downstream sessions draw this as an orphaned anchor that regraphs and may reconnect). Pod-death rule: a non-adjacent transition where the ship became a capsule classifies `re-anchor`, not `hole-crossing` (operator-accepted, fine-tuning deferred out of scope). Repeated arrivals are memoryless — every transition is judged alone; dedup is 4.0.4.2.2's idempotent-upsert contract. Simultaneous scouts are structurally independent (per-character documents and verdicts). Filament/Pochven teleports remain indistinguishable from hole crossings by location alone — accepted by operator ruling; 4.0.4.2.2's signature-first authoring bounds the consequence. **Rejected:** separate gate/wormhole user vocabulary (operator-rejected; the doorway kind is an edge attribute, not a jump kind); region-specific filament heuristics (complexity without a reliable signal).
- **Contract PD-3 — Tracking representation and teardown: Convex-native registry plus a per-character location document.** `mapTracking` rows (`mapId`, `userId`, `characterId`) are live map state, toggled by one gated mutation (map access required; the UI offers only the caller's own characters, and ownership is structurally enforced at sync time because the action enumerates and vends tokens only for the caller's characters — the heartbeat-hint doctrine). `characterLocation` is one document per character — not per map — carrying current system, docked station/structure, ship type, previous system, sample continuity, and ETags; viewers join through the registry, so one movement is one write regardless of how many maps track the character. Teardown matrix: toggle-off deletes the registry row; access revocation cascades registry deletion inside the existing projection apply; map deletion sweeps its registry rows through the existing map purge door; account/character purge deletes both tables through a new bearer-gated purge door registered as a purge contributor with `NON_NEON_HOMES` coverage; EVE-side scope loss stops polling per character via the eligibility gate (`reauth_required`, no writes). **Rejected:** Neon-owned opt-in with projection (identity-grade machinery and a slow toggle round-trip for what is live map state); per-(map, character) location documents (write amplification and divergent location truth).
- **Plan — classifier placement: pure library, client/test evaluated.** `classifyMovement` lives beside the map pure-logic peers (`src/data/maps/`), takes geography as injected functions, and never runs inside Convex — the gate graph stays out of the sync action and the Convex bundle. In 4.0.4.2.2 the tracked pilot's own client (guaranteed open, because polling is presence-gated) evaluates the same library to drive authoring. **Rejected:** server-side classification at apply time (requires the adjacency asset inside Convex — off-pattern payload and memory for a problem the client already solves).

### Interfaces and contracts

- `SYNC_DATASET_CONFIG.characterLocation` — `{ cadenceFloorMs: 5_000, tokenGroup: 'char-location', chainOnSuccess: true, rateKeyScope: 'subject' }`; the two new optional fields default to today's behavior for existing datasets.
- `convex/schema.ts` `mapTracking` — `{ mapId: string, userId: string, characterId: number }`, indexes `by_map`, `by_map_user`, `by_user_character`; `characterLocation` — `{ userId: string, characterId: number, solarSystemId: number, stationId: number|null, structureId: number|null, shipTypeId: number|null, prevSolarSystemId: number|null, prevFresh: boolean, observedAt: number, etagLocation: string|null, etagShip: string|null }`, indexes `by_user`, `by_user_character`.
- `api.mapTracking.setTracking` mutation — `{ mapId, characterId, tracked: boolean }`; requires the caller's map-access claim; upserts/deletes the caller's own row; refuses nothing else (ownership is enforced structurally at sync time).
- `api.mapTracking.forMap` query — `{ mapId }` → tracking rows joined with location documents for map members, answered through the access claim as a value (empty when revoked, per the 4.0.2.3.1 subscription doctrine). The join key is pinned to the row's own `(userId, characterId)` pair via `by_user_character` — never `characterId` alone — so a forged tracking row naming someone else's character joins to no document and can never disclose location state across maps.
- `internal.characterLocationSync.syncUser` internalAction — `{ userId, generation }`; sequential per-character loop; per-character error taxonomy identical to the canary (`reauth_required`, `token_unavailable`, `budget_exhausted`, `contract_error`, `esi_<status>`; throw = transient/retryable).
- `internal.characterLocation.applySyncResults` internalMutation — generation-guarded; movement writes stamp `prevSolarSystemId`/`prevFresh` (continuity from the subject's previous covered run within `JUMP_CONTINUITY_MS`), fetch-side ship result, and nudge the user's `onlineStatus` subject due-now; 304 results write nothing to the payload table.
- `classifyMovement(facts, geography)` (pure, `src/data/maps/movement-classification.ts`) — `facts: { fromSolarSystemId: number|null, toSolarSystemId: number, prevFresh: boolean, shipBecameCapsule: boolean, sameSystemStateChange: boolean }`, `geography: { gateLinked(a, b): boolean, isWormholeSpace(id): boolean }` → `'stationary' | 'same-system-state' | 'gate-placement' | 'hole-crossing' | 're-anchor'`; total over inputs, no I/O, no throw.
- Engine chain-on-success — on `onSyncComplete` success with fresh presence and `chainOnSuccess`, the completion writes `nextDueAt` to the chain boundary itself — `max(minExpiresAt, now + cadenceFloorMs)`, **jitter-free** (jitter exists to stagger the shared scan's herds; a per-subject chain must not be re-armed later than its own scheduled hop, or every hop no-ops against the due-ness check and the cadence silently degrades to the 30s scan) — and schedules `internal.engine.chainDispatch` (`{ dataset, userId }`) at that same instant. `chainDispatch` re-reads the subject and calls the existing private `dispatch` only when the subject is idle, `nextDueAt` is non-null and reached, and presence is fresh; otherwise it no-ops. Failed completions keep today's jittered floor re-arm and never chain, so takeover, generation, and scan-retry semantics are untouched.
- `POST /purge-location-tracking` (Convex HTTP, bearer-gated) — `{ userId, characterId | null }` → deletes `characterLocation` docs and `mapTracking` rows; driven by `locationTrackingPurgeContributor` registered in `src/composition/purge/register-all.ts`.

### Control and data flow

Opening a tracked map mounts the toggle surface, which mounts `useSyncSubject('characterLocation', ownTrackedCharacterIds)` → mount heartbeat → immediate dispatch (stale) → Workpool runs `syncUser`: enumerate the caller's characters from Neon, intersect with `mapTracking` rows, gate per character on `canSyncLocation`, vend tokens, `readEsiAuthed` location with held ETag (304 → unchanged; 200 → parse), fetch ship only for characters whose system changed, then one generation-guarded `applySyncResults` writes changed documents, stamps continuity facts, and nudges `onlineStatus` when movement was observed. Completion stamps the subject (cache window, rate-limit snapshot) and — success + fresh presence — schedules `chainDispatch` at the `Expires` boundary, sustaining the ~5s loop while the map stays visible on any monitor (visibility-gated heartbeats, not focus). Client-side, viewers read `forMap`; the decision table classifies transitions from the stored facts plus the already-loaded adjacency asset. Failure at any point ends the chain and the 30s scan resumes ownership; closing the map lets presence go cold, the scan retires the subject, and polling stops.

### Edge and failure behavior

- Stationary pilot (ETag match) → 304 → no payload write, no subscriber re-fire; subject bookkeeping only — the contract's zero-write case.
- Dock/undock/station change (same system) → payload patch of state fields; verdict `same-system-state`; never a jump, never chain-doc adjacent.
- ESI transient failure (network, 5xx) → action throws → Workpool retries (4 attempts, exponential) → terminal failure recorded on the subject; no chain; scan re-arms at the cadence floor.
- Missing scope / no refresh token / mid-run unlink → per-character recorded error (`reauth_required` / `token_unavailable` / skip), other characters unaffected, no write for the errored character.
- ESI budget exhausted → run stops, recorded, resumes on the next dispatch — identical to the canary.
- Presence goes cold mid-chain (tab hidden/closed) → completion declines to chain; scan's cold branch retires the subject; return beat resumes instantly.
- Tracked character with no location document yet (first sample) → written with `prevSolarSystemId: null` → verdict `re-anchor` (baseline).
- Sample gap beyond `JUMP_CONTINUITY_MS` with a system change → `prevFresh: false` → `re-anchor`; no invented path.
- Concurrent chain and heartbeat/scan dispatch → existing `isRunningFresh`/generation guards make the duplicate a no-op.
- Map deleted / access revoked mid-poll → registry rows are gone at the next poll-set read; the character drops out of the union; revocation cascade also removes rows immediately.
