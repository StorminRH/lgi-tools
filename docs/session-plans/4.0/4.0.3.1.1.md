## Scope (the destination)

The session ends with a new pure directory, `src/mapper/layout/`, owning the
deterministic layout kernel:

- **Input:** `LayoutFacts` — systems in synchronized creation order,
  connections in synchronized creation order, an optional synchronized root
  override. Array position carries the order; no other fact may influence
  shared layout (HC-2).
- **Derivation:** a spanning tree from the root (default: first system in
  creation order; operator decision) via first-parent-wins over
  creation-ordered connections; connections that join two already-attached
  systems are loop-closing and have zero positional influence (operator
  decision); systems not yet connected to the root park deterministically in an
  overflow sector by creation order.
- **Output:** one `ChainPosition` per input system, radial compass-tree shaped:
  root centered, depth mapped to rings, root-subtrees claiming compass sectors
  in creation order, siblings subdividing their parent's wedge in creation
  order.
- **Engine decision:** ELK radial (elkjs 0.12.0) and the compass-sector
  fallback both run the identical property harness over a seeded generated
  corpus; a weighted scorecard (hard gates: determinism, no-overlap; weighted:
  stability blast radius, crossings, wedge balance, dependency cost,
  tunability) plus rendered snapshots go to the operator, who selects the
  engine and its spawn-movement configuration posture. The loser is deleted.

Stability is deliberately configurable rather than absolute: the operator ruled
(2026-08-01) that nodes may move on new spawns depending on look and feel, so
the kernel exposes wedge policy as configuration (`fixed-slot`: adds move
nothing; `proportional`: a sector fill re-spreads exactly its sibling group),
the suites measure and record the moved-set per configuration, and the final
feel judgment belongs to 4.0.3.1.2's live tuning loop. Contract §§3–6 are
satisfied without widening: DC-1/DC-2 by the pure seam and determinism gate,
DC-3 by the measured stability fixtures under the ratified configuration,
DC-4 by the generated-chain properties, DC-5 by the recorded comparison; no
integration surface changes, so OOS-1/OOS-2 hold by construction.

## Resolved implementation decisions

- **Contract PD-1 — the graph and position contract: `LayoutFacts → Promise<ReadonlyMap<number, ChainPosition>>`.**
  Systems and connections arrive as readonly arrays whose order IS synchronized
  creation order; `rootSystemId` is an optional synchronized override defaulting
  to the first system (operator decision: home-by-default with a settable
  root later; the setter is future synchronized state, not this session).
  Output reuses `ChainPosition` from `intents.ts`. The kernel type is async so
  one seam admits both engines (elkjs is promise-based); the compass engine's
  core stays a synchronous pure function wrapped at the seam. No production
  bridge to `PlacementAssigner` ships this session — 4.0.3.1.2 owns the worker
  bridge and its caching — but a test proves kernel output drives
  `reconcileChain` into correct `system-appeared`/`system-moved` intents.
  Named consequence for that bridge (recorded now so 4.0.3.1.2 starts from a
  problem, not a rediscovery): `reconcileChain` consults its assigner
  synchronously and `use-map-chain.ts` re-merges only when `chainSignature`
  changes, so an async kernel result resolving after a merge has no re-merge
  trigger of its own — 4.0.3.1.2 must design one (for example a cached-
  positions ref whose worker-resolution bump forces a re-merge) plus the
  first-appearance-before-resolution rendering behavior, without changing the
  frozen reconciler/intent contract.
  **Rejected:** implementing the kernel as a `PlacementAssigner` directly — its
  input carries current positions and lock state, which HC-2 forbids the shared
  layout from seeing; purity by type beats purity by discipline.
- **Contract PD-2 — the ELK experiment: elkjs 0.12.0, `org.eclipse.elk.radial`, fixed seed, creation-index ordering, full documented matrix.**
  Installed as a regular dependency for the probe phase (removed if ELK loses).
  Matrix pinned from current primary documentation (eclipse.dev/elk reference,
  elkjs README, retrieved 2026-08-01): `org.eclipse.elk.randomSeed` fixed
  non-zero (the default seeds from system time — determinism requires this),
  `radial.sorter` ∈ {`NONE`, `ID`} with `radial.orderId` = creation index,
  `radial.wedgeCriteria` ∈ {`NODE_SIZE`, `LEAF_NUMBER`}, `radial.compactor` ∈
  {`NONE`, `RADIAL_COMPACTION`, `WEDGE_COMPACTION`}, `radial.centerOnRoot` =
  true, `radial.radius` = the shared ring-spacing constant. Probes run through
  the promise API in Vitest (no worker; documented Node support). Documented
  prior, carried into the plan honestly: wedges are allocated proportionally to
  subtree size with no documented angle-freezing option and no documented root
  designation, so ELK is expected to score poorly on stability — the probes
  measure it anyway. **Rejected:** `layered`/`mrtree` algorithms (not the
  radial compass shape the product contract names) and every force/stress
  algorithm (HC-3).
- **Contract PD-3 — the selection threshold: weighted comparison with two hard gates, decided at an operator pause.**
  Operator-directed (2026-08-01) divergence from DC-3's absolute wording,
  recorded for the as-built: stability is a weighted, configurable axis, not a
  disqualifier. Hard gates any winner must pass: determinism (identical facts →
  byte-identical positions, in-process and cross-process) and zero node overlap
  at the shared minimum-separation constant. Weighted axes, measured on the
  identical seeded corpus: leaf-add moved-set size, sector-fill blast radius
  (moved nodes outside the sibling group), crossings beyond loop-closing edges,
  wedge balance (from rendered snapshots), dependency and bundle cost (~1.2 MB
  compressed elkjs versus zero-dependency ~150-line fallback), and tunability
  against 4.0.3.1.2's named dial set (ring spacing, wedge width, sibling gap,
  direction bias). The operator reviews the scorecard plus per-configuration
  SVG snapshots (uncommitted session artifacts, 4.0.2.2.2 precedent) and
  selects the engine and configuration posture; fallback selection is the
  contract's G-1 approval. **Rejected:** absolute disqualification on any DC-3
  deviation — the operator explicitly opened spawn movement to feel-based
  tuning in 4.0.3.1.2.
- **Plan — loser disposition and record home (operator decisions):** the losing
  engine's code is deleted before the final commit (and `elkjs` uninstalled if
  it loses); git history and the comparison record preserve the evidence. The
  DC-5 decision record — scorecard, probe measurements, and documentation
  citations — lives in the session as-built
  (`docs/session-as-built/4.0/4.0.3.1.1.md`), not a standalone ADR.
- **Plan — proof kit placement:** the seeded chain generator, geometry
  predicates (pairwise separation, segment intersection), and digest harness
  live in `src/mapper/layout/proof-kit.ts`, consumed only by the layout suites
  (established test-helper pattern, e.g. the DB test harness); fixtures commit
  their seeds and expected digests.

- `src/mapper/layout/proof-kit.ts` — seeded chain generator, geometry

### Interfaces and contracts

- `LayoutFacts` — `{ readonly systems: readonly { readonly systemId: number }[]; readonly connections: readonly { readonly fromSystemId: number; readonly toSystemId: number }[]; readonly rootSystemId?: number }`.
  Draft contract comment: “The synchronized graph facts — the only inputs that
  may influence shared layout (contract HC-2). Array order is synchronized
  creation order; a root override must itself be synchronized state.”
- `LayoutConfig` — `{ readonly ringSpacing: number; readonly minSeparation: number; readonly wedgePolicy: 'fixed-slot' | 'proportional'; readonly directionSequence: readonly number[] }`
  (exact knob set may grow during execution; every knob is a code constant
  identical on every client this session — 4.0.3.1.2 turns them into dials).
- `LayoutKernel` — `(facts: LayoutFacts, config?: LayoutConfig) => Promise<ReadonlyMap<number, ChainPosition>>`.
  Draft contract comment: “The pure seam (contract HC-1): facts in, one
  position per input system out. Deterministic — no randomness, clock, or
  caller state; identical facts and config yield identical positions on every
  client (D1/D2). Async only to admit promise-based engines.”
- `deriveChainTree(facts: LayoutFacts)` → `{ rootSystemId: number | null; parents: ReadonlyMap<number, number>; childrenInOrder: ReadonlyMap<number, readonly number[]>; loopEdges: readonly LayoutEdge[]; orphans: readonly number[] }` —
  pinned attachment semantics: a single scan over connections in creation
  order, attaching **immediately** when exactly one endpoint is attached (the
  attached endpoint becomes the parent); the scan repeats in full passes until
  a pass makes no new attachment. Every connection is classified **exactly
  once**: examined while unclassified, it becomes a tree edge when exactly one
  endpoint is attached, becomes loop-closing when both endpoints are already
  attached, and stays unclassified when neither is; a classified edge is
  excluded from all later passes, so a tree edge is never re-read as
  loop-closing. Duplicate and self edges classify as loop-closing. Two pinned
  examples, each a named unit case: single-pass diamond — creation-ordered
  edges `(A,C)`, `(B,C)`, `(A,B)` with root `A` yield `parent(C)=A`,
  `parent(B)=C`, `(A,B)` loop-closing; multi-pass — edges `(B,C)`, `(A,B)`
  with root `A` skip `(B,C)` in pass 1, attach `parent(B)=A` via `(A,B)`,
  then attach `parent(C)=B` via `(B,C)` in pass 2, with `(A,B)` remaining a
  tree edge.
- No existing export changes: `intents.ts` supplies `ChainPosition` unchanged;
  `placement.ts`, `reconciler.ts`, and every canvas module keep their shipped
  signatures.

### Control and data flow

No runtime data flow changes this session: the live path
(subscriptions → `reconcileChain` → `gridAssigner` → canvas) is untouched, and
the kernel is exercised only by tests and probe scripts. The proven-for-later
flow is: `LayoutFacts` (from the same creation-ordered rows the reconciler
already receives) → `deriveChainTree` → engine geometry → positions map →
(4.0.3.1.2's worker bridge) → `PlacementAssigner` proposals → `system-moved` /
`system-appeared` intents. The reconciler-compat test executes exactly that
chain minus the worker, feeding a kernel result through a stub assigner into
`reconcileChain`.

### Edge and failure behavior

- Empty `systems` → empty position map; no throw (kernel is total).
- Single system → it is the root, placed at the origin.
- `rootSystemId` names an absent system → the override is ignored and the
  creation-order default applies (fail-safe, deterministic, unit-tested).
- A system with no path to the root (its connection has not drained yet, or a
  generated adversarial graph) → parked deterministically in the overflow
  sector by creation order; when its edge arrives it relocates into its wedge
  as an ordinary spawn move — never a crash, never nondeterminism.
- Duplicate edges between one pair, and self-edges → classified loop-closing;
  zero positional influence; unit-tested.
- An engine that fails to complete a probe run (rejects, times out, or returns
  a partial position map) → the failure is recorded as a hard-gate fail on the
  scorecard for that configuration; the session continues with the surviving
  candidates.
