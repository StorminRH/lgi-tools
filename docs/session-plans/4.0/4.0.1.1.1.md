## Why now

Decision D5 makes this helper the one and only access gate for every later map
caller, and both sub-version 4.0.2.2's Convex projection writer and sub-version
4.0.4.4's access editor are written against its signature. Nothing in the
repository can answer "may this user see this map" today, so the signature must
be settled before a second consumer exists to constrain it. Landing the tables,
the gate, and the principal seam together is what lets every later Phase 1 and
Phase 2 slice assume a trustworthy access answer instead of inventing one.

## Scope (the destination)

The finished slice adds two Neon tables and one composed server-side helper.
`maps` holds a map's identity, display name, creator, timestamps, and its
archive marker. `map_access` holds delegated grants: one row per
map-plus-grantee, where the grantee is a character or a corporation and the role
is viewer, editor, or owner. Ownership itself is not a grant row — `maps.user_id`
is authoritative, so a creator cannot lose their own map by deleting a row.

`getMapAccess(userId, mapId)` returns `{ role, canView, canEdit }`. It resolves
the user's principal set — their linked characters, plus the corporations those
characters currently belong to — reads that map's grants, and applies one pure
role rule. Character grants match on character id and never consult ESI. Corp
grants match against the freshness-gated affiliation cache that shipped in
3.7.3.2, so a corp grant costs at most one bulk ESI call per user per hour and
usually none. The helper awaits that resolution and always returns an
authoritative answer.

Contract §3's done conditions are satisfied without widening §4: `DC-1` by the
migration, `DC-2` and `DC-3` by the gate and its coverage, `DC-4` by the enum
plus capability-record representation, and `DC-5` and `DC-6` by consuming the
already-shipped and already-declared affiliation dataset. Contract §5's
exclusions stay untouched because nothing in this session renders UI, writes a
grant row, touches `convex/`, or creates `src/mapper/`. Contract §6's constraints
are carried verbatim into the `hard_constraints` block above.

## Resolved implementation decisions

- **Contract PD-1 — the principal-resolution seam: `resolveMapPrincipals(userId)`
  exported from `src/composition/map-access.ts`, returning
  `{ characterIds, corporationIds }`.** It composes existing auth primitives:
  `refreshStaleAffiliationsForUser` (a no-op when nothing is stale), then
  `getUserAffiliations`, then `memberCorpIds` for the corp half and the same
  rows' character ids for the character half. Composition is the correct owner
  because the seam crosses `platform/auth` and `data/maps`, and Fallow's rules
  forbid `data` importing `platform/auth` — placing it in `platform/auth`
  instead would force an auth-to-maps edge and put a new file beside the AF-008
  authorization-surface watch. **Rejected:** a `src/platform/auth/principals.ts`
  module. It reads as the more natural home for an identity question, but it
  must import the map principal vocabulary from `src/data/maps/access.ts` to
  stay type-aligned, which inverts the dependency the gate needs and spreads one
  seam across two zones for no gain. Zone note the executor must respect: the
  `convex` zone may import only `platform/esi`, `platform/auth`, `data`, and
  `lib`, so `resolveMapPrincipals` serves Neon-side callers only. Sub-version
  4.0.2.2's projection writer is Neon-side by its own contract's `HC-2` and may
  call it; the Convex-side gate never needs it, because it reads the projected
  access rows by verified token identity. The cross-runtime guarantee is carried
  by `src/data/maps/access.ts`, which `convex/` may import — so decision D5's
  single rule stays reachable without a forbidden composition edge.
- **Contract PD-2 — corp-grant resolution: the grant row is static and stores the
  corporation principal; membership resolves per user at check time from the
  freshness-gated affiliation cache.** No corp member roster is ever fetched or
  stored, so `DEP-6`'s static-access-list posture holds: adding a corp is one row
  that never changes until an operator edits it. What varies is each user's own
  cached corp id, which the shipped login hook, on-view refresh, and nightly cron
  already maintain. The gate calls `refreshStaleAffiliationsForUser` before
  deciding, so a first-ever sign-in resolves immediately rather than failing
  closed against an empty cache, and a fresh cache dispatches nothing. Because
  `POST /characters/affiliation/` is unauthenticated it draws on the shared
  per-IP budget rather than a per-character bucket, but it accepts up to 1000 ids
  per request and is hour-gated per character, so the worst case is one bulk-
  capable call per user per hour. **Rejected:** expanding a corp grant into a
  stored member list at grant-write time. It requires a corp roster read the
  repository has never taken, needs its own registry entry and refresh trigger
  the contract excludes in `OOS-4`, and goes stale the moment anyone joins.
- **Contract PD-3 — role representation: a Postgres enum driven from
  `MAP_ROLES = ['viewer', 'editor', 'owner'] as const`, with capabilities read
  from an explicit `MAP_ROLE_CAPABILITIES` record and multi-grant precedence
  from an explicit ordered list.** The enum-from-`as const` pattern is the
  repository's stated invariant and matches `ownedAssetOwnerTypeEnum`. Adding a
  value later is a hand-written `ALTER TYPE ... ADD VALUE` custom migration —
  confirmed against current Drizzle documentation, which routes enum additions
  through `drizzle-kit generate --custom` — and it rewrites no rows, satisfying
  `DC-4`. Capabilities never derive from ordering, satisfying `HC-4`. When a user
  matches more than one grant, capabilities union and the reported role is the
  first match in the precedence list. **Rejected:** a `text` column with a check
  constraint, and an integer rank. The text form loses database-level vocabulary
  enforcement for no gain now that `SC-4` proves enum extension is cheap; the
  integer rank makes an access-managing-but-cannot-delete role unrepresentable,
  which `HC-4` forbids outright.
- **Contract PD-4 — affiliation cache time and stale-gate threshold: 3600
  seconds, unchanged.** Verified against the live ESI specification during
  planning: `POST /characters/affiliation` publishes `x-client-cache-ttl: 3600`
  and `x-server-cache-ttl: 3600`. The registry's recorded
  `verifiedCacheSeconds: 3600` therefore remains correct, and
  `freshnessGate('affiliations').ttlMs` continues to derive the one-hour window
  every membership predicate already reads. One drift note for the executing
  agent: the specification renamed this field from `x-cached-seconds`, which the
  existing source comment still cites; the value did not change, and correcting
  that comment is the only permitted edit to the shipped affiliation modules.
  **Rejected:** introducing a map-specific TTL override. It would create a second
  freshness authority for one dataset and contradict `HC-2`'s placement rule.

## Implementation blueprint

### Owned surfaces

- `src/data/maps/schema.ts` — owns the `maps` and `map_access` Drizzle tables,
  the `MAP_ROLES` and `MAP_ACCESS_OWNER_TYPES` `as const` vocabularies, and the

- `src/data/maps/access.ts` — owns the pure role decision: the capability record,

- `src/data/maps/queries.ts` — owns the two reads the gate needs: a map's
  creator and archive marker, and that map's grant rows.
- `src/data/maps/purge.ts` — owns teardown of both tables at the `credential`
  tier, on the character axis for grants and the user axis for owned maps.
- `src/composition/map-access.ts` — owns `resolveMapPrincipals` and the composed
  `getMapAccess` gate. The only production module that decides map access.
- `src/composition/drizzle-schema.ts` — gains one re-export line for the slice.
- `src/composition/purge/register-all.ts` — gains the maps contributor.
- `src/composition/table-growth-registry.ts` — gains two `purge-managed` stories.
- `src/composition/data-ownership-registry.ts` — gains `data/maps` to the

- `drizzle/` — gains one generated migration creating both enums and both tables.

### Interfaces and contracts

- `resolveMapRole(input: { isCreator: boolean; grants: readonly MapGrant[];
  principals: MapPrincipals }): MapAccess` — pure. Returns
  `{ role: 'owner', canView: true, canEdit: true }` when `isCreator`. Otherwise
  keeps grants whose `ownerType`/`ownerId` pair appears in `principals`, unions
  their capabilities from `MAP_ROLE_CAPABILITIES`, and reports the first role in
  `MAP_ROLE_PRECEDENCE` that matched. Returns `{ role: null, canView: false,
  canEdit: false }` when nothing matches. Draft contract comment: *"Decides one
  user's role and capabilities for one map from its grant rows and that user's
  resolved principals. The single access rule for the version (decision D5):
  capabilities come from the capability record, never from role ordering, so a
  later access-managing role that cannot delete a map stays representable."*
- `resolveMapPrincipals(userId: string): Promise<MapPrincipals>` — where
  `MapPrincipals` is `{ characterIds: readonly number[]; corporationIds:
  readonly number[] }`. Refreshes only stale affiliations, then reads them once.
  Character ids are every linked character regardless of affiliation freshness;
  corporation ids are fail-closed and exclude any stale or never-refreshed row.
  Draft contract comment: *"Resolves a Better Auth user into the EVE principals
  they act as. The single seam where character and corporation principals bind to
  a user id; the map gate, the Convex access projection, and the access editor
  all resolve through it."*
- `getMapAccess(userId: string, mapId: string): Promise<MapAccess>` — reads the
  map row, resolves principals, reads that map's grants, and applies
  `resolveMapRole`. Returns the all-false shape for a map that does not exist.
  Awaits every resolution so the answer is authoritative and never provisional.
  Draft contract comment: *"The single map authorization gate (decision D5).
  Resolves a signed-in user and a map into their role and their view and edit
  capability. Always authoritative and safe to await inside a Suspense boundary;
  never returns a provisional deny that a later refresh would contradict. No
  second access-check path may exist."*
- `mapsPurgeContributor: PurgeContributor` — `tier: 'credential'`, claiming both
  tables. `purgeCharacter` deletes grant rows whose `ownerType` is `'character'`
  and whose `ownerId` is the purged character; `purgeUser` deletes that user's
  maps and their dependent grant rows.

### Control and data flow

A server caller invokes `getMapAccess(userId, mapId)`. The gate reads the map row
from Neon; a missing row short-circuits to the all-false result before any
affiliation work. It then calls `resolveMapPrincipals`, which first calls
`refreshStaleAffiliationsForUser` — the only outward boundary in the flow, and a
no-op unless a linked character's affiliation is missing or older than the
one-hour window, in which case the shipped `esiFetch` path dispatches one bulk
request under the shared budget and writes the result to `characters`. Principals
are then read from Neon and the corp half is filtered fail-closed on freshness.
The gate reads that map's grant rows from Neon and hands both sets to the pure
`resolveMapRole`. Three Neon reads and at most one hour-gated ESI call produce
the answer; nothing is written except the affiliation cache refresh. No Convex
document is read or written anywhere in this path.

### Edge and failure behavior

- Map id does not exist → `{ role: null, canView: false, canEdit: false }`,
  decided in the gate before principal resolution.
- User has no linked characters → empty principal set, so only creator ownership
  can grant access; the gate owns this and the pure rule needs no special case.
- ESI unreachable and the user's corp was never cached → `fetchAffiliations`
  swallows the failure, `memberCorpIds` returns an empty list, and corp grants
  do not match. Creator ownership and character grants are unaffected because
  neither consults ESI. The pure rule owns the fail-closed result.
- Character affiliation is stale but the user holds a direct character grant →
  access is granted. Freshness gates the corp half only; the character axis is
  identity, not cached state.
- A user matches several grants, or is both creator and grantee → capabilities
  union and the reported role is the highest-precedence match, owned by
  `resolveMapRole` and covered by a dedicated unit test.
- Map is archived → `archived_at` is stored but the gate does not filter on it.
  Archive lifecycle semantics belong to sub-version 4.0.4.4; encoding a meaning
  here would create a second access rule.
- Character is transferred to a different human → the owner-hash reconciler runs
  its `credential`-tier purge on the next sign-in, which now includes the maps
  contributor, so the previous owner's grants are destroyed before the new owner
  resolves any principal.
