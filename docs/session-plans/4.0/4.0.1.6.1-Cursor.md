## Why now

Phase 1 closes the reference layer the mapper will read before the map exists.
Universe assets and the wormhole codex shipped in 4.0.1.3 without per-system
statics; the signature inference engine in 4.0.4.3 cannot constrain a system's
unknowns without them. This slice is the version's only genuine external feed
with a human promote gate, so the approved topology keeps it as its own
sub-version rather than bundling it with derived assets.

## Scope (the destination)

A new `src/data/wormhole-statics/` slice owns:

- **Pull:** discover the feed version from `controller.js`, fetch
  `static.json` at that version through a declared vendor wrapper, normalize to
  `(system_id, type_id, type_code)` assignment rows, and write a version-pinned
  snapshot in Neon without mutating the promoted copy.
- **Promote gate:** compute the absolute assignment-pair delta against the
  current promoted copy; auto-promote when within threshold (or bootstrap with
  size floor + lineage agreement); otherwise mark the snapshot `pending_review`
  and present the diff on an admin surface; admin promote applies the snapshot
  explicitly under the same advisory lock.
- **Cross-check:** before bootstrap auto-promote, and again after every
  successful promote, fetch Pathfinder `system_static.csv`, compare
  `(system_id, type_id)` sets, and record agreement counts plus disagreement
  samples — never silently reconcile. Bootstrap auto-promote requires set
  agreement; post-promote reports ongoing drift without blocking.
- **Serving:** read API/query returns per-system statics solely from the
  promoted tables; with the feed down or never promoted, last-good (or empty)
  still answers without erroring on the external host.
- **Attribution + declaration:** `/legal` credits anoik.is; dataset registry
  entry + vendor entries + `DATA_SOURCES.md` status/succession text land in the
  same change.

Contract §§3–6 are satisfied without widening: no inference consumer, no
mapper code, no succession decision, no effects ingest.

## Resolved implementation decisions

- **Contract PD-1 — Snapshot and promote mechanics: dual-table snapshot →
  promote with admin diff presentation.** Neon tables:
  (1) `wh_statics_snapshots` — one row per pull (`id`, `feed_version`,
  `pulled_at`, `status` ∈ `pending_review|promoted|rejected`,
  `assignment_count`, `system_count`, `diff_summary` jsonb);
  (2) `wh_statics_snapshot_assignments` — `(snapshot_id, system_id, type_id,
  type_code)` for the pinned pull;
  (3) `wh_statics_promoted_assignments` — the served copy keyed by
  `(system_id, type_id)` with `type_code`, `promoted_at`, `source_snapshot_id`,
  `feed_version`;
  (4) `wh_statics_meta` — keys for `promoted_feed_version`,
  `last_crosscheck_at`, `last_crosscheck_report` jsonb.
  Cron/on-demand pull only inserts a snapshot + assignment rows, then runs the
  promote decision in the same locked critical section. Auto-promote copies
  snapshot assignments into the promoted table inside one transaction when
  under threshold (or bootstrap rules); over-threshold sets `pending_review`
  and stops. Admin UI at `/admin` gains a Statics section showing pending
  snapshot id, feed version, counts, and a compact diff (added/removed/changed
  assignment counts + capped sample rows) from `getWhStaticsAdminStatus` —
  server-rendered, no separate admin GET API. Admin form POSTs
  `/api/admin/wh-statics/promote` and `/api/admin/wh-statics/reject` follow the
  live `checkAdmin` + `requireSameOrigin` + `parseFormBody` +
  `capabilityRoute` + 303 redirect pattern (`esi-jobs/retry` exemplar), with
  form field `snapshotId` and capabilities `admin.wh-statics-promote` /
  `admin.wh-statics-reject`. Both admin mutations acquire
  `ADVISORY_LOCK_WH_STATICS` before promote/reject. Reject sets snapshot status
  `rejected` and leaves the promoted copy unchanged. **Rejected:** single-table
  overwrite on pull (violates HC-1/HC-2); SDE-style auto-apply on version drift
  (no human gate); storing only raw JSON blobs without normalized rows (makes
  diff and serving awkward for 4.0.4.3 consumers); JSON body admin APIs that
  diverge from the established form/redirect admin mutations.

- **Contract PD-2 — Review threshold: absolute assignment-pair delta > 25
  blocks auto-promote when a promoted copy exists; bootstrap requires size
  floor + lineage agreement.** Diff unit is the set of `(system_id, type_id)`
  pairs. `delta = |only_incoming| + |only_promoted|`. When a promoted copy
  exists: auto-promote iff `delta ≤ 25`; otherwise `pending_review`. When the
  promoted table is empty (bootstrap): auto-promote only if
  `assignment_count ≥ 3700` (live corpus is 3,772; floor rejects truncated
  first pulls) **and** a pre-promote Pathfinder lineage cross-check reports
  `onlyPromoted === 0 && onlyLineage === 0` (perfect set agreement). Otherwise
  bootstrap stays `pending_review` for admin. Version number alone does not
  gate — a version bump with delta 0 auto-promotes. **Rejected:**
  percentage-only thresholds; blocking on any nonzero delta; blocking solely on
  version jumps; unconditional first-promote with only a zero-systems check
  (would let a truncated feed become the HC-1 last-good copy).

- **Contract PD-3 — Cadence and shell placement: weekly Monday 08:00 UTC via
  the existing cron shell.** `vercel.json` entry
  `{ "path": "/api/cron/refresh-wh-statics", "schedule": "0 8 * * 1" }` —
  avoids the daily 11:xx pack and GSC's 09:00. Declaration uses
  `defineCronRoute` / `CronRouteDeclaration` with `wakeClass: 'batch'`,
  advisory lock `ADVISORY_LOCK_WH_STATICS` in slice constants, capability
  `cron.refresh-wh-statics`, registry + capability census updates, and an
  `idempotency-registry` `CRON_ENTRIES` row (`cron/refresh-wh-statics`,
  `key-protected` via the advisory lock, vendor `anoik-statics`). Cron work
  also prunes old non-promoted snapshots per the growth-registry retention
  policy (keep the latest pending/rejected plus a small promoted history)
  before upstream pull, mirroring GSC housekeeping. On-demand:
  `pnpm db:refresh-wh-statics` → `src/scripts/refresh-wh-statics.ts` wraps the
  same ingest entry in `withAdvisoryLock` on `resolveLockConnectionUrl()`
  (the `refresh-sde.ts` pattern), is listed in `.fallowrc.json` `entry`, and
  shares the lock with cron/admin. **Rejected:** daily cadence; cloning a
  standalone scheduler; piggybacking onto `refresh-sde`; a lock-free CLI that
  can race the cron.

- **Contract PD-4 — Cross-check surfacing: Pathfinder `system_static.csv`
  comparison recorded in meta and shown on admin; bootstrap-blocking,
  otherwise report-only.** Fetch
  `https://raw.githubusercontent.com/exodus4d/pathfinder/master/export/csv/system_static.csv`
  through declared vendor wrapper `pathfinder-lineage`, compute set
  differences, and store
  `{ agreed, onlyPromoted, onlyLineage, samples[], lineageFetchFailed? }` in
  `wh_statics_meta.last_crosscheck_report`. On bootstrap auto-promote, perfect
  agreement is required (PD-2). After any successful promote, disagreements
  never rewrite the promoted copy. Admin Statics section renders the latest
  report. Lineage fetch failure: bootstrap auto-promote blocks (cannot prove
  agreement); post-promote path records `lineageFetchFailed: true` and still
  keeps the promoted copy. Live evidence: current feeds agree 3,772/3,772.
  Naming: treat this CSV as the master plan's "Pathfinder-lineage" artifact.
  **Rejected:** making Pathfinder a second runtime source; failing every
  subsequent promote when lineage disagrees; silently preferring one side.

- **Contract PD-5 — Cache time and placement: Neon `global-cron` /
  `cron-cadence` with new upstream kind `anoik-statics`.** Registry entry
  `wh_statics`: `store: 'neon'`, `shape: 'global-cron'`,
  `freshnessModel: 'cron-cadence'`, `refreshOwner: { kind: 'cron', route:
  '/api/cron/refresh-wh-statics' }`, `upstream: { kind: 'anoik-statics' }`,
  mirror tables = the four tables above. Extend `EsiUpstream` with
  `'anoik-statics'`. Vendor resilience: add `anoik-statics` (wrapper
  `discoverAndFetchStatics` in `src/data/wormhole-statics/source.ts`, 10s
  `fetchWithTimeout`, no retry storm, weekly rate, degrade = keep promoted
  copy) and `pathfinder-lineage` (wrapper `fetchLineageStatics`, same timeout,
  degrade = skip/fail cross-check per PD-4). Host literals only in that source
  module; update lint rails including
  `eslint.config.mjs` `serverRootImportPatterns` for
  `@/data/wormhole-statics/source`, plus vendor census
  `EXPECTED_INTEGRATIONS`. **Rejected:** Convex placement; attaching columns
  onto `eve_solar_systems`; folding into `data/eve-data`.

### Interfaces and contracts

- `discoverAndFetchStatics(): Promise<{ feedVersion: number; systems: …;
  wormholes: … }>` — parses `static_expected_version` from controller.js,
  fetches `static.json?version=N`, validates body `version === N`, returns
  normalized payload; throws typed failure on transport/parse errors without
  touching Neon.
- `fetchLineageStatics(): Promise<ReadonlyArray<{ systemId: number; typeId:
  number }>>` — downloads and parses the Pathfinder CSV.
- `pullWhStaticsSnapshot(db): Promise<PullResult>` — must be invoked only under
  `ADVISORY_LOCK_WH_STATICS`. Writes snapshot rows, computes delta, applies
  PD-2 auto-promote or `pending_review`, and on promote runs cross-check
  persistence. Returns `{ snapshotId, feedVersion, delta, status }` where
  status is `promoted` or `pending_review`.
- `promoteWhStaticsSnapshot(db, snapshotId)` /
  `rejectWhStaticsSnapshot(db, snapshotId)` — admin paths; also require the
  advisory lock; reject unknown/non-pending ids.
- `getSystemStatics(db, systemId): Promise<ReadonlyArray<{ typeId: number;
  typeCode: string }>>` — serving read from promoted table only.
- `getWhStaticsAdminStatus(db)` — pending snapshot summary, promoted meta,
  latest cross-check report for the server-rendered admin section.
- Dataset entry `wh_statics` as specified in PD-5.
- Cron response type and admin form schemas in slice `api-contract.ts`.
- Draft export contract comments on every new production export.

### Control and data flow

1. Cron/CLI → unpooled advisory lock → optional snapshot prune →
   `discoverAndFetchStatics` (no DB held across network; lock connection idle
   only) → normalize codes via feed `wormholes[code].typeID` → insert snapshot
   + assignments → compute delta vs promoted → PD-2 decision (including
   bootstrap size floor + pre-promote lineage agreement) → on promote run
   post-promote cross-check persistence → release lock → telemetry.
2. Admin form POST → `checkAdmin` + same-origin + parse form → advisory lock →
   promote or reject transaction → on promote cross-check → 303 back to
   `/admin` → release lock.
3. Serving → `getSystemStatics` SELECT from promoted table only; never calls
   anoik or Pathfinder.

### Edge and failure behavior

- Controller.js unreachable or unparseable → pull fails; promoted copy
  unchanged; cron reports degraded/skipped with reason.
- `static.json` version mismatch vs discovered N → fail closed; no snapshot.
- Zero systems / unknown type codes → fail the pull (do not write a partial
  snapshot).
- Non-empty but truncated first pull (`assignment_count < 3700`) → snapshot
  written, bootstrap auto-promote blocked → `pending_review`.
- Bootstrap lineage disagreement or lineage fetch failure → `pending_review`;
  admin may still promote deliberately after review.
- Pathfinder CSV unreachable after a non-bootstrap promote → promote still
  succeeds; cross-check report records `lineageFetchFailed: true`.
- Concurrent cron + admin + CLI → advisory lock serializes; second caller gets
  busy skip / lock error as per cron-gate / script patterns.
- Reject of a `pending_review` snapshot → status `rejected`; promoted copy
  unchanged.
