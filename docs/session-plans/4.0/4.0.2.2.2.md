  authoritative. Convex `mapAccess` rows carry only `{ mapId, userId, roles }` —
  never grant rows, principal ids, corp ids, timestamps, or map metadata. Any
  claim state must be exactly reproducible by `projectMapAccess(mapId)` from
  Neon alone; the teardown+resync proof (SC-2) is the enforcement. Nothing ever

- **Contract HC-2:** No write flows from Convex to Neon, and no second
  access-check path exists. The only new cross-system call is a Neon-side POST
  to the bearer-gated Convex HTTP door; Convex gains no Neon client, no action

  a chain table without `requireMapAccess` first. `resolveMatchedMapRoles`
  remains the single rule; the gate keeps applying the same shared capability
  record to the projected role set.
- **Contract HC-3:** Revocation participates in every protected read set through
  the shipped gate. Do not weaken, cache, memoize, or bypass the gate's
  `by_map_user` claim read in any query; deleting a claim row must re-run every
  live subscription on that map for that user. SC-3's live probe is the direct
  witness.
- **Plan:** The projection write contract is declarative full-state per map: one
  request carries the complete desired claim set for one map, and the reconcile
  mutation converges storage to it (insert missing, update changed, delete
  absent, repair duplicates, skip identical). This single shape makes grant
  changes, teardown (`claims: []`), and resynchronization the same idempotent
  operation — there is no imperative add/remove API to drift.
- **Plan:** Exactly one `mapAccess` row per `(mapId, userId)` after any
  reconcile, enforced by the reconcile mutation itself (the sole production
  writer). `requireMapAccess` reads with `.unique()`, so a duplicate claim would
  make every gated call on that map throw. Three layers hold the invariant: the
  door's zod body rejects a payload containing the same `userId` twice (clean
  400), the mutation last-entry-wins dedupes its desired input and
  canonicalizes each claim's roles (unique, `MAP_ROLE_PRECEDENCE` order) before
  compare/store so the invariant survives any internal caller, and the mutation
  deletes stored duplicates it encounters rather than assume cleanliness.
- **Plan:** The new Neon-side module lives at
  `src/composition/map-access-projection.ts` and no new file may match the

- **Plan:** All Convex-bound reads stay indexed and bounded: reconcile reads one
  `by_map` claim scan (bounded by principal count), user purge deletes through
  `by_user` in batches of at most 128 with truthful `hasMore`, and no path adds

## Why now

The 4.0.2.2.1 gate fails closed for every production map because nothing writes
claims: the vault has a guard with an empty list. Until the durable rule is
projected, no live map read can ever succeed, and 4.0.2.3's reactive read path
cannot exist. Completing the projection, its teardown/resync proof, the live
revocation eviction, and the cost measurement finishes the sole collaborative
authorization path and closes sub-version 4.0.2.2 with its single PR.

## Scope (the destination)

The finished slice adds one Neon-side projection module, one Convex reconcile
surface behind the existing bearer-gated HTTP door, purge-time teardown wiring,
and the evidence the contract names. Concretely: `projectMapAccess(mapId)`
computes the complete desired claim set for one map from Neon (creator →
`owner`; character and corporation grants resolved to users through the
existing account/characters join and the single role rule) and POSTs it to
`/project-map-access`, whose internal mutation converges the `mapAccess` table
to that exact set. Teardown is the same call with an empty set; resync is the
same call again; user purge deletes claims through `by_user` via
`/purge-map-access`. The maps purge contributor captures affected map ids
before deleting durable rows and re-projects or tears down afterwards,
best-effort. The gate, chain tables, fixture functions, and every 4.0.2.2.1
behavior are unchanged. No UI, route, server action, grant editor, or
production subscription is added (IS-1/IS-2 delivered; OOS-1/OOS-2 untouched;
HC-1..3 held as above). Corp-membership drift after a projection run remains
stale by explicit operator ruling until a later session wires an automatic
trigger; resync is the documented correction.

## Resolved implementation decisions

- **Contract PD-1 — projected role claim and mapping: the full effective role
  array from `resolveMatchedMapRoles`, stored in `MAP_ROLE_PRECEDENCE` order.**
  Both ends already agree: `resolveMatchedMapRoles` was added in 4.0.2.2.1 as
  the capability-preserving set the writer consumes, and the Convex validator is
  compile-bound to `MAP_ROLES`. The claim is the rule's output, not its inputs:
  no grants, principals, or corp ids cross the bridge. Precedence ordering makes
  equal sets byte-comparable so an unchanged re-projection writes nothing.
  **Rejected:** projecting a single collapsed display role — it silently drops
  capabilities for multi-principal users and diverges from the shipped gate,
  which already stores and unions a role array.
- **Contract PD-2 — durable-side trigger and idempotent resynchronization
  boundary: a declarative full-state reconcile per map, exposed as one Neon-side
  seam (`projectMapAccess`) that every durable grant change must call; resync
  and teardown are the same operation.** Since no production grant editor exists
  until 4.0.4.4, the in-repo triggers this session are: the purge contributor
  (character purge deletes character grants → re-project affected maps; user
  purge deletes owned maps → tear down their claims and purge the user's own
  claims by `by_user`) and tests/probe. The reconcile mutation is idempotent by
  construction — converging storage to a stated set — so re-running after any
  fault, race, or drift is always safe and always correct against the Neon
  snapshot it was computed from. **Rejected:** imperative per-grant add/remove
  APIs (they drift under missed events and cannot self-heal) and wiring an
  affiliation-change trigger now (operator ruling: deferred; out of contract
  scope "on grant changes" and it would grow the auth-adjacent surface).
- **Contract PD-3 — deterministic subscription-cost method: an executable
  convex-test measurement at pinned fixture sizes plus the derived formula,
  recorded in `docs/SCRATCHPAD.md`.** The test seeds fixed collection sizes,
  drains each gated collection query, and asserts exact page row counts against
  `MAP_FIXTURE_PAGE_SIZE = 25`, making the cost claim executable: each gated
  call reads 1 indexed claim row + at most 25 payload rows; a full four-
  collection map watch is 4 claim reads + one page per open cursor per update
  cycle. The scratchpad entry records the formula, the pinned sizes, and the
  measured counts. **Rejected:** a reasoned-only formula (operator selected the
  executable variant; a silent cost regression should fail a test, not a
  memory).
- **Plan — revocation evidence shape: convex-test logic proof plus a live
  two-client probe against the real local backend (operator ruling: both).**
  The probe is not committed; its full procedure is in Ordered work step 7 and
  its transcript is recorded evidence. Feasibility is proven against installed
  versions: `ConvexClient.setAdminAuth(adminKey, identity)` exists in convex
  1.42.3 (`node_modules/convex/dist/esm/browser/simple_client.js:277`) and the
  local backend's admin key is at `.convex/local/default/config.json`
  (`adminKey`, ports 3210/3211). **Rejected:** committing the probe as a
  maintained script (adds permanent surface for one-time protocol evidence) and
  a manual two-browser demo (not reproducible, and no UI exists to drive).

### Interfaces and contracts

- `src/composition/map-access-projection.ts`:

  ```ts
  /** One projected claim: the complete effective role set one user holds on one map. */
  export interface MapAccessClaim {
    readonly userId: string;
    readonly roles: readonly MapRole[];
  }

  /**
   * Computes the complete desired claim set for one map from durable Neon state.
   * Creator resolves to ['owner']; every candidate user reached by a character or
   * corporation grant is resolved through resolveMapPrincipals and the single
   * resolveMatchedMapRoles rule. Users with an empty role set are omitted. A
   * missing map returns the empty set (its projection tears down). Deterministic:
   * results are sorted by userId and roles are in MAP_ROLE_PRECEDENCE order.
   * Refresh-shortfall guard: after the per-candidate refresh attempt, if any
   * candidate's affiliations remain stale (ESI unreachable — refreshAffiliations
   * swallows failures and leaves the cache stale), this throws
   * ProjectionUnavailableError instead of returning a silently shrunken set: a
   * transient outage must fail the projection loudly, never durably revoke
   * corp-derived claims that were not actually lost.
   */
  export async function computeMapAccessClaims(mapId: string): Promise<MapAccessClaim[]>

  /**
   * Projects one map's durable access into Convex: computes the desired set and
   * POSTs it to the bearer-gated /project-map-access door. One-way by
   * construction — it sends state and returns Convex's reconcile counts; it
   * never reads Convex to decide durable truth. Throws ProjectionUnavailableError
   * when the Convex URL or service secret is unset or the door answers non-2xx;
   * callers own retry/resync policy (grant-change callers surface the failure,
   * purge callers swallow it best-effort).
   */
  export async function projectMapAccess(mapId: string): Promise<ProjectionResult>
  ```

- `convex/mapAccessProjection.ts`:

  ```ts
  /**
   * Converges the mapAccess table to exactly the stated claim set for one map:
   * inserts missing rows, replaces rows whose ordered roles differ, deletes rows
   * for absent users and every duplicate beyond the first, and skips identical
   * rows so an unchanged re-projection writes nothing. Guarantees exactly one
   * row per (mapId, userId) afterwards for ANY caller: the desired input is
   * last-entry-wins deduped by userId and each roles array is canonicalized
   * (unique values, MAP_ROLE_PRECEDENCE order) before compare/store, so a
   * repeated userId or unordered roles in one payload cannot create duplicates
   * or byte-different equal sets. Empty claims = full teardown for the map.
   * Returns { inserted, updated, deleted, unchanged } for evidence.
   */
  export const reconcileMapClaims = internalMutation({ args: { mapId: v.string(), claims: v.array(v.object({ userId: v.string(), roles: v.array(mapRoleValidator) })) }, ... })

  /**
   * Deletes one user's claims across all maps through by_user in batches of at
   * most 128, returning { deleted, hasMore } so the calling HTTP action can loop
   * to completion without an unbounded single-transaction scan.
   */
  export const purgeUserClaims = internalMutation({ args: { userId: v.string() }, ... })
  ```

- `convex/http.ts` routes (both bearer-gated by the existing `bearerOk`,
  malformed/wrong-typed bodies → 400, missing/wrong bearer → 401):
  - `POST /project-map-access` body
    `{ mapId: string, claims: Array<{ userId: string, roles: MapRole[] }> }`
    (zod schema binds `roles` to the shared `MAP_ROLES` vocabulary, requires
    `roles` non-empty via `.min(1)`, and rejects a payload repeating a
    `userId` via `superRefine` — both as clean 400s before the mutation) → runs
    `reconcileMapClaims`, returns its counts as JSON.
  - `POST /purge-map-access` body `{ userId: string }` → loops
    `purgeUserClaims` until `hasMore` is false, returns `{ deleted }` totals.
- `src/data/maps/queries.ts` additions (both single batched selects, no N+1):
  - `getUserIdsOwningCharacters(characterIds: number[]): Promise<Map<number, string>>`
    — EVE-provider `account` rows keyed by character id.
  - `getUserIdsInCorporations(corporationIds: number[]): Promise<Set<string>>`
    — `account` ⋈ `characters` on the cached `corporationId`.
- The gate (`requireMapAccess`), fixture functions, and all chain-table

### Control and data flow

Grant-change / resync flow: caller → `projectMapAccess(mapId)` →
`getMapAccessSubject` + `getMapGrants` (Neon) → candidate users = creator ∪
character-grant owners ∪ corp-grant members (two batched queries over the
cached account/characters join; complete only with respect to the cached
affiliation snapshot — a superset in the leaving direction, while a pilot who
JOINED a granted corp but whose cache still shows the old corp is not
enumerated until the affiliation cron or a login refreshes them, covered by
the same deferred-drift/resync ruling) → per candidate
`resolveMapPrincipals(userId)` (refreshes stale affiliations, exactly as the
live `getMapAccess` path does), then the refresh-shortfall guard (any
still-stale candidate → `ProjectionUnavailableError`, never a shrunken set) →
`resolveMatchedMapRoles` → drop empty → sorted claim set →
`fetchWithTimeout` POST to
`deriveConvexSiteUrl(NEXT_PUBLIC_CONVEX_URL)/project-map-access` with
`Bearer CONVEX_SERVICE_SECRET` → HTTP action validates body → one atomic
`reconcileMapClaims` mutation converges storage → Convex reactivity re-runs
every live subscription whose read set contained a changed/deleted claim row →
the gate re-throws `FORBIDDEN` for evicted users. Purge flow: orchestrator →
contributor captures affected map ids → durable deletes → best-effort door
calls (teardown/re-project/purge-by-user); failures are swallowed and heal on
the next projection or resync. No Convex→Neon flow exists anywhere.

### Edge and failure behavior

- Corp grant matching a user with stale cached affiliations → the candidate
  enumeration includes them; `resolveMapPrincipals` refreshes first, so
  membership truth is as fresh as the live access path; a user who genuinely
  left resolves to no roles and gets no claim (and an existing claim is deleted
  by the reconcile).
- ESI unreachable during compute (refresh attempt leaves any candidate's
  affiliations stale) → `computeMapAccessClaims` throws
  `ProjectionUnavailableError` rather than emitting a shrunken set that would
  durably and wrongly revoke corp-derived claims; purge callers swallow it
  (best-effort), grant-change and resync callers surface it and retry later.
  The live gate path degrades transiently per-request; the projection must
  never convert that transient into a durable eviction. Proven by a
  mocked-stale-after-refresh test.
- Candidate user with no matching principals after refresh (character
  transferred away, corp left) → empty role set → omitted from claims →
  reconcile deletes any stale row. Owning layer: compute (omission) +
  reconcile (deletion).
- Map deleted or id unknown → `computeMapAccessClaims` returns `[]` →
  projection call becomes a teardown. No error: deletion and never-existed are
  the same desired state.
- Duplicate `(mapId, userId)` rows encountered (the as-built landmine that
  would brick `.unique()` in the gate) → reconcile keeps/creates exactly one
  row and deletes every duplicate, restoring gate liveness. Proven by a
  seeded-duplicate test.
- Re-projection with an unchanged set → every row compares equal (ordered
  roles) → zero writes (`unchanged` counts only), so watched subscriptions are
  not needlessly re-run. Proven by asserting reconcile counts and document
  equality including `_creationTime`.
- Concurrent reconciles for one map (two racing grant changes) → each mutation
  is atomic and serializable, so storage always equals ONE complete stated set,
  never a torn merge; a stale-snapshot winner is possible and self-heals on the
  next projection or resync. Documented, accepted (admin-gated, single
  operator; declarative contract makes the heal trivial).
- `NEXT_PUBLIC_CONVEX_URL`/`CONVEX_SERVICE_SECRET` unset, door unreachable, or
  non-2xx → `projectMapAccess` throws `ProjectionUnavailableError`; purge
  contributor wraps every door call in try/catch and completes the Neon purge
  regardless (orchestrator awaits contributors with no try/catch — a throw
  would abort the purge mid-tier).
- Malformed or wrong-typed door body → clean 400 before any mutation runs;
  missing/wrong bearer → 401 (`/purge-online` precedent, including the
  zod-before-mutation rationale).
- Revoked user's later direct call (Door-2 attempt without a page) → gate's
  claim read finds nothing → `FORBIDDEN`; signed-out caller stays
  `UNAUTHENTICATED`. The two codes remain distinguishable — 4.0.2.3's no-access
  UI depends on it, and the probe asserts the exact code.
- User purge where the user both owns maps and holds claims on others' maps →
  owned maps' claims torn down per map (`claims: []`), the user's own claims
  removed via `/purge-map-access`; character purge re-projects each affected
  map (captured before the delete — both direct character-grant maps AND maps
  with a corporation grant matching the character's cached
  `characters.corporationId`, because the departing character may have been the
  user's only pilot in that corp and the claim must fall). This is correct only
  because `authPurgeContributor` runs BEFORE `mapsPurgeContributor` in
  `src/composition/purge/register-all.ts` (the account link is already deleted
  when re-projection computes) and because the auth purge preserves the
  `characters` profile row (it only resets preferences), keeping the cached
  corp id readable. That registration order is load-bearing; do not reorder.
- Deleted map whose teardown POST failed (purge-time Convex outage) → the
  claims for that map have NO automatic healer: no grant change can ever occur
  on a deleted map and nothing schedules a resync, so previously-authorized
  holders keep live chain access until a manual per-map resync or user-level
  purge runs. The contributor logs every map id whose door call failed
  (console.error) so the operator knows exactly what to resync; the residual is
  accepted (admin-gated, single user, holders had legitimate access) and
  recorded in the scratchpad entry.
- Projection racing a concurrent user purge (compute reads Neon before the
  purge deletes account rows; its POST lands after `/purge-map-access`
  finished) → the reconcile can re-insert the purged user's claims. Accepted
  window: the compute span is small, the state is fully correctable, and
  re-running the user purge door call or a per-map resync removes the remnant;
  no ordering machinery is added for it in an admin-gated single-user app.

### Ordered work

1. **Convex reconcile mutation.** Create `convex/mapAccessProjection.ts` with
   `reconcileMapClaims`. First normalize the desired input: last-entry-wins
   dedupe by `userId`, then canonicalize each roles array to unique values in
   `MAP_ROLE_PRECEDENCE` order (a repeated `userId` or unordered roles from any
   caller must not be able to break the invariant — the drafted per-entry
   insert would otherwise create duplicates because the first insert does not
   update the existing-rows lookup). Then read the map's existing claims with
   one `by_map` indexed scan into a `userId → rows[]` map; for each normalized
   desired claim: missing → insert; present-once with different canonical
   roles → replace; present-once identical → skip; present-multiple → keep
   first, delete rest, then apply the compare. Delete every existing row whose
   user is not in the desired set. Why this shape: the full-state converge is
   what makes teardown/resync/grant-change one idempotent operation (PD-2) and
   what guarantees the `.unique()` invariant the gate depends on. Prove with
   convex-test cases: fresh write, identical re-run (all `unchanged`,
   `_creationTime` stable), role change, user removal, empty-set teardown,
   seeded-duplicate repair, a desired payload repeating one `userId` (converges
   to one row, last entry wins), and unordered/duplicated roles input stored
   canonical and comparing equal.
2. **Convex user purge mutation.** Add `purgeUserClaims` batching deletes via
