## Why now

The version's signature inference engine cannot constrain a system's unknown
connections without knowing which wormholes that system always spawns, and CCP
publishes that fact nowhere — it is the version's one genuine external data gap.
Every other groundwork slice is first-party data we already mirror, so this is
also the only slice needing a refresh feed, a review gate, and a degradation
path. Landing it now, well ahead of its 4.0.4.3 consumer, means that consumer
starts against a populated, cross-checked table.

## Scope (the destination)

When this session is finished, Neon holds a promoted copy of per-system
wormhole statics — roughly 3,772 `(system_id, code)` rows covering 2,604
systems — and a cached server read path answers statics for any system id from
that copy alone. A weekly Vercel cron joins the existing shell and asks anoik.is
one conditional question: has this changed since the stored ETag? The
overwhelmingly normal answer is `304`, which costs zero body bytes, takes no
advisory lock, writes no rows, and ends the run. The same work path is available
on demand through an operator-triggered admin action, satisfying the contract's
scheduled-and-on-demand requirement without a second owner.

When the answer is `200`, the run validates the payload at the boundary,
normalizes it, cross-checks it against the committed Pathfinder lineage fixture
through the shipped wormhole codex, computes a full difference against the
promoted copy, and stores all of it as one **pending** snapshot, superseding any
earlier pending row. It promotes nothing. An admin-gated screen presents that
pending snapshot and an explicit operator action promotes or rejects it.
Contract §§3–6 are satisfied without widening: the pull, snapshot, promote gate,
cross-check, serving path, attribution, registry declaration and source-map flip
all land; no consumer of the data is built, no observation scoring exists, and
no map or mapper file is touched.

## Resolved implementation decisions

- **Contract PD-1 — Snapshot and promote mechanics: a holding-pen table with a
  surrogate key and an operator-only promote path.** `wh_statics_snapshots`
  carries `id` as a `bigserial` primary key — the API addresses a snapshot by
  that id — plus the payload `version`, the ETag and `Last-Modified` that
  produced it, a SHA-256 of the normalized entries, the system count, a `status`
  of `pending` / `promoted` / `rejected` / `superseded`, the normalized entries
  as `jsonb`, and the computed difference and cross-check as `jsonb`. Neither
  table carries a user or character column, so neither needs a purge
  contributor; the surrogate key is an addressing concern, not an identity one.
  `wh_system_statics` is the promoted served copy keyed `(system_id, code)`.
  **Every successful snapshot insert marks any other `pending` row
  `superseded` in the same transaction**, so at most one snapshot is ever
  pending and the review screen has an unambiguous target. Promotion is a single
  transaction: replace `wh_system_statics` from the snapshot's entries and mark
  that snapshot `promoted`; `revalidateTag` runs after the commit. Storing
  entries on the snapshot row keeps the difference a pure in-memory computation
  over ~3,772 pairs. **Rejected:** promoting by mutating one table in place with
  no holding pen — it makes "what would change if I accepted this?"
  unanswerable before the fact, which is the entire point of the gate.

- **Contract PD-2 — The review threshold: there is none; every difference stops
  and asks.** Measured drift is exactly zero — a January 2024 lineage snapshot
  and a January 2025 feed agree on all 2,604 systems — so a difference is far
  more likely to be upstream breakage than a real game change. No refresh path
  promotes. It writes a `pending` snapshot and stops; only the admin action
  promotes. A snapshot whose digest equals the promoted copy's is recorded with
  a zero difference and needs no operator attention, so ETag churn on an
  unchanged re-upload creates no review work. **Divergence:** Contract `AC-2`
  expects an ordinary difference to promote cleanly under a threshold. Operator
  direction in this planning session replaced the threshold with
  review-everything. Authority: operator direction, 2026-07-28. This is strictly
  stricter than `HC-2` and cannot violate it. **Rejected:** a percentage
  threshold blocking above ~0.5% of systems changed — it was the drafted answer,
  and the operator judged that at this change frequency any difference is worth
  a look.

- **Contract PD-3 — Cadence and shell placement: `0 6 * * 1` weekly as an eighth
  `defineCronRoute` declaration, with an operator-triggered on-demand action.**
  Weekly matches a dataset that has not moved in over a year, and 06:00 UTC
  Monday clears both the 09:00 GSC job and the 11:00–11:50 daily cluster. The
  declaration is `wakeClass: 'batch'` — `src/app/api/cron/registry.test.ts`
  treats a fixed minute and hour as not sub-daily, so the `idle-silent` rule does
  not apply — with lock key `8273619018`, the next free key after `…013`–`…017`,
  and `record: { policy: 'always', justification: 'weekly batch preserves every
  unchanged, feed-unavailable and snapshot-pending outcome for operator
  review' }`, which the declaration type requires whenever the policy is
  `always`. The conditional GET runs in `preLock`, exactly as `refresh-sde`
  probes its manifest, so the unchanged path never reserves a connection.
  Contract `DC-1` also requires the pull be available on demand; that is the
  admin route's `refresh` action, which runs the same work under the same
  advisory lock rather than duplicating it. Vercel permits 100 crons per project
  on all plans, so 7 → 8 is unconstrained. **Rejected:** daily — it multiplies
  requests to a small community publisher sevenfold for a dataset with a
  measured annual change count of zero, against `HC-4`. **Rejected:** a separate
  on-demand route — it would create a second entry point into one work path.

- **Contract PD-4 — Cross-check disagreements: computed at snapshot time against
  a committed lineage fixture, stored on the snapshot, and surfaced on the review
  screen.** `export/csv/system_static.csv` is committed under
  `src/data/wh-statics/__fixtures__/` with its MIT provenance in a header
  comment. The repository was last pushed 2024-01-06 and is effectively frozen,
  and `DEP-3` designates it a bootstrap and cross-check rather than a runtime
  source — so fetching it at runtime would buy nothing and would cost a second
  vendor entry, a second timeout, and a network dependency inside the check whose
  whole purpose is independence. Disagreements are never auto-resolved: they are
  stored on the snapshot and rendered, and the operator decides. A code the codex
  cannot resolve to a `typeId` is a hard parse failure, not a disagreement.
  **Rejected:** fetching the CSV from `raw.githubusercontent.com` per run — a
  runtime vendor for a file unchanged in two years.

- **Contract PD-5 — Cache time and placement: a `global-cron` dataset in Neon,
  in a new `src/data/wh-statics/` slice, read through `'use cache'` with
  `cacheLife('max')` and tag invalidation.** The registry declaration Contract
  `DC-6` requires is an `ESI_DATASET_ENTRIES` entry in
  `src/lib/esi-datasets/entries.ts` — the gate in `registry.test.ts` rejects an
  unregistered mirror table. It is `store: 'neon'`, `shape: 'global-cron'`,
  `freshnessModel: 'cron-cadence'` (the schedule owns freshness, so no static
  TTL applies), `refreshOwner: { kind: 'cron', route:
  '/api/cron/refresh-wh-statics' }`, and `mirrorTables: ['wh_statics_snapshots',
  'wh_system_statics']`. `EsiUpstream` is a closed union, so it gains an
  `{ kind: 'anoik-statics' }` member; the type's own contract already exempts
  non-ESI upstreams from cache-time rules but not placement rules. Placement is a
  new slice rather than `src/data/eve-data/` because `eve-data` is the
  first-party CCP mirror with no parked-versus-live concept, while this is
  community-sourced data whose whole lifecycle is holding-pen-and-approval; the
  slice imports `eve-data` for the codex under the shared reference-core
  exemption `docs/architecture-boundaries.md` already grants, and the `data`
  Fallow zone auto-discovers it. `source.ts` carries `import 'server-only'`
  matching `src/data/gsc/source.ts`, which means adding it to `SERVER_ROOTS` and
  `EXPECTED_MARKERS` in `src/lib/server-only-boundary.test.ts`, adding
  `@/data/wh-statics/source` to the client lint patterns in `eslint.config.mjs`,
  and updating the "exactly four modules" inventory in
  `docs/architecture-boundaries.md` to five. `getSystemStatics` returns
  `PromotedStatics` = `{ version: string; systems: { systemId: number; codes:
  readonly string[] }[] }`, system-id sorted with codes sorted — codes only, since
  `typeId` is resolvable from the codex and storing it would create a second
  owner of that mapping. **Rejected:** folding the tables into `eve-data` — it
  mixes "CCP said so" with "the community worked it out" in one owner and widens
  the repository's broadest data slice.

### Interfaces and contracts

- `fetchStaticsFeed(knownEtag: string | null): Promise<StaticsFeedResult>` in
  `source.ts`. One GET with `If-None-Match` when `knownEtag` is non-null, the
  shared `OUTBOUND_USER_AGENT`, and `WH_STATICS_FETCH_TIMEOUT_MS`. Returns
  `{ status: 'unchanged' }` on `304`, `{ status: 'changed', body, etag,
  lastModified }` on `200`, and `{ status: 'unavailable', reason }` on any other
  status or a thrown network or timeout error. It never throws to its caller.
  ```ts
  /**
   * Asks anoik.is whether the statics feed changed since `knownEtag`, returning the
   * new body only when it did. An unreachable or erroring feed resolves to
   * `unavailable` rather than throwing, because a failed refresh must never affect
   * the promoted copy that serving reads.
   */
  ```
- `parseStaticsPayload(body: string): ParsedStaticsFeed` in `parse.ts`.
  Zod-validates the payload's `version`, `systems` and `wormholes` maps at the
  boundary and returns `{ feedVersion, entries }`, `entries` being a
  `systemId`-then-`code` sorted array of `{ systemId, systemName, code }`. Throws
  a named error when a system lists a code absent from the `wormholes` map.
  Ignores `wormholes[code].static`, `cels`, `effects` and `effectName`.
- `diffStatics(promoted, incoming): StaticsDiff` in `diff.ts`. Pure. Returns
  `{ systemsAdded, systemsRemoved, systemsChanged, codesAdded, codesRemoved,
  totalDifferences }`, `systemsChanged` carrying before and after code sets.
  `totalDifferences === 0` is the nothing-to-review signal.
- `crossCheckStatics(entries, lineageRows, codex): StaticsCrossCheck` in
  `cross-check.ts`. Pure. Resolves each entry's code to a `typeId` through the
  codex and compares per-system type sets against the lineage. Returns
  `{ agreedSystems, disagreements, lineageOnlySystems, feedOnlySystems }`. Throws
  when a code has no codex entry.
- `recordSnapshot(db, input): Promise<{ snapshotId: number }>` in `queries.ts`.
  One transaction: mark every existing `pending` row `superseded`, then insert
  the new `pending` snapshot. Returns its `bigserial` id.
- `promoteSnapshot(db, snapshotId): Promise<PromoteResult>` and
  `rejectSnapshot(db, snapshotId)`. Promote runs one transaction that replaces
  `wh_system_statics` from the snapshot's entries and marks it `promoted`, then
  calls `revalidateTag(WH_STATICS_TAG, 'max')` after the commit. Both reject a
  snapshot that is not `pending`.
- `pruneWhStaticsSnapshots(db, retentionDays): Promise<number>` in `queries.ts`.
  Deletes `promoted`, `rejected` and `superseded` rows older than the retention
  window while always preserving any `pending` row and the currently promoted
  snapshot. Called from `refresh-gsc`'s existing housekeeping batch and named as
  the growth registry's `prunedBy` owner.
- `getSystemStatics(): Promise<PromotedStatics>` in `queries.ts`. `'use cache'`,
  `cacheLife('max')`, `cacheTag(WH_STATICS_TAG)`, wrapped in
  `withColdStartRetry`. Reads `wh_system_statics` only and returns
  `{ version: string; systems: { systemId: number; codes: readonly string[] }[] }`
  sorted by system id with codes sorted. Returns an empty `systems` array before
  the first promote.
- `POST /api/admin/wh-statics` — a form POST from the review screen, following
  the live `admin/role` and `esi-jobs/retry` pattern: fields `action`
  (`promote` | `reject` | `refresh`) and `snapshotId` (required for `promote`
  and `reject`, absent for `refresh`), validated with `parseFormBody` against
  the slice `api-contract.ts` form schema, answering with a `303` redirect back

  the handler calls `checkAdmin` and `requireSameOrigin` before any work. The
  `refresh` action runs the same pull-and-snapshot path as the cron under lock
  `8273619018` and is the contract's on-demand pull.
- `refreshWhStaticsDeclaration: CronRouteDeclaration<CronRefreshWhStaticsResponse,
  WhStaticsPreLock>` — the eighth declaration, registered in `cronRegistry`.

### Control and data flow

Weekly, Vercel calls `GET /api/cron/refresh-wh-statics`. `defineCronRoute` runs
bearer auth, the correlation scope, then `preLock`. `preLock` reads the newest
snapshot's ETag from Neon and calls `fetchStaticsFeed`. On `unchanged` it
short-circuits with outcome `unchanged`, `workDone: false` — no lock is
reserved and no row is written. On `unavailable` it short-circuits with outcome
`feed-unavailable`, `workDone: false`; the promoted copy is untouched and serving
is unaffected. Only a `changed` result proceeds, at which point the shell
reserves lock `8273619018` and calls `work`.

`work` validates the body, reads the current promoted copy and the wormhole
codex, parses the committed lineage fixture, computes the difference and the
cross-check, and calls `recordSnapshot`, which supersedes any prior pending row
and inserts one `pending` snapshot carrying entries, difference, cross-check,
feed version, ETag and digest. It promotes nothing and invalidates no cache. The
outcome is `snapshot-pending` with the difference counts in telemetry.

The admin route's `refresh` action drives that identical path behind
`checkAdmin`, so the on-demand pull cannot diverge from the scheduled one.
Separately, and only on operator action, `promote` or `reject` runs
`promoteSnapshot` or `rejectSnapshot`. `promoteSnapshot` replaces the promoted
copy inside one transaction and then invalidates `WH_STATICS_TAG`, after which
`getSystemStatics` serves the new copy. No other path writes
`wh_system_statics`.

### Edge and failure behavior

- Feed returns `304` → outcome `unchanged`, zero body bytes, no lock, no write.
  This is the expected weekly result.
- Feed unreachable, times out, or returns any other non-200 status → outcome
  `feed-unavailable`, recorded durably; the promoted copy and every read path are
  untouched. This is the `HC-1` degradation demonstration.
- Feed returns `200` with bytes identical to the promoted copy (Apache ETag churn
  on an unchanged re-upload) → a `pending` snapshot with `totalDifferences: 0`,
  which the review screen shows as requiring no action.
- A second change arrives before the operator reviews the first → the earlier
  `pending` row becomes `superseded` inside the insert transaction, so exactly
  one snapshot is ever pending.
- A system lists a code absent from the payload's `wormholes` map, or a code
  cannot be resolved to a `typeId` by the codex → the run fails loudly with a
  named error and writes no snapshot. Silent dropping is forbidden.
- The cross-check finds a disagreement → the snapshot is still stored `pending`
  with the disagreement recorded and rendered. It is never auto-resolved and
  never blocks storing the snapshot.
- A cron run and an on-demand refresh overlap → the advisory lock short-circuits
  the second to the declared busy body.
- An operator promotes or rejects a snapshot that is no longer `pending` → the
  action is refused with a typed failure; the promoted copy is unchanged.
- `wh_system_statics` empty before the first promote → `getSystemStatics` returns
  an empty `systems` array rather than throwing.
