## Why now

Phase 1 is "everything the map reads before the map exists." The universe data
shipped to Neon in 3.7.2.2 but has no client-consumable form, the wormhole
codex exists nowhere, and D15 has no first instance — so the mapper
sub-versions (4.0.2.3 node labels, 4.0.4.1 type auto-fill, 4.0.4.2 jump
classification, 4.0.4.3 sig inference and widget hosting) would each block on
this reference layer. Shipping all three here, through one shared pipeline and
convention set, is exactly the merged topology the contract records.

## Scope (the destination)

Three versioned client assets exist, all derived at read time from the shipped
Neon SDE mirror and cached until the SDE refresh cron busts
`BLUEPRINT_STRUCTURE_TAG`:

- a **system directory** mapping every persistent solar system id to
  `{name, whClassId, security}`;
- a **stargate adjacency graph** as sorted `[systemId, neighbours[]]` entries
  (systems without gates — all of J-space — are simply absent);
- a **wormhole codex** resolving each group-988 type code to
  `{totalMass, maxJumpMass, massRegen, lifetimeMinutes, sizeClass,
  targetClass}`, with K162 present as the explicit far-side entry.

Each asset is served by a version-addressed public route
(`/api/universe/assets/[version]/…`) carrying
`Cache-Control: public, max-age=31536000, immutable`; a tiny uncached manifest
route (`/api/universe/assets`) hands out the current version
(`eve_data_meta.sde_version`, the CCP build number). Typed client loaders
memoize one manifest-plus-assets fetch per session and expose
name/class/security/neighbour and codex lookups. The sites card gains an
embeddable widget at the feature's new single public-surface module,
`src/features/wormhole-sites/widget.tsx`, rendering from a site identifier
inside whatever box its host provides; `/preview/widgets` is its isolation
surface and first consumer. Contract §§3–6 are satisfied without widening: no
watch-listed module changes, no SDE re-ingest, no mapper code, no card
redesign, no convention retrofit.

## Resolved implementation decisions

- **Contract PD-1 — Asset format, versioning, and load strategy: fetched
  JSON from version-addressed routes backed by `'use cache'` queries.**
  Version = `eve_data_meta.sde_version` (CCP build number, live value
  `3444265`), already maintained by the daily refresh cron. Queries use
  `cacheLife('max')` + `cacheTag(BLUEPRINT_STRUCTURE_TAG)` — the exact shipped
  `getSystemSearchIndex` pattern — so an SDE refresh is reflected without a
  deploy, and each cached payload carries the version it was built from.
  Exact serving mechanics (settled here, not left to the executor): a
  versioned asset route 404s when the **cached payload's own** `version`
  differs from the path parameter — never by comparing against a separate
  live meta read, so a refresh-window race can only produce a clean 404, not
  stale rows under a new URL. Matching responses are stamped
  `Cache-Control: public, max-age=31536000, immutable` through one
  transport-owned `withCacheControl` helper (header mutation on the
  `apiResponse` `Response` is verified to work in this runtime). The manifest
  route reads the same tag-cached `getCachedSdeVersion` (keeping manifest and
  assets coherent on the same tag), calls `connection()` first so it is
  honestly dynamic, and is stamped `Cache-Control: no-store` so every session
  asks the origin. The three `[version]` routes are dynamic by handler shape;
  all four are registered as `dynamic` with `_reasons` lines. **Rejected:**
  bundling the assets (ships ~500 KB to every page and pins the data to a
  deploy); build-time emission to `public/` (goes stale against the daily
  drift cron between deploys and couples the build to Neon; the `universe.ts`
  comment sketching that emitter predates the cron-refresh reality and is a
  suggestion, not a constraint); an uncached manifest meta read (would let
  the manifest advertise a new build before the tag bust lands, widening the
  exact incoherence window the payload-version gate closes); prerendering the
  manifest `static` like `/api/industry/systems` (would freeze version
  discovery until the next deploy, defeating `no-store`).
- **Contract PD-2 — Codex generation extends the universe asset path.** Same
  api-contract module, same route family, same version stamp, same cache tag,
  same loader idiom; its own pure builder and query because its sources
  (`eve_types` group 988 + `type_dogma` + `dgm_attribute_types`) are disjoint
  from the universe tables. Separability judgement: each asset has its own
  query, endpoint, and route; the shared parts are conventions and one version
  read, so removing or changing any one asset never forks the others.
  **Rejected:** a parallel standalone codex pipeline — it would duplicate the
  version/serving/loader conventions the contract explicitly says to reuse.
- **Contract PD-3 — Feature public-surface convention: a dedicated widget
  module, not a general public barrel.** A feature that exports an embeddable
  widget owns exactly one module, `src/features/<name>/widget.tsx`, exporting
  the widget component and its props type; hosts import only that module.
  Everything else keeps today's deep-path imports. Recorded in
  `docs/architecture-boundaries.md`; mechanical host-side enforcement arrives
  with the mapper zone (D14) in 4.0.2.x. This answers D15 for every later
  widget without touching any existing import — so the contract's split
  trigger (repository-wide import changes) does not fire. **Rejected:** a full
  `public.ts` barrel per feature — it forces a repository-wide import
  migration (the recorded split trigger, and OOS-6), and barrels invite
  re-export sprawl that Fallow's dead-export gate then fights.
- **Contract PD-4 — Widget props contract: entity id in, container-filling
  render out.** `SiteCardWidget({ siteId, className? })`: a client component
  that loads its own data (apiFetch of the existing `siteDetailEndpoint`),
  owns its loading skeleton and error state, and fills the host's box
  (`h-full` + internal `overflow-y-auto` scroll region). The window
  communicates its size constraint purely through the container box it gives
  the widget — no width/height props, no resize protocol. That is the D15
  template: later widgets swap only the id name and endpoint. **Rejected:**
  explicit pixel props or a host-side data-injection contract — both leak
  host knowledge into features (against HC-3's direction) and make every
  future window/widget pair renegotiate sizing.
- **Contract PD-5 — Authoritative wormhole attribute identifiers (live, from
  the ingested schema mirror, this session):** 1381
  `wormholeTargetSystemClass`, 1382 `wormholeMaxStableTime` (minutes; B274 =
  1440), 1383 `wormholeMaxStableMass` (total mass, kg), 1384
  `wormholeMassRegeneration`, 1385 `wormholeMaxJumpMass`. Generation resolves
  them **by name** with a throwing assertion, so these numbers never appear as
  literals in production code. Size class is a **total function** over
  `maxJumpMass` with ordered inclusive thresholds — `≤ 5e6 → 'S'`,
  `≤ 6.2e7 → 'M'`, `≤ 4.1e8 → 'L'`, `> 4.1e8 → 'XL'` — covering every live
  value (5e6 / 6.2e7 / 3.75e8 / 4.1e8 / 1e9 / 2e9) with no gap or ambiguity;
  destination class shares the `wormholeClassId` value vocabulary already
  documented in `docs/DATA_SOURCES.md`. **Rejected:**
  hard-coding the ids — planning itself caught the master plan's recalled ids
  being wrong, which is the exact failure HC-1 exists to prevent.

- `SystemDirectoryEntry` — `{ id: number; name: string; whClassId: number |

  identity: name, coarse wormhole/space class, and raw security status. */`
- `AdjacencyEntry` — `[systemId: number, neighbours: number[]]`, both sorted
  ascending; only systems with at least one stargate appear.
- `WormholeCodexEntry` — `{ code: string; typeId: number }` intersected with
  `{ farSide: true } | { farSide: false; totalMass: number; maxJumpMass:
  number; massRegen: number; lifetimeMinutes: number; sizeClass:
  'S'|'M'|'L'|'XL'; targetClass: number }`. `code` is the name suffix
  (`/^[A-Z]\d{3}$/`, e.g. `B274`, `K162`); `sizeClass` comes from the total
  threshold function under PD-5.
- `withCacheControl(response: Response, value: string): Response` (in
  `src/transport/api-response.ts`) — `/** Stamps one Cache-Control value on an
  apiResponse-built response; the universe manifest and asset routes are its
  consumers. */`
- `derivedClientAssets` (optional on the registry entry type in
  `src/lib/esi-datasets/types.ts`) — `readonly { name: string; route: string;
  placement: 'versioned-immutable-route'; refresh: 'sde-refresh-cron-tag-bust'
  }[]`; the literal placement/refresh vocabulary makes HC-5's declaration
  mechanical. The `sde` entry declares `universe-system-directory`,
  `universe-adjacency-graph`, and `wormhole-codex` with their route paths, and
  the census test asserts all four fields per declared asset.
- `getSystemDirectory() / getAdjacencyGraph() / getWormholeCodex()` —
  `'use cache'` + `cacheLife('max')` + `cacheTag(BLUEPRINT_STRUCTURE_TAG)`;
  each returns `{ version, … }` with version and rows read in the same cached
  fill (so a tag bust refreshes them together). Each wraps an exported
  uncached core (`readSystemDirectory(db)` etc.) that the spot-check script
  reuses with its own connection — the `meta.ts` cached/uncached split.
- Endpoints (in `src/data/eve-data/api-contract.ts`): manifest
  `GET /api/universe/assets` → `{ version: string }` (503 problem when no SDE
  is ingested); assets `GET /api/universe/assets/[version]/systems |
  adjacency | wormholes` → `{ version, systems | adjacency | types }`, 404
  problem when the cached payload's `version` differs from the path parameter
  (the payload-version gate from PD-1). The manifest handler calls
  `connection()` before its version read and is stamped `no-store`; matching
  asset responses are stamped immutable via `withCacheControl`. Routes carry
  `// authz: public` and `// input: none` / `// input: path`; clients use
  `apiFetch` only.
- Loaders (`universe-assets-client.ts`):
  `loadUniverseAssets(): Promise<UniverseAssets>` where `UniverseAssets`
  exposes `version`, `systemInfo(id)` → entry or null, and `neighbours(id)` →
  `readonly number[]` (empty for gateless systems);
  `loadWormholeCodex(): Promise<WormholeCodex>` with `byCode(code)` → entry or
  null. Both memoize a module-level promise, clear it on failure
  (`systems-search.ts` idiom), and on a 404 versioned fetch refetch the
  manifest once before failing.
- `SiteCardWidget({ siteId, className }: { siteId: number; className?:
  string })` — `/** The sites card as a D15 embeddable widget: loads one site
  by id through the feature's own endpoint and fills whatever container the
  host provides (internal scroll; loading skeleton; inline error state). The
  host owns the box; the widget owns everything inside it. */`

### Control and data flow

Map session (later versions): `loadUniverseAssets()` → uncached manifest GET →
two immutable versioned GETs → route handlers → cached queries → Neon mirror
tables → memoized lookup maps. Refresh path: daily cron detects a new CCP
build → re-ingest → `BLUEPRINT_STRUCTURE_TAG` bust → next manifest read hands
out the new version; old immutable URLs 404 at origin but are never re-asked
by sessions that already loaded them. Widget: mount → `apiFetch` of
`siteDetailEndpoint` → existing route → existing `getPricedSiteDetail` →
`SiteCard` render inside the container frame. No write path changes anywhere.

### Edge and failure behavior

- No `sde_version` row (fresh local DB) → manifest returns a 503 problem;
  loaders reject with that failure; nothing caches.
- Version raced past by a refresh between manifest and asset fetch → the
  payload-version gate returns 404 (never stale rows under a new URL) →
  loader refetches the manifest once (it is `no-store`, so now current) and
  retries; a second failure rejects and clears the memo for a later retry.
- Group-988 type other than K162 lacking a dogma row or a required attribute,
  or an attribute name missing from `dgm_attribute_types`, or a type name not
  matching `Wormhole [A-Z]\d{3}` → generation throws (loud schema-drift
  alarm, the `requireName`/`resolveIndustryServiceIds` precedent).
- Gateless system (all J-space) → absent from the adjacency asset;
  `neighbours()` returns `[]`, never throws.
- Widget: unknown site id → endpoint 404 → inline error state, no crash;
  unmounted or re-pointed mid-fetch → stale response discarded by an id guard.
