## Delivered outcome

Per-system wormhole statics now refresh weekly or on demand into an
operator-reviewed Neon snapshot, promote transactionally into a versioned
serving copy, and remain available from that copy when anoik.is is unreachable.

## Divergences from plan

- Step 1 named the shared `REPLACE_ALL` boundary, but
  `wh_system_statics` uses the custom `WH_STATICS_PROMOTE_BATCH`
  transactional-batch boundary because PD-1 requires delete, insert, and
  snapshot-state promotion to commit atomically. Authority: operator direction.
- The lineage cross-check maps each unique Pathfinder `typeId` through the
  codex and compares per-system code sets; it does not assume one type id per
  code because J244, F216, and C729 each legitimately map from multiple type
  ids. Authority: operator direction.
- The committed Pathfinder fixture has 3,772 data rows, not the plan's 3,771;
  the latter omitted one data row during pre-plan counting. Authority: operator
  direction.
- Unshipped migration 0052 was regenerated with
  `wh_system_statics.feed_version`, populated during promotion, so
  `getSystemStatics` can return the promoted version while reading only the
  serving table. Authority: operator direction.
- The live feed carries `static: null` for six definitions. The parser accepts
  that shape and continues to ignore the non-authoritative flag, matching the
  plan's validity rule. Authority: discovered evidence.
- The spot-check CLI calls the serving-table reader directly because Next cache
  APIs require a request or static-generation context; the production admin
  page is the real cached `getSystemStatics` consumer. Authority: discovered
  evidence.

## Successor notes

- The codex bridge is uniquely keyed by `typeId`; duplicate type ids that map
  to one code are deliberate and collapse only after translation to code sets.
- A changed feed always becomes pending, even at zero difference; no refresh
  path calls promotion.
- Snapshot recording serializes writers and reuses the latest row when both its
  ETag and normalized assignment digest match, so overlapping observations do
  not supersede one another.
- The pre-lock probe retains the newest snapshot id alongside the conditional
  ETag, and the locked write compares and swaps on it. A response that was in
  flight while another refresh recorded a newer snapshot returns
  `stale-observation` instead of superseding it, so the pending review and the
  next conditional probe never regress to an older revision.
- The review surface lists the complete code set for every added and removed
  system, not only its id, because promotion authorizes assignments rather than
  system membership.
- Empty snapshots remain reviewable but cannot replace the promoted serving
  copy.
- Rejected snapshots are excluded from conditional-probe and identical-observation
  reuse, so a later scheduled or on-demand refresh can make the same upstream
  revision pending again.
- The cron shell holds the advisory lock on its reserved session while the
  transactional snapshot write uses the shared direct postgres-js pool.
- The feed's `static` field is neither a validity nor promotion signal and may
  be `false` or `null`.
