## Session 4.0.4.3.2 — Signature inference and provenance

**Sub-version:** 4.0.4.3
**Master plan:** `docs/VERSION_4_0_PLAN.md` §4.0.4.3
**UX gate:** No
**Execution profile:** Frontier autonomous coding agent
**Delivery unit:** One agent session, one shared sub-version branch, one PR per session
**Roadmap coverage:** §4.0.4.3 pure constraint solver, contradiction behavior, three-tier provenance and honest degraded mode
**Internal phases:** 1. Model signatures as unknowns and statics as constraints; 2. Propagate typed, jumped and eliminated facts with provenance; 3. Prove contradiction and unavailable-statics behavior
**Split triggers:** Correct inference requires assuming a complete scan or fabricating an unavailable static

## 1. Objective

Prove the flagship signature reasoning as a pure, reviewable system before
ranking, observation emission or visual integration can obscure its honesty.

## 2. Current context and dependencies

- **DEP-1:** Session 4.0.4.3.1 shipped parsed signature lifecycle and stub nodes.
- **DEP-2:** The statics dataset is available but inference must degrade honestly if it is unavailable.
- **DEP-3:** Provenance is the honesty mechanism because scan completeness cannot be proven.

## 3. Done conditions

- **DC-1:** Every wormhole signature is an unknown and every known system static is a constraint that must be satisfied.
- **DC-2:** Single-static, two-static elimination and history-narrowing cases resolve where evidence permits.
- **DC-3:** Inferred, user-confirmed and jump-verified values carry ordered provenance; contradictions yield and inference never overrides a person.
- **DC-4:** With statics unavailable, inference is off while signature lifecycle remains usable.

## 4. In scope

- **IS-1:** The pure constraint solver and propagation rules.
- **IS-2:** Provenance ordering, contradiction state and degraded behavior.

## 5. Out of scope

- **OOS-1:** Pick-list ranking, observation emission, sites-widget hosting and final presentation, owned by 4.0.4.3.3.
- **OOS-2:** Changes to parsing, lifecycle or collapse behavior.

## 6. Hard constraints

- **HC-1:** Inference never assumes scan completeness.
- **HC-2:** Jump-verified outranks user-confirmed, which outranks inferred.
- **HC-3:** Inference never silently overrides a person or fabricates a static.

## 7. Decisions the session plan must resolve

- **PD-1:** The solver's plain-language constraint model.
- **PD-2:** Contradiction detection and yielding semantics.
- **PD-3:** The boundary between pure provenance results and later presentation.

## 8. Acceptance criteria

- **AC-1:** Single-static and two-static fixtures produce the expected deductions — proving DC-1 and DC-2.
- **AC-2:** Confirmed history narrows later possibilities — proving DC-2.
- **AC-3:** Every provenance ordering and contradiction case yields the required result without overriding a person — proving DC-3.
- **AC-4:** Removing statics disables inference without breaking lifecycle — proving DC-4 and HC-3.

## 9. Verification

- **V-1:** Inference matrix for self-label, elimination and history.
- **V-2:** Provenance/contradiction and degraded-mode coverage.
- **V-3:** The repository's standing definition-of-done gate.

## 10. UX/operator gates

- **G-1:** The operator reviews the solver model in plain language before this session's pull request opens.

## 11. Baseline/hotspot boundary

Expected baseline effect is Neutral. The solver is a likely complexity hotspot;
planning must keep it pure, behaviorally covered and below universal caps.

## 12. Close-out behavior

This is the second of three sessions in sub-version 4.0.4.3 and ships through
its own pull request. It may become `Complete` after external review and merge;
the lifecycle branch is then recreated from main for 4.0.4.3.3.
