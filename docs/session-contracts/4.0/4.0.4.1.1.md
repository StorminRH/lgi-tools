## Session 4.0.4.1.1 — Gated chain authoring

**Sub-version:** 4.0.4.1
**Master plan:** `docs/VERSION_4_0_PLAN.md` §4.0.4.1
**UX gate:** Yes
**Execution profile:** Frontier autonomous coding agent
**Delivery unit:** One agent session, one shared sub-version branch, one sub-version PR
**Roadmap coverage:** §4.0.4.1 gated field-scoped mutations, first-run root flow, add/edit authoring and reversible mutation foundations
**Internal phases:** 1. Land editor-gated field mutations and optimistic rejection handling; 2. Land home selection and add-from-node authoring; 3. Land edit and tombstone/restore foundations and review the flow
**Split triggers:** Authoring requires a mutation shape that prevents the later unified collapse pathway from owning every destructive connection outcome

## 1. Objective

Make a blank map hand-authorable from one root while establishing the gated,
field-scoped and reversible mutation foundations later connection behavior uses.

## 2. Current context and dependencies

- **DEP-1:** Sub-version 4.0.2.2 shipped the chain schema and authorization gate.
- **DEP-2:** Sub-version 4.0.2.3 shipped the reactive fan-out and 4.0.3.3 shipped the window surfaces.
- **DEP-3:** Decision D11 requires additions to grow from an existing node and forbids disconnected systems.

## 3. Done conditions

- **DC-1:** A blank map shows only the home-system prompt and the selected system becomes its root.
- **DC-2:** An editor can add a destination from an existing node and the system and connection fan out to every client.
- **DC-3:** Every mutation is field-scoped, equality-skipping and editor-gated; viewers are rejected and optimistic rejection reconciles correctly.
- **DC-4:** Editing is live, and tombstone/restore foundations round-trip prior system and connection state.
- **DC-5:** No user-facing connection sever or delete bypasses the collapse pathway reserved for 4.0.4.1.2.

## 4. In scope

- **IS-1:** Home, add-from-node, type-ahead and field editing.
- **IS-2:** Gate enforcement, optimistic rejection and no-op skipping.
- **IS-3:** Reversible tombstone/restore foundations without destructive connection UI.

## 5. Out of scope

- **OOS-1:** Codex auto-fill, EOL, mass presentation and user-facing sever/delete, owned by 4.0.4.1.2.
- **OOS-2:** Automatic mapping and signatures.

## 6. Hard constraints

- **HC-1:** Additions grow from an existing node so one root holds by construction.
- **HC-2:** Viewers cannot mutate and unchanged values produce no write.
- **HC-3:** No destructive connection surface exists outside the later unified collapse pathway.

## 7. Decisions the session plan must resolve

- **PD-1:** Field mutation granularity and optimistic rejection reconciliation.
- **PD-2:** Home and add-from-node composition against the shipped canvas/window surfaces.
- **PD-3:** The tombstone contract 4.0.4.1.2 can use without migration.

## 8. Acceptance criteria

- **AC-1:** The first selected system becomes the only root — proving DC-1.
- **AC-2:** Add-from-node appears on a second client and no disconnected-add affordance exists — proving DC-2.
- **AC-3:** Viewer rejection, editor success and equality-skip behavior are deterministic — proving DC-3.
- **AC-4:** Edit and tombstone/restore return the prior fixture state — proving DC-4.
- **AC-5:** Inspection finds no destructive connection path outside the reserved seam — proving DC-5 and HC-3.

## 9. Verification

- **V-1:** Two-client home, add and edit demonstration.
- **V-2:** Role, optimistic rejection, equality-skip and restore coverage.
- **V-3:** Operator review and the repository's standing definition-of-done gate.

## 10. UX/operator gates

- **G-1:** The operator reviews the home, add and edit flow before this session commits in-branch.

## 11. Baseline/hotspot boundary

Expected baseline effect is Neutral. Planning must keep mutation authority and
optimistic reconciliation focused and below the universal complexity caps.

## 12. Close-out behavior

This is the first of two sessions in sub-version 4.0.4.1. It verifies, pauses
for operator review and commits on the shared branch without opening the
sub-version pull request, then hands off to 4.0.4.1.2.
