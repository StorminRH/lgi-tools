## Session 4.0.1.1.1 — Map access foundation and corp membership resolution

**Sub-version:** 4.0.1.1
**Master plan:** `docs/VERSION_4_0_PLAN.md` §4.0.1.1
**UX gate:** No
**Execution profile:** Frontier autonomous coding agent
**Delivery unit:** One agent session, one shared sub-version branch, one sub-version PR
**Roadmap coverage:** §4.0.1.1 map access foundation and §4.0.1.2 corp membership resolution, merged by the approved delivery topology because they share one principal-resolution seam
**Internal phases:** 1. Land the Neon map and map-access tables with the single authorization helper and its allow-and-deny coverage; 2. Resolve the principal seam and land the gated corp-membership helper against it with its dataset declaration; 3. Prove the gate and the helper together across character and corp principals
**Split triggers:** The principal-resolution seam cannot serve both the Next server caller and the future Convex-side projection writer without a product decision on how corp grants resolve, requiring operator direction before the gate signature can be fixed

## 1. Objective

Establish the durable foundation of map multi-tenancy — the Neon map and access
tables, the single audited authorization helper, and the gated helper that answers
current corp membership — before any map interface exists. This belongs in
sub-version 4.0.1.1 because decision D5 makes this helper the one and only access
gate for every future caller, and its signature must be settled before a second
consumer can be written against it.

## 2. Current context and dependencies

- **DEP-1:** This is the first feature slice of version 4.0; it depends only on sub-version 4.0.0.1 having completed the version-opening obligations.
- **DEP-2:** Decision D5 fixes a single authorization gate for all map access, with no second access-check path permitted at any later point in the version.
- **DEP-3:** Decision D3 places map metadata and access in Neon while per-map chain state lives in Convex, and forbids any Convex write back to Neon.
- **DEP-4:** The corp-membership helper follows the repository's established affiliation pattern for personal slow-changing data and routes every external call through the shared gated fetch wrapper; no new external host literal is introduced.
- **DEP-5:** The principal-resolution seam established here is consumed later by sub-version 4.0.2.2's Neon-to-Convex access projection and by sub-version 4.0.4.4's access editor.
- **DEP-6:** The master plan's carry-forward records static access-list resolution at grant-write time as the starting posture for corp membership, with dynamic lookup deferred until corp-scale usage demands it.

## 3. Done conditions

- **DC-1:** A migration applies a map table carrying identity, name, owner, timestamps and archive fields, and a map-access table keyed by map, principal and role, where a principal may be a character or a corp and a role is viewer, editor or owner.
- **DC-2:** A single authorization helper resolves a user and a map into that user's role and their view and edit capability, and it is the only access-check path in the repository.
- **DC-3:** The helper's allow-and-deny behavior is proven for character principals and for corp principals independently.
- **DC-4:** The role representation admits additional roles later without a schema migration that rewrites existing rows.
- **DC-5:** A gated helper answers whether a given character currently belongs to a given corp, refreshed under the stale-gated slow-data pattern rather than on every read.
- **DC-6:** The corp-membership dataset carries its declaration in the dataset registry, including its resolved cache time and its storage placement.

## 4. In scope

- **IS-1:** The Neon schema migration for the map and map-access tables.
- **IS-2:** The authorization helper, its signature, and its allow-and-deny coverage.
- **IS-3:** The corp-membership helper, its stale-gating, and its registry declaration.
- **IS-4:** The principal-resolution seam that turns character and corp principals into account identity, shared by both helpers.

## 5. Out of scope

- **OOS-1:** Any Convex schema, Convex function, or the Neon-to-Convex access projection, which belong to sub-version 4.0.2.2.
- **OOS-2:** Any user interface, including the access editor and the map creation flow, which belong to sub-version 4.0.4.4.
- **OOS-3:** The finer role model beyond viewer, editor and owner; it is deliberately deferred rather than rejected and is reconsidered at corp-scale usage.
- **OOS-4:** Dynamic corp-membership refresh events; this session ships the stale-gated read only.
- **OOS-5:** Any `src/mapper/` directory or host-layer scaffolding, which belongs to sub-version 4.0.2.1.

## 6. Hard constraints

- **HC-1:** The authorization helper is the gate required by decision D5. Its signature must serve every future caller, including the Next server and the later Convex-side projection writer, and no second access-check path may be introduced anywhere in the version.
- **HC-2:** The corp-membership placement is declared before it is implemented: the resolved affiliation cache time determines Neon placement and stale-gated refresh on view. A contradiction between that declaration and existing behavior is a placement defect, never a precedent.
- **HC-3:** Every external call routes through the repository's declared wrapper for that integration with an explicit timeout; no new external host literal appears outside its owning module.
- **HC-4:** The role representation must not preclude later roles, including an access-managing role that cannot delete a map.

## 7. Decisions the session plan must resolve

- **PD-1:** The principal-resolution seam — exactly where and how character and corp principals become account identity, given both this session's helpers and two later consumers depend on it.
- **PD-2:** The corp-membership refresh trigger, and whether a corp grant snapshots membership at grant-write time or resolves it at read time under the starting posture the master plan records.
- **PD-3:** The role representation that satisfies the later-roles constraint without over-designing for roles no approved outcome requires.
- **PD-4:** The resolved affiliation cache time from the current external specification, and the stale-gate threshold that follows from it.

## 8. Acceptance criteria

- **AC-1:** Applying the migration to a clean database produces both tables with the recorded columns, keys and constraints — proving DC-1.
- **AC-2:** The authorization helper returns the expected role and capabilities for an owner, an editor, a viewer and an unrelated user, and a repository-wide search confirms no second access-check path exists — proving DC-2 and HC-1.
- **AC-3:** The helper resolves access granted by character principal and access granted by corp principal independently, including the deny case for each — proving DC-3.
- **AC-4:** Adding a role to the representation requires no rewrite of existing access rows — proving DC-4.
- **AC-5:** The corp-membership helper answers correctly against a mocked external response, refreshes only once its stale gate opens, and does not call outward on a fresh read — proving DC-5.
- **AC-6:** The dataset registry contains the corp-membership declaration with its cache time and placement, and the registry's own checks pass — proving DC-6 and HC-2.

## 9. Verification

- **V-1:** Migration application output against a clean database, with the resulting table definitions.
- **V-2:** The allow-and-deny matrix output for the authorization helper across both principal kinds.
- **V-3:** Corp-membership helper coverage against mocked external responses, including the stale-gate open and closed cases.
- **V-4:** Dataset-registry declaration checks.
- **V-5:** The repository's standing definition-of-done gate.
