## Session 4.0.4.2.1 — Tracked location and jump classification

**Sub-version:** 4.0.4.2
**Master plan:** `docs/VERSION_4_0_PLAN.md` §4.0.4.2
**UX gate:** No
**Execution profile:** Frontier autonomous coding agent
**Delivery unit:** One agent session, one shared sub-version branch, one PR per session
**Roadmap coverage:** §4.0.4.2 per-character/per-map tracking, existing-engine dataset registration, cadence and pure jump classification
**Internal phases:** 1. Resolve placement and register the opt-in tracked-location dataset; 2. Prove access teardown and zero-write stationary behavior; 3. Classify gate, wormhole and noise transitions
**Split triggers:** The dataset cannot follow the existing synchronization subject pattern, or the required external scopes are unavailable before deployment

## 1. Objective

Establish the live location signal and classify movement correctly before any
classification is allowed to mutate the shared chain.

## 2. Current context and dependencies

- **DEP-1:** The operator must enable the location, ship-type and online read scopes before this session deploys.
- **DEP-2:** The existing synchronization engine and registry own dataset cadence, no-op writes and teardown.
- **DEP-3:** The shipped adjacency asset distinguishes stargate travel from wormhole travel.

## 3. Done conditions

- **DC-1:** Tracking is opt-in per character per map and follows the existing engine subject pattern and dataset union.
- **DC-2:** Revoking access tears down tracking, and unchanged upstream state produces no write.
- **DC-3:** Adjacent locations classify as gate travel; non-adjacent locations classify as a wormhole jump.
- **DC-4:** Docking, undocking, same-system movement and session discontinuities author nothing and classify according to the resolved policy.
- **DC-5:** Location bookkeeping never lands on a watched chain document.

## 4. In scope

- **IS-1:** Tracking opt-in, registry declaration, engine integration and cadence.
- **IS-2:** Pure jump classification and noise filtering.

## 5. Out of scope

- **OOS-1:** Collaborative authoring, mass decrement and observation emission, owned by 4.0.4.2.2.
- **OOS-2:** Fog and promotion, owned by 4.0.4.2.3.

## 6. Hard constraints

- **HC-1:** Placement follows current cache specifications and the existing live-core engine.
- **HC-2:** No third scheduler or synchronization mechanism is introduced.
- **HC-3:** Stationary pilots cause zero collaborative writes and location never touches chain documents.

## 7. Decisions the session plan must resolve

- **PD-1:** Current cache times, cadence floor and registry shape.
- **PD-2:** Session-change, simultaneous-scout and repeated-arrival classification behavior.
- **PD-3:** Tracking representation and access-revocation teardown.

## 8. Acceptance criteria

- **AC-1:** The dataset appears in the engine union and opt-in is scoped per character per map — proving DC-1.
- **AC-2:** Revocation stops tracking and a stationary observation window produces zero writes — proving DC-2.
- **AC-3:** Known gate and non-gate pairs classify correctly — proving DC-3.
- **AC-4:** Docking, same-system and session-change fixtures follow the resolved no-authoring policy — proving DC-4.
- **AC-5:** Storage inspection finds no location field on a chain document — proving DC-5 and HC-3.

## 9. Verification

- **V-1:** Dataset registration, access teardown and zero-write evidence.
- **V-2:** Classification/noise test matrix.
- **V-3:** Registry checks and the repository's standing definition-of-done gate.

## 10. UX/operator gates

- **G-1:** The session stops before deployment unless the operator has enabled all three required external scopes.

## 11. Baseline/hotspot boundary

Expected baseline effect is Neutral. Planning must extend the protected
synchronization engine through its existing subject pattern and verify its
complexity remains within universal caps.

## 12. Close-out behavior

This is the first of three sessions in sub-version 4.0.4.2 and ships through its
own pull request. It may become `Complete` after external review and merge; the
shared lifecycle branch is then recreated from main for 4.0.4.2.2.
