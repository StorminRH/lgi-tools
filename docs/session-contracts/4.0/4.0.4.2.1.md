## Session 4.0.4.2.1 — Jump tracking, classification and authoring

**Sub-version:** 4.0.4.2
**Master plan:** `docs/VERSION_4_0_PLAN.md` §4.0.4.2
**UX gate:** No
**Execution profile:** Frontier autonomous coding agent
**Delivery unit:** One agent session, one shared sub-version branch, one PR per session
**Roadmap coverage:** §4.0.4.2 auto-mapping on jump — the tracked-location dataset, jump classification, wormhole-exit authoring, the observed-jump mass layer, and the first observation emissions
**Internal phases:** 1. Land the opt-in tracked-location dataset on the existing synchronization engine following its documented registration path; 2. Classify consecutive locations into gate jumps and wormhole jumps against the adjacency asset, filtering docking and same-system noise; 3. Author the system and connection on a wormhole jump, decrement the crossed connection's mass budget, and emit the first observation events
**Split triggers:** The location dataset cannot be registered on the existing engine without forking its subject pattern, or the operator scope registration named below has not been completed before this session's code would deploy

## 1. Objective

Deliver the heartbeat: a tracked scout's wormhole jump authors the system and the
connection for every viewer with no interaction. This is the first session of
sub-version 4.0.4.2 and delivers the complete authoring capability; the fog halo,
the promotion rule and the hole-matching refinement follow in the second session.
The sub-version ships one pull request per session because its combined diff would
otherwise be too large to review as one change.

## 2. Current context and dependencies

- **DEP-1:** An operator step precedes this session's deployment: the location, ship-type and online read scopes must be enabled on the external application registration before this code deploys, under the standing scope-ceiling rule.
- **DEP-2:** The repository's synchronization engine documents its own registration path for adding a dataset, and its source explicitly anticipates the mapper re-instantiating that pattern against its own dataset lifecycle. The extension follows that path rather than forking it.
- **DEP-3:** Sub-version 4.0.1.3 shipped the stargate adjacency asset that classification runs against.
- **DEP-4:** Sub-version 4.0.4.1 shipped the mutations this session drives and the two mass layers this session's third layer completes.
- **DEP-5:** Decision D16 binds the observation stream's attribution and anti-circularity rules as written: an observation attributes to a wormhole's origin side only, the untyped far-side code is never an attributable type, and inferred values never enter the stream.
- **DEP-6:** Decision D6 permits only the two sanctioned reactivity mechanisms; this session adds a dataset to the existing engine and introduces no third scheduler.
- **DEP-7:** The token-refresh race that once gated this work is fixed and directly covered, so no additional pre-gate applies.

## 3. Done conditions

- **DC-1:** A tracked scout's wormhole jump causes the destination system and the connection to appear for every viewer of the map with no interaction.
- **DC-2:** Tracking is opt-in per character per map, and the location dataset follows the engine's established subject pattern, including its addition to the engine's dataset union.
- **DC-3:** An unchanged upstream response produces no write, so a tracked but stationary pilot generates no collaborative writes at all.
- **DC-4:** Consecutive locations adjacent in the gate graph are classified as gate jumps and author nothing; non-adjacent consecutive locations are classified as wormhole jumps and author the system and connection.
- **DC-5:** Docking, undocking and same-system movement are filtered and never classified as a jump.
- **DC-6:** A wormhole jump decrements the crossed connection's mass budget, completing the mass model's third layer.
- **DC-7:** A jump-verified connection observation is recorded in the durable observation stream carrying no map identity and no pilot identity, attributed to the wormhole's origin side only.
- **DC-8:** Authoring is confined to wormhole exits; travel beyond an exit authors nothing in this session.

## 4. In scope

- **IS-1:** The per-character-per-map tracking opt-in.
- **IS-2:** The location dataset registered on the existing synchronization engine.
- **IS-3:** Jump classification against the adjacency asset, including noise filtering.

## 6. Hard constraints

- **HC-1:** The placement declaration comes first: the location, ship and online cache times resolved from the external specification place this dataset in the live collaborative core under the engine's established pattern, with its registry declaration included. Any deviation is a placement defect.
- **HC-2:** Authoring every visited system is forbidden. Only wormhole exits are authored, which is why no orphan-cleanup machinery is needed.
- **HC-3:** Location data never lands on a chain document, preserving the separation between frequently-changing bookkeeping and the watched chain payload.
- **HC-4:** The observation event carries no chain topology, no map identity and no pilot identity, and attributes only to the origin side. The untyped far-side code is never recorded as an attributable type.
- **HC-5:** No third reactivity mechanism is introduced; this extends the existing engine.

## 7. Decisions the session plan must resolve

- **PD-1:** Classification edge cases — session changes producing a location discontinuity, several scouts moving simultaneously, and how repeated arrival stays idempotent against the map-and-system index.
- **PD-2:** The resolved cache times for the location, ship and online datasets from the current external specification, and the cadence floor that follows.
- **PD-3:** How the opt-in is represented per character per map, and what happens to tracking when access is revoked.
- **PD-4:** The exact observation event shape that satisfies the attribution rules while remaining useful.

## 8. Acceptance criteria

- **AC-1:** With tracking enabled, a scout's wormhole jump surfaces the destination system and connection on a second client with no interaction — proving DC-1 and DC-8.
- **AC-2:** The dataset appears in the engine's dataset union and follows its subject pattern, with the opt-in scoped per character per map — proving DC-2 and HC-5.
- **AC-3:** A tracked but stationary pilot produces no collaborative writes over an observation window — proving DC-3.
- **AC-4:** Adjacent consecutive locations author nothing while non-adjacent ones author a system and connection, verified against known gate pairs — proving DC-4.
- **AC-5:** Docking, undocking and same-system movement produce no classification — proving DC-5.
- **AC-6:** A wormhole jump reduces the crossed connection's remaining mass budget by the crossing — proving DC-6.
- **AC-7:** An emitted observation contains the origin-side system and type with no map or pilot identity, and a far-side untyped crossing emits no attributable type — proving DC-7 and HC-4.
- **AC-8:** An inspection of the location dataset's storage confirms it touches no chain document, keeping it within the engine subject pattern DC-2 requires — proving DC-2 and HC-3.
