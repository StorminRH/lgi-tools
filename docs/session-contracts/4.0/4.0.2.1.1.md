## Session 4.0.2.1.1 — Map shell and host layer

**Sub-version:** 4.0.2.1
**Master plan:** `docs/VERSION_4_0_PLAN.md` §4.0.2.1
**UX gate:** Yes
**Execution profile:** Frontier autonomous coding agent
**Delivery unit:** One agent session, one shared sub-version branch, one sub-version PR
**Roadmap coverage:** §4.0.2.1 map shell, kept as its own bundle by the approved delivery topology because the route restructure's blast radius is every route in the application and must be revertable on its own
**Internal phases:** 1. Restructure the routes into groups so the existing site chrome moves without any visual change to any existing route; 2. Add the admin-gated development wall and the edge-to-edge full-viewport map canvas; 3. Create the mapper host layer with its boundary rules and compose the floating chrome at the application layer
**Split triggers:** The route restructure proves not to be a mechanical no-op for some existing route, requiring a visual or behavioral change that this session's scope explicitly forbids

## 1. Objective

Create the stage: a development-walled, true edge-to-edge full-viewport map route
with floating chrome, and the mapper host layer with the boundary rules that keep
it above features in the import direction. This belongs in sub-version 4.0.2.1
because everything later in the version renders inside it, and because the route
restructure it requires touches every route in the application and must land as
an independently revertable change.

## 2. Current context and dependencies

- **DEP-1:** The application currently has no route groups. Every route sits directly under the application root, and the root layout renders the site header and footer for all of them.
- **DEP-2:** The site header and footer components have no covering tests, so proving the restructure is a no-op for existing routes cannot rely on existing coverage.
- **DEP-3:** Decision D9 fixes the map's chrome as exactly three floating elements composed at the application layer and never inside the mapper: a menu at the top left, a reserved search slot at the top centre, and the existing account control at the top right. The map switcher added later is the fourth.
- **DEP-4:** Decision D14 makes the mapper a host layer that sits above features in the import direction: the mapper may import a feature's public surface, and no feature may ever import the mapper.
- **DEP-5:** The repository's boundary configuration is deny-by-default with an explicit permitted-dependency list per zone, so an import from a feature to a new mapper zone already fails unless it is explicitly permitted. The required work is registering the zone and its permitted directions, and proving the forbidden direction stays forbidden.
- **DEP-6:** Decision D13 keeps the map behind an administrator wall until the version completes its audit; sub-version pull requests may merge half-built behind that wall.
- **DEP-7:** Decision D11 forbids shipping an inert placeholder control, which is why the top-centre search slot is reserved rather than built.

## 3. Done conditions

- **DC-1:** A non-administrator reaching any map route sees an under-development wall enforced on the server in the map route group's layout, and an administrator sees the canvas.
- **DC-2:** The map canvas is edge-to-edge at any window size against the full dynamic viewport height, the page itself never scrolls, the wheel zooms rather than scrolls, the view re-fits on resize under a debounce, and the camera is bounded by minimum and maximum zoom.
- **DC-3:** The menu and the account control float over the canvas, composed at the application layer in the map group's layout, with cross-tool links opening in new tabs so a live map is never navigated away from. The top-centre search slot is reserved and no inert control ships in it.
- **DC-4:** A mapper host layer exists as a registered boundary zone whose permitted import directions are recorded, and an import from a feature into the mapper fails the boundary check, proven by a test.
- **DC-5:** Every existing route is visually and behaviorally unchanged by the route restructure, verified mechanically rather than by inspection alone.

## 4. In scope

- **IS-1:** The route-group restructure that moves the existing site chrome into a site group while leaving each route's rendered output unchanged.
- **IS-2:** The server-side development wall in the map route group's layout and the administrator allow-list mechanism it consults.
- **IS-3:** The full-viewport canvas container, its resize and camera bounding behavior.
- **IS-4:** The mapper host layer, its boundary-zone registration, its permitted directions, and the test proving the forbidden direction fails.
- **IS-5:** Composition of the menu and account control as floating chrome at the application layer.

## 5. Out of scope

- **OOS-1:** Any map data, Convex schema, subscription or mutation, which belong to sub-versions 4.0.2.2 and later.
- **OOS-2:** The overlay window framework, which belongs to sub-version 4.0.3.3.
- **OOS-3:** Building the search control in the reserved slot, which belongs to a later version.
- **OOS-4:** Touch and mobile optimization, which decision D12 defers to a separate later decision.
- **OOS-5:** Map settings content inside the account control, and the map switcher, which belong to sub-version 4.0.4.4.
- **OOS-6:** Any change to an existing route's appearance or behavior.

## 6. Hard constraints

- **HC-1:** The development wall is enforced on the server in the route group's layout. A client-side hide is not an acceptable implementation.
- **HC-2:** The floating chrome is composed at the application layer. The mapper must not import the account control or any other authentication-owned component, because the permitted import direction runs from the mapper to features and the application composes above both.
- **HC-3:** The restructure moves the existing site chrome without any visual change to any existing route.
- **HC-4:** No feature may import the mapper, in this session or any later one, and the boundary configuration must express that as a permanent rule rather than a convention.
- **HC-5:** No inert placeholder control ships in the reserved search slot.

## 7. Decisions the session plan must resolve

- **PD-1:** The separability judgement on the route restructure — confirming the move is mechanical and reversible before executing it, and establishing how a no-op is proven for every existing route given the site chrome has no covering tests.
- **PD-2:** The administrator allow-list mechanism, including where administrator identity is read from on the server.
- **PD-3:** The mapper zone's permitted import directions, expressed against the repository's current zone model rather than a simplified layer stack.
- **PD-4:** The resize and re-fit behavior's debounce, and the camera bounds that keep the canvas usable without trapping the view.

## 8. Acceptance criteria

- **AC-1:** A request to a map route as a non-administrator renders the wall and as an administrator renders the canvas, with the decision made on the server — proving DC-1 and HC-1.
- **AC-2:** The canvas fills the viewport at several window sizes with no page scroll, the wheel zooms, a resize re-fits under the debounce, and the camera respects its bounds — proving DC-2.
- **AC-3:** The menu and account control render over the canvas from the application layer, cross-tool links open in new tabs, and the reserved slot contains no control — proving DC-3 and HC-5.
- **AC-4:** A deliberately added import from a feature into the mapper fails the boundary check, and removing it restores a passing check — proving DC-4 and HC-4.
- **AC-5:** Every existing route renders identically before and after the restructure under a mechanical comparison — proving DC-5 and HC-3.
- **AC-6:** A repository-wide check confirms the mapper imports no authentication-owned component, so the floating chrome is composed at the application layer as DC-3 requires — proving DC-3 and HC-2.

## 9. Verification

- **V-1:** Wall and canvas behavior demonstrated for both an administrator and a non-administrator.
- **V-2:** Resize, scroll-suppression and camera-bound behavior at several viewport sizes.
- **V-3:** The boundary-check failure output for a feature-to-mapper import, and the passing state without it.
- **V-4:** The mechanical no-op comparison covering every existing route.
- **V-5:** The repository's standing definition-of-done gate.

## 10. UX/operator gates

- **G-1:** The `UX gate` marker is `Yes`. The operator reviews, in a local browser, the wall and canvas behavior at several window sizes, the floating chrome placement, and a sample of existing routes confirming the restructure changed nothing. The session pauses for that review before the pull request opens.

## 11. Baseline/hotspot boundary

Expected baseline effect is Neutral: new host-layer code is feature growth rather
than pressure on a measured surface. Planning must verify against the live
baseline that composing the account control at the application layer consumes it
rather than modifying it, so the authorization-surface watch AF-008 — whose
trigger counts files matching the authorization contract and schema patterns — is
not advanced by this session. Production file and line counts will rise; that is
expected for a new host layer.

## 12. Close-out behavior

This session is the only session of sub-version 4.0.2.1, so it completes the
sub-version: it commits on the shared lifecycle branch, pauses for the operator
browser review named above, then opens the sub-version pull request. It may
become `Complete` only once that pull request passes the external review gate and
merges. The map ships behind the development wall and is not released. On merge,
the resolver advances to sub-version 4.0.2.2.
