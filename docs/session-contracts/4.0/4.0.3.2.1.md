## Session 4.0.3.2.1 — Motion layer

**Sub-version:** 4.0.3.2
**Master plan:** `docs/VERSION_4_0_PLAN.md` §4.0.3.2
**UX gate:** Yes
**Execution profile:** Frontier autonomous coding agent
**Delivery unit:** One agent session, one shared sub-version branch, one sub-version PR
**Roadmap coverage:** §4.0.3.2 motion layer, kept as its own bundle by the approved delivery topology because it runs a second distinct operator tuning loop whose inputs are unknown until the layout engine resolves
**Internal phases:** 1. Land the surfacing birth vocabulary and the position-tween scheduler with edges tracking state; 2. Land camera easing, hover life, the reduced-motion path and the drag-performance hardening; 3. Expose the tempo and flavor dials and iterate to operator sign-off from live mapping
**Split triggers:** The tween scheduler cannot hold its frame budget with many simultaneous movers without a layout or reconciler change that belongs to another sub-version, requiring operator direction before proceeding

## 1. Objective

Make the canvas move like water: births that surface in place, forced shifts that
glide with their edges tracking, a camera that always eases, and stillness when
nothing is happening. This belongs in sub-version 4.0.3.2 because motion is how
the map communicates change, and because decision D8 makes motion presentation —
local, derived, and never fed back into shared state.

## 2. Current context and dependencies

- **DEP-1:** Sub-version 4.0.3.1 shipped the deterministic layout engine whose computed positions are the targets this session animates toward.
- **DEP-2:** Sub-version 4.0.2.3 shipped the reconciler whose named intents — arrival, departure and repositioning — this session consumes as motion intents.
- **DEP-3:** Decision D8 fixes motion as meaning rather than decoration: birth surfaces in place with no positional travel, forced shifts are tweened with edges tracking, the map is still when still, hover is the one cursor-responsive moment, and the camera always glides.
- **DEP-4:** Decision D8 also fixes one spring-like easing family and three duration tiers, all exposed as dials, with no new animation dependency introduced.
- **DEP-5:** The repository forbids running a production-mode build locally or before merge; only the deployment platform builds for production after a change reaches the trunk. Any performance claim must therefore be established by a method compatible with that rule.
- **DEP-6:** Sub-version 4.0.2.3 established that loading is not a distinct visual state, so the surfacing animation covers both initial arrival and live insertion with one vocabulary.

## 3. Done conditions

- **DC-1:** An arriving node surfaces in place — starting slightly small, dim and soft, scaling through a small overshoot and settling sharp — with no positional travel, on both initial load and live insertion.
- **DC-2:** A forced layout shift glides with its edges tracking the moving nodes, with no visual desynchronization between an edge and its endpoints and no per-frame layout thrash.
- **DC-3:** A node under the user's own drag responds at one-to-one with no smoothing and no transition applied, and dragging remains smooth under production-like conditions.
- **DC-4:** Hover produces a glow and a subtle breathing response, and the map is otherwise completely still, with no idle animation and no rendering work at rest.
- **DC-5:** Camera movement always eases and never jumps.
- **DC-6:** A reduced-motion preference collapses all motion to instant or gentle fades.
- **DC-7:** The operator has signed off the feel from live mapping, with the tempo and flavor dials exposed.

## 4. In scope

- **IS-1:** The birth, departure and hover presentation, applied to an inner element through transform and opacity only.
- **IS-2:** The position-tween scheduler that drives state so edges track their endpoints.
- **IS-3:** Camera easing.
- **IS-4:** The reduced-motion path.
- **IS-5:** Drag-performance hardening, including node memoization and the removal of any per-frame re-render cascade.
- **IS-6:** The tempo tier, overshoot, and flavor dial set.

## 5. Out of scope

- **OOS-1:** Window and overlay animation, which belongs to sub-version 4.0.3.3.
- **OOS-2:** Any new layout behavior; this session animates toward the shipped engine's targets and never influences them.
- **OOS-3:** Sound.
- **OOS-4:** Any new animation dependency.
- **OOS-5:** Any change to the reconciler's intent vocabulary beyond consuming it.

## 6. Hard constraints

- **HC-1:** Position transitions are scheduled in code and drive state. A stylesheet transition on node position is forbidden, because edges are computed from state and a style-only glide desynchronizes them.
- **HC-2:** User input is never smoothed, and transitions are suppressed on any node the user is dragging.
- **HC-3:** One spring-like easing family and three duration tiers, all dials, with no new animation dependency.
- **HC-4:** Motion never feeds back into layout or into any synchronized state.
- **HC-5:** The map performs no work at rest: no idle animation and no rendering cost when nothing has changed.
- **HC-6:** Performance evidence must be produced without running a production build locally, because the repository forbids that; the required outcome is smooth dragging under production-like conditions, and the means of establishing it is a planning decision.

## 7. Decisions the session plan must resolve

- **PD-1:** The method by which production-like drag performance is established and evidenced, given local production builds are forbidden — for example a deployed preview, a production-mode profile taken from the platform, or an equivalent the operator accepts.
- **PD-2:** The tween scheduler's design and its frame budget with many simultaneous movers.
- **PD-3:** Whether a chain collapse receives a heavier departure than an ordinary removal, resolved during the tuning loop.
- **PD-4:** Whether an edge fades with its child or grows from its parent, resolved as a tuning dial.
- **PD-5:** The three duration tiers' values around the specified middle anchor.

## 8. Acceptance criteria

- **AC-1:** A node arriving on initial load and a node arriving live both surface in place with no positional travel — proving DC-1.
- **AC-2:** A forced layout shift shows edges tracking their endpoints throughout, with no desynchronization and no layout thrash in a profile — proving DC-2 and HC-1.
- **AC-3:** Dragging is one-to-one with no transition applied to the dragged node, and drag smoothness is evidenced under production-like conditions by the method resolved in planning — proving DC-3, HC-2 and HC-6.
- **AC-4:** Hover produces its response, and a profile of the idle map shows no animation and no rendering work — proving DC-4 and HC-5.
- **AC-5:** Camera movements ease in every case, including fit and focus — proving DC-5.
- **AC-6:** With a reduced-motion preference set, all motion collapses to instant or gentle fades — proving DC-6.
- **AC-7:** The operator records sign-off on the feel after live mapping with the dials exposed — proving DC-7.
- **AC-8:** An inspection confirms one easing family, three duration tiers, and no new animation dependency in the manifest, and those tiers are the dials the operator tuned — proving DC-7 and HC-3.

## 9. Verification

- **V-1:** Frame-rate evidence during dragging and during a multi-node re-layout, produced under production-like conditions by the planning-resolved method.
- **V-2:** A profile of the idle map showing no animation and no rendering work.
- **V-3:** A reduced-motion demonstration.
- **V-4:** Edge-tracking evidence across a forced layout shift.
- **V-5:** The operator's recorded sign-off from live mapping.
- **V-6:** The repository's standing definition-of-done gate.

## 10. UX/operator gates

- **G-1:** The `UX gate` marker is `Yes`, and the live tuning loop is the gate itself: the tempo, overshoot and flavor dials are exposed, the operator maps in-game against the local development server, and iteration continues to sign-off. The session pauses for that loop before the pull request opens.
- **G-2:** If establishing production-like performance evidence requires a deployed preview, that deployment is requested from the operator rather than performed autonomously, and the preview is removed after use.

## 11. Baseline/hotspot boundary

Expected baseline effect is Neutral; this is all-new mapper presentation code.
Planning must confirm against the live baseline that none of AF-006, AF-007 or
AF-008 counts a surface this session touches, and must watch the tween scheduler's
own complexity on arrival so a frame-budget-driven design does not land above the
repository's universal complexity caps.

## 12. Close-out behavior

This session is the only session of sub-version 4.0.3.2, so it completes the
sub-version: it commits on the shared lifecycle branch, runs the tuning loop and
pauses for operator sign-off, then opens the sub-version pull request. It may
become `Complete` only once that pull request passes the external review gate and
merges. The map remains behind the development wall. On merge, the resolver
advances to sub-version 4.0.3.3.
