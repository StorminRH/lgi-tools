## Session 4.0.1.6.1 — Statics dataset ingest

**Sub-version:** 4.0.1.6
**Master plan:** `docs/VERSION_4_0_PLAN.md` §4.0.1.6
**UX gate:** No
**Execution profile:** Frontier autonomous coding agent
**Delivery unit:** One agent session, one shared sub-version branch, one sub-version PR
**Roadmap coverage:** §4.0.1.6 statics dataset ingest, kept as its own bundle by the approved delivery topology because an external refresh feed with a promote gate and a degradation path is a materially different risk domain from derived reference assets
**Internal phases:** 1. Land the version-discovered scheduled pull into a version-pinned snapshot with a promote gate; 2. Cross-check the snapshot against the independent lineage source and land the serving read path with its degradation behavior; 3. Record attribution, the registry declaration and the resolved source status
**Split triggers:** The community feed's shape or licensing differs materially from what the master plan records, or the cross-check source disagrees with the feed beyond a reconcilable margin, requiring an operator decision on which source is authoritative

## 1. Objective

Close the version's one genuine external data gap by landing per-system static
wormhole assignments as a controlled, versioned copy of the community dataset.
This belongs in sub-version 4.0.1.6 because the signature inference engine cannot
constrain a system's unknowns without knowing that system's statics, and because
an external feed with a scheduled pull, a human promote gate and a degradation
path is independent of every other groundwork slice.

## 2. Current context and dependencies

- **DEP-1:** This is the version's only genuinely external dataset. The repository's external-data policy treats such a source as a refresh feed, never a runtime dependency, and requires serving to continue from the last good copy when the feed is unavailable.
- **DEP-2:** The feed's current version is discovered from the publisher's own controller script rather than assumed, and the data changes rarely, so a large difference between snapshots is a signal to review rather than to apply.
- **DEP-3:** An independently licensed lineage source exists and is the confirmed original of the community dataset; it serves as the bootstrap and cross-check rather than as a second runtime source.
- **DEP-4:** `docs/DATA_SOURCES.md` is the resolved map from data domain to source and records the succession watch on an expanded upstream interface that would, if it reaches production with per-system statics, become primary and demote this feed to fallback.
- **DEP-5:** This sub-version must ship, or be explicitly running degraded, before the second session of sub-version 4.0.4.3; nothing earlier in the version depends on it.
- **DEP-6:** The repository already owns a scheduled-task shell; a new schedule joins that shell rather than cloning it.

## 3. Done conditions

- **DC-1:** A scheduled pull, running on a recurring cadence and available on demand, retrieves the community statics feed at its discovered version and writes a version-pinned snapshot to Neon.
- **DC-2:** A promote step stands between the snapshot and the served data, presenting the difference against the current promoted copy so a large change is reviewed rather than applied automatically.
- **DC-3:** The promoted copy is cross-checked against the independent lineage source, and disagreements are surfaced rather than silently resolved.
- **DC-4:** The serving read path returns per-system statics from the last good promoted copy, and continues to do so while the external feed is unavailable.
- **DC-5:** Attribution to the community source is present in the site's credits, and the pull cadence is polite to the publisher.
- **DC-6:** The dataset carries its registry declaration with resolved cache time and placement, and the resolved source map records this domain's status in the same change.

## 4. In scope

- **IS-1:** The scheduled and on-demand pull, version discovery, and the version-pinned snapshot storage.
- **IS-2:** The promote gate and its difference presentation.
- **IS-3:** The cross-check against the independent lineage source.
- **IS-4:** The serving read path and its last-good-copy degradation behavior.
- **IS-5:** Attribution, the registry declaration, and the resolved source-map status update.

## 5. Out of scope

- **OOS-1:** Any consumer of the statics data, including the inference engine and the pick list, which belong to sub-version 4.0.4.3.
- **OOS-2:** Observation scoring, per-system confidence thresholds, and the merge of observed data over the community copy, which belong to a later version.
- **OOS-3:** System effects, which are derivable from the static export and ship with a later version.
- **OOS-4:** Acting on the upstream succession watch; if the expanded interface reaches production, that promotion is a separate future decision.
- **OOS-5:** Any map interface or `src/mapper/` code.

## 6. Hard constraints

- **HC-1:** The external feed is never runtime load-bearing. Serving degrades to the last good promoted copy and never fails because the feed is down.
- **HC-2:** A large difference between the incoming snapshot and the promoted copy blocks automatic promotion and requires review.
- **HC-3:** The new schedule joins the repository's existing scheduled-task shell rather than cloning it.
- **HC-4:** Attribution to the community source is present, and the pull cadence does not burden the publisher.
- **HC-5:** The succession watch stays recorded in the resolved source map; this session does not decide it.

## 7. Decisions the session plan must resolve

- **PD-1:** The snapshot and promote mechanics — how a snapshot is pinned, how promotion is triggered, and how the difference is presented for review.
- **PD-2:** The threshold that distinguishes an ordinary difference from one large enough to block promotion.
- **PD-3:** The schedule's cadence and its placement within the existing scheduled-task shell.
- **PD-4:** How cross-check disagreements are surfaced and where they are recorded.
- **PD-5:** The resolved cache time and storage placement for the dataset declaration.

## 8. Acceptance criteria

- **AC-1:** A pull run discovers the feed's current version and writes a version-pinned snapshot without touching the promoted copy — proving DC-1.
- **AC-2:** Promotion of a snapshot whose difference exceeds the review threshold is blocked pending review, while an ordinary difference promotes cleanly — proving DC-2 and HC-2.
- **AC-3:** The cross-check against the independent lineage source reports agreement for known systems and surfaces any disagreement — proving DC-3.
- **AC-4:** Statics for known systems are served correctly against community-known values, and serving continues from the last good copy with the external feed made unavailable — proving DC-4 and HC-1.
- **AC-5:** Credits display the community attribution, and the schedule is registered within the existing scheduled-task shell rather than a new one — proving DC-5 and HC-3.
- **AC-6:** The dataset registry contains this dataset's declaration and the resolved source map records this domain's current status — proving DC-6.

## 9. Verification

- **V-1:** A promoted snapshot serving statics for known systems, spot-checked against community-known values.
- **V-2:** A feed-unavailable degradation demonstration showing serving continues from the last good copy.
- **V-3:** Cross-check output against the independent lineage source.
- **V-4:** Promote-gate behavior for both an ordinary and an over-threshold difference.
- **V-5:** Dataset-registry and resolved-source-map checks.
- **V-6:** The repository's standing definition-of-done gate.

## 10. UX/operator gates

This session changes no user-facing behavior beyond the credits attribution, and
its `UX gate` marker is `No`; no operator browser review is required before the
pull request opens. The promote gate is an operational review step inside the
delivered system, not a lifecycle pause for this session. The standing external
review gate on the pull request still applies.

## 11. Baseline/hotspot boundary

Expected baseline effect is Neutral. Planning must verify against the live
baseline that the scheduled-task shell's registered declaration count moves by
exactly the one schedule this session adds, and that the new ingest does not
widen an already-watched query surface. The live baseline carries watch findings
AF-006, AF-007 and AF-008; planning must confirm none of their triggers is
approached by this change.

## 12. Close-out behavior

This session is the only session of sub-version 4.0.1.6, so it completes the
sub-version: it commits on the shared lifecycle branch, opens the sub-version
pull request, and may become `Complete` only once that pull request passes the
external review gate and merges. It publishes no version record. On merge, the
resolver advances to sub-version 4.0.2.1.
