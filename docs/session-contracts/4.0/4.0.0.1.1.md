## Session 4.0.0.1.1 — Version-opening obligations

**Sub-version:** 4.0.0.1
**Master plan:** `docs/VERSION_4_0_PLAN.md` §4.0.0.1
**UX gate:** No
**Execution profile:** Frontier autonomous coding agent
**Delivery unit:** One agent session, one shared sub-version branch, one sub-version PR
**Roadmap coverage:** The four version-opening obligations recorded by the v3.10 close audit in `docs/backlog.md`, which the approved 4.0 delivery topology schedules as Phase 0
**Internal phases:** 1. Give the baseline an adoption-time `Version-start` capture mechanism and apply it to the 4.0 adoption ref; 2. Register the surfaces v3.10 created as baseline metric rows and split the conflated source-suppression metric; 3. Extend the archive fidelity check to the session as-built directory and prove every change against the owning schema
**Split triggers:** Applying the adoption-time capture reveals that a registered metric cannot be measured reproducibly at the adoption ref and needs an operator decision on its definition before the column can be frozen

## 1. Objective

Land the four lifecycle-tooling obligations the v3.10 close audit assigned to the
4.0 opening, so that version 4.0 measures itself against its own starting state
rather than its predecessor's. This belongs in sub-version 4.0.0.1 because all
four are baseline-schema and lifecycle-tooling changes that the baseline's
write-once rule and frozen registered-row set bar once a version's first session
has shipped. They are the only work in 4.0 that must precede every feature slice.

## 2. Current context and dependencies

- **DEP-1:** The obligations and their rationale are recorded in `docs/backlog.md` under the workflow and documentation heading, sourced from v3.10 contract 3.10.0.2.2 decision PD-2 and the archived v3.10 version-audit plan.
- **DEP-2:** `docs/workflows/schema/code-health-baseline.md` is the canonical owner of the baseline's form, its registered metric rows, and its write-once rule; every change here is made through that schema, not against the live document alone.
- **DEP-3:** `docs/CODE_HEALTH_BASELINE.md` is the live baseline at the v3.10 cycle-4 audited ref. It carries watch findings AF-006, AF-007 and AF-008; the `Version-start` column currently holds v3.9-start values because the capture mechanism does not exist.
- **DEP-4:** `.agent-local/verify_archive.py` owns archive fidelity checking and has an existing test module beside it; the v3.10 archive compensated for the missing `session-as-built` coverage with an explicitly recorded manual directory comparison.
- **DEP-5:** No feature slice of 4.0 may ship before this session completes, because the write-once rule freezes the registered-row set once the version's first session lands.

## 3. Done conditions

- **DC-1:** A documented mechanism exists that, at master-version adoption, freezes the adoption ref's measured values into the baseline's `Version-start` column, and the live baseline's `Version-start` column holds values measured at the 4.0 adoption ref rather than inherited v3.9 values.
- **DC-2:** The wide surfaces v3.10 created are registered baseline metric rows with measured current values: Fallow boundary coverage, the vendor-resilience registry, capability instrumentation, and the v3.10 Phase 4 adoption census families.
- **DC-3:** The `Source suppressions` metric is split so that self-invalidating negative type assertions in test files are counted separately from true diagnostic suppressions, and each resulting row reports its own value.
- **DC-4:** `.agent-local/verify_archive.py` checks `session-as-built` directory fidelity as part of its normal bundle verification, with coverage proving the check fails on a corrupted or incomplete as-built directory.
- **DC-5:** The baseline schema and the live baseline agree: every registered row present in one is present in the other, and the schema documents the adoption-time capture rule.

## 4. In scope

- **IS-1:** The adoption-time `Version-start` capture mechanism, its documentation in the owning baseline schema, and its first application to the 4.0 adoption ref.
- **IS-2:** The registered-row additions for the four v3.10-created surfaces and the source-suppression metric split, in both the schema and the live baseline.
- **IS-3:** The `session-as-built` fidelity extension to `.agent-local/verify_archive.py` and its test coverage.
- **IS-4:** Removal of the backlog entry that records these four obligations, once they are delivered.

## 5. Out of scope

- **OOS-1:** Any `src/mapper/` code, Convex schema, or other 4.0 feature work; this session touches lifecycle tooling and documentation only.
- **OOS-2:** Re-auditing the v3.10 measurements or revisiting closed v3.10 findings; the archived bundle is frozen.
- **OOS-3:** Changing watch findings AF-006, AF-007 or AF-008, their triggers, or their dispositions.
- **OOS-4:** Broader refactoring of `.agent-local/` checkers beyond the `session-as-built` fidelity extension.
- **OOS-5:** Introducing new baseline metrics that no recorded obligation calls for.

## 6. Hard constraints

- **HC-1:** The baseline schema remains the single owner of baseline form and registered rows; the live baseline is updated to match it, and no rule is restated in a second document.
- **HC-2:** The source-suppression split must preserve historical readability — the pre-split total must remain reconstructable from the new rows so past deltas stay interpretable.
- **HC-3:** The adoption-time capture mechanism must be reproducible from the adoption ref alone, so a fresh clone measures the same `Version-start` values.
- **HC-4:** This session must complete before any 4.0 feature slice ships, because the write-once rule freezes the registered-row set at the version's first shipped session.

## 7. Decisions the session plan must resolve

- **PD-1:** Where the adoption-time capture mechanism lives — a checker under `.agent-local/`, a documented procedure step in the owning workflow, or a combination — and how it is invoked at adoption.
- **PD-2:** The exact registered-row names, units, and measurement commands for the four v3.10-created surfaces, resolved against how each surface is actually measurable today.
- **PD-3:** The precise boundary of the suppression split — what mechanically distinguishes a self-invalidating negative type assertion in a test file from a true diagnostic suppression — and how each side is counted.
- **PD-4:** Whether the `session-as-built` fidelity check reuses the existing bundle-list mechanism or needs a distinct comparison, given as-built records are per-session files.

## 8. Acceptance criteria

- **AC-1:** Running the adoption-time capture at the 4.0 adoption ref produces the `Version-start` column now recorded in the live baseline, and repeating it from a clean checkout reproduces the same values — proving DC-1 and HC-3.
- **AC-2:** The live baseline and the baseline schema list the identical registered-row set, including the four newly registered surfaces, each with a measured current value — proving DC-2 and DC-5.
- **AC-3:** The split suppression rows report separate counts whose combination reconstructs the previously reported total — proving DC-3 and HC-2.
- **AC-4:** `.agent-local/verify_archive.py` passes on a well-formed bundle and fails on a bundle whose `session-as-built` directory is incomplete or altered — proving DC-4.
- **AC-5:** `docs/backlog.md` no longer lists the four opening obligations as deferred work — proving DC-1, DC-2, DC-3 and DC-4 are delivered rather than re-deferred.

## 9. Verification

- **V-1:** Output of the archive-fidelity test module covering the new `session-as-built` check, including its failing case.
- **V-2:** The measurement commands and their output for each newly registered baseline row and for the split suppression rows.
- **V-3:** A schema-versus-live-baseline row comparison showing the registered sets agree.
- **V-4:** The repository's standing definition-of-done gate.

## 10. UX/operator gates

This session changes no user-facing behavior or appearance, so its `UX gate`
marker is `No` and no operator browser review is required before the pull
request opens. The standing external review gate on the pull request still
applies.

## 11. Baseline/hotspot boundary

This session rewrites the baseline's `Version-start` column and its registered-row
set by design; that is the obligation, not a regression. Expected effect on
measured production surfaces is Neutral — no production source changes. Planning
must confirm against the live baseline that AF-006, AF-007 and AF-008 remain the
only watch findings and carry into 4.0 unchanged, and that no registered row is
silently dropped while the set is extended.

## 12. Close-out behavior

This session is the only session of sub-version 4.0.0.1, so it completes the
sub-version: it commits on the shared lifecycle branch, opens the sub-version
pull request, and may become `Complete` only once that pull request passes the
external review gate and merges. It publishes no version record and bumps no
application version beyond the sub-version's own changelog obligations. On merge,
the resolver advances to sub-version 4.0.1.1.
