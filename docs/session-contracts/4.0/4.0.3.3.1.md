## Session 4.0.3.3.1 — Overlay window framework

**Sub-version:** 4.0.3.3
**Master plan:** `docs/VERSION_4_0_PLAN.md` §4.0.3.3
**UX gate:** Yes
**Execution profile:** Frontier autonomous coding agent
**Delivery unit:** One agent session, one shared sub-version branch, one sub-version PR
**Roadmap coverage:** §4.0.3.3 overlay window framework, kept as its own bundle by the approved delivery topology because combining a general window primitive with its first real consumer would produce an unreviewable diff
**Internal phases:** 1. Build the one window primitive and prove absolute event isolation; 2. Land the three surfaces on that primitive with stacking and dismissal behavior; 3. Add per-device position and size memory and host a placeholder widget through the shipped props contract
**Split triggers:** Absolute event isolation cannot be achieved without a change to the canvas library's event handling that would alter shipped canvas behavior, requiring operator direction

## 1. Objective

Give the map its window system: anchored dock panels, floating pop-outs, and
node-anchored summaries, all on one primitive, with absolute event isolation.
This belongs in sub-version 4.0.3.3 because every later surface that needs to show
detail over the canvas depends on it, and because a second window implementation
appearing later would be architecturally irreversible.

## 2. Current context and dependencies

- **DEP-1:** Sub-version 4.0.2.1 shipped the map shell and the host layer these windows render inside as siblings above the canvas.
- **DEP-2:** Sub-version 4.0.1.3 shipped the widget props contract and the feature public-surface convention that a hosted widget follows; this session exercises that contract with a placeholder before any real widget arrives.
- **DEP-3:** Decision D1 makes window position and size local presentation: they persist per device and are never synchronized.
- **DEP-4:** Decision D15 makes the mapper the provider of the window while features provide the widget, so this session builds the container and not the content.
- **DEP-5:** The master plan records an explicit scope fence here, because an equivalent window manager elsewhere consumed months of effort; the excluded capabilities are deliberate.
- **DEP-6:** This session has no dependency on the layout engine or the motion layer, so it may be re-sequenced earlier within the canvas phase if the layout work stalls.

## 3. Done conditions

- **DC-1:** The current-system panel opens anchored to an edge at a fixed size, driven by selection, and closes on a canvas click.
- **DC-2:** A panel can be popped out into a floating window that can be dragged and freely resized, and its position and size are remembered per device across a reload.
- **DC-3:** Selecting a system other than the current one shows a node-anchored summary card with placeholder content that tracks panning and zooming, and dismisses on deselection or canvas click.
- **DC-4:** Typing and scrolling inside any window never pans or zooms the map.
- **DC-5:** The escape key closes the topmost window, clicking a window brings it to the front, nothing is ever modal over the map, and the canvas stays interactive everywhere a window is not.
- **DC-6:** All three surfaces are built on one primitive, and no second window implementation exists.
- **DC-7:** A placeholder widget renders inside the primitive through the shipped props contract.

## 4. In scope

- **IS-1:** The single window primitive with its thin title, close control, drag handle and pop-out toggle.
- **IS-2:** The three surfaces — anchored dock panel, floating pop-out, and node-anchored summary — built on that primitive.
- **IS-3:** Absolute event isolation between window contents and the canvas.
- **IS-4:** Per-device position and size persistence.
- **IS-5:** Window stacking, front-bringing and escape dismissal.
- **IS-6:** A placeholder widget hosted through the props contract.

## 5. Out of scope

- **OOS-1:** Real panel content — signatures belong to sub-version 4.0.4.3, and richer intelligence content belongs to a later version.
- **OOS-2:** Resizing an anchored panel; anchored panels are fixed-fit and only unanchored windows resize.
- **OOS-3:** A taskbar, minimize behavior, snapping grids, synchronized layouts, multi-monitor pop-outs, and mobile sheet presentations.
- **OOS-4:** Any change to canvas panning or zooming behavior beyond suppressing it under a window.
- **OOS-5:** Window entrance and exit animation beyond what the primitive needs to feel settled; the motion vocabulary belongs to sub-version 4.0.3.2.

## 6. Hard constraints

- **HC-1:** Event isolation is absolute, and its coverage is part of the finished state rather than optional.
- **HC-2:** One primitive underlies all three surfaces, and no second window implementation may appear later in the version.
- **HC-3:** Windows render in the host layer as siblings above the canvas, not inside the canvas.
- **HC-4:** Window position and size are local and per device, and are never synchronized.
- **HC-5:** Nothing is ever modal over the map; the canvas remains interactive wherever a window is not covering it.

## 7. Decisions the session plan must resolve

- **PD-1:** The pointer-event architecture that achieves absolute isolation without making the canvas inert where a window is absent.
- **PD-2:** The separability of the primitive from its first consumers, so the primitive's contract is not shaped by placeholder content.
- **PD-3:** Where per-device position and size are persisted, and how a stale persisted position for a window now off-screen is recovered.
- **PD-4:** How a node-anchored summary tracks panning and zooming without re-rendering on every frame.

## 8. Acceptance criteria

- **AC-1:** Selecting a system opens the anchored panel at its fixed size and a canvas click closes it — proving DC-1.
- **AC-2:** A popped-out window drags, resizes freely, and restores its position and size after a reload on the same device — proving DC-2 and HC-4.
- **AC-3:** Selecting another system shows a node-anchored summary that stays attached through panning and zooming and dismisses on deselection — proving DC-3.
- **AC-4:** Typing and scrolling inside every surface leaves the map's pan and zoom untouched, proven by coverage rather than observation — proving DC-4 and HC-1.
- **AC-5:** The escape key closes the topmost window, clicking brings a window forward, and the canvas remains interactive beside an open window with no modal blocking — proving DC-5 and HC-5.
- **AC-6:** An inspection confirms all three surfaces resolve to one primitive rendered in the host layer above the canvas — proving DC-6 and HC-3.
- **AC-7:** A placeholder widget renders inside the primitive using the shipped props contract unchanged — proving DC-7.

## 9. Verification

- **V-1:** Event-isolation coverage output for typing and scrolling across all three surfaces.
- **V-2:** A reload demonstration showing per-device position and size persistence.
- **V-3:** A placeholder widget render inside the primitive.
- **V-4:** Stacking, front-bringing and escape-dismissal behavior.
- **V-5:** The repository's standing definition-of-done gate.

## 10. UX/operator gates

- **G-1:** The `UX gate` marker is `Yes`. The operator reviews, in a local browser, all three window surfaces, their dismissal behavior, free resizing and reload persistence, and confirms that interacting inside a window never disturbs the canvas. The session pauses for that review before the pull request opens.

## 11. Baseline/hotspot boundary

Expected baseline effect is Neutral; this is all-new mapper code. Planning must
confirm against the live baseline that none of AF-006, AF-007 or AF-008 counts a
surface this session touches, and should watch the primitive's own complexity so a
single component carrying three surfaces plus persistence and stacking does not
land above the repository's universal complexity caps.

## 12. Close-out behavior

This session is the only session of sub-version 4.0.3.3, so it completes the
sub-version: it commits on the shared lifecycle branch, pauses for the operator
browser review named above, then opens the sub-version pull request. It may
become `Complete` only once that pull request passes the external review gate and
merges. The map remains behind the development wall. On merge, the resolver
advances to sub-version 4.0.4.1.
