## Session 4.0.3.1.1 — Deterministic auto-layout engine

**Sub-version:** 4.0.3.1
**Master plan:** `docs/VERSION_4_0_PLAN.md` §4.0.3.1
**UX gate:** Yes
**Execution profile:** Frontier autonomous coding agent
**Delivery unit:** One agent session, one shared sub-version branch, one sub-version PR
**Roadmap coverage:** §4.0.3.1 auto-layout engine, kept as its own bundle by the approved delivery topology because it carries an unresolved algorithm pivot whose outcome changes later implementation
**Internal phases:** 1. Establish the pure layout seam and the sticky creation-order sector model; 2. Configure the radial layout behind that seam, running off the main thread, and prove determinism and stability; 3. Expose the tuning dials, land local-only pinning, and iterate to operator sign-off from live mapping
**Split triggers:** The configured layout cannot reach the specified feel through its dials, making the designed fallback algorithm the recommended path — a decision that changes this session's deliverable and requires operator direction before proceeding

## 1. Objective

Draw the chain identically on every client from shared facts alone: a
deterministic radial compass-tree over sticky creation-order sectors, behind a
single pure seam, tuned live until it feels right. This belongs in sub-version
4.0.3.1 because it is the mechanism that makes decision D1 work — if the same
graph does not produce the same picture everywhere, no position synchronization
is impossible rather than merely unnecessary.

## 2. Current context and dependencies

- **DEP-1:** Sub-version 4.0.2.3 shipped the reconciler this session feeds positions into, and its provisional placement is replaced here.
- **DEP-2:** Decision D2 fixes a deterministic radial compass-tree over sticky creation-order sectors, forbids force-directed layouts, and holds that one map is one chain from one root.
- **DEP-3:** Decision D1 requires that no position is ever synchronized; sticky sectors derive only from synchronized creation order, which is shared, rather than from any local state.
- **DEP-4:** Decision D8 establishes that the motion layer animates toward whatever targets this engine produces and never feeds back into them.
- **DEP-5:** The master plan records a designed fallback: a compact compass-sector algorithm with no external dependency behind the same seam, to be recommended with evidence if the configured layout's dials cannot reach the specified feel.
- **DEP-6:** Library and framework behavior must be verified against current primary documentation rather than recalled behavior before the layout is configured.

## 3. Done conditions

- **DC-1:** The same graph produces identical positions on two independent clients.
- **DC-2:** Adding a leaf moves no existing node, and an addition that fills a sector moves only that sector's sibling group.
- **DC-3:** Generated chains produce no overlapping nodes, and edge crossings occur only on connections that close a loop, because the layout places the spanning tree from the root and loop-closing connections draw as additional edges.
- **DC-4:** The layout computation runs off the main thread, leaving it free during a pass, and the layout library loads only on the map route.
- **DC-5:** A node can be unlocked, dragged and re-locked; while pinned it is excluded from layout, its pin is never synchronized, and re-locking returns it to its computed position.
- **DC-6:** One map remains one chain from one root throughout.
- **DC-7:** The operator has signed off the drawing feel from live mapping, with the tuning dials exposed.

## 4. In scope

- **IS-1:** The pure layout seam whose contract is a graph in and positions out.
- **IS-2:** The radial layout configuration and the sticky creation-order sector model.
- **IS-3:** The off-main-thread execution and route-scoped loading of the layout library.
- **IS-4:** The tuning dial set covering ring spacing, sector width, sibling gap and direction bias.
- **IS-5:** Local-only unlock-to-drag pinning, integrated with the shipped reconciler.

## 5. Out of scope

- **OOS-1:** Any motion or animation; this session may snap positions, and animation belongs to sub-version 4.0.3.2.
- **OOS-2:** Placement of systems beyond wormhole space and the fog halo, which belong to sub-version 4.0.4.2.
- **OOS-3:** Edge styling and connection presentation.
- **OOS-4:** The overlay window framework, which belongs to sub-version 4.0.3.3.
- **OOS-5:** Any change to the reconciler's intent vocabulary beyond consuming it.

## 6. Hard constraints

- **HC-1:** Layout is a pure function behind exactly one seam: a graph enters and positions leave. Nothing else in the application may compute a position.
- **HC-2:** No local state may influence shared layout. Sticky sectors derive only from synchronized creation order.
- **HC-3:** A pinned node's pin is local only, excluded from layout, and never synchronized.
- **HC-4:** If the configured layout cannot reach the specified feel through its dials, the fallback algorithm is recommended with evidence rather than the configured layout being forced.
- **HC-5:** No force-directed layout is used, in this session or later.

## 7. Decisions the session plan must resolve

- **PD-1:** The seam's exact contract, chosen so the fallback algorithm could replace the configured layout behind it without changing any caller.
- **PD-2:** The tuning dial set and each dial's range.
- **PD-3:** How loop-closing connections are placed, given the layout positions a spanning tree from the root.
- **PD-4:** The layout algorithm and option starting point, verified against current primary documentation for the chosen library.
- **PD-5:** How determinism is guaranteed across clients given any ordering the layout library may impose internally.

## 8. Acceptance criteria

- **AC-1:** Two independent clients given the same graph compute identical positions — proving DC-1 and HC-2.
- **AC-2:** Adding a leaf leaves every existing position unchanged, and a sector-filling addition moves only that sibling group — proving DC-2.
- **AC-3:** A property check over generated chains finds no node overlap, and every edge crossing traces to a loop-closing connection — proving DC-3.
- **AC-4:** The main thread remains responsive during a layout pass and the layout library is absent from bundles for non-map routes — proving DC-4.
- **AC-5:** An unlock, drag and re-lock round trip pins the node locally, excludes it from layout while pinned, leaves it unsynchronized to another client, and returns it on re-lock — proving DC-5 and HC-3.
- **AC-6:** A chain built through the shipped write path remains one chain from one root under every layout pass — proving DC-6.
- **AC-7:** The operator records sign-off on the drawing feel after live mapping with the dials exposed — proving DC-7.
- **AC-8:** A repository-wide check confirms the layout seam is the only position-computing path, which is what makes the identical-positions result of DC-1 hold for every client — proving DC-1 and HC-1.

## 9. Verification

- **V-1:** Determinism, stability and no-overlap coverage output, including the generated-chain property check.
- **V-2:** Off-main-thread profiling evidence and route-scoped bundle evidence for the layout library.
- **V-3:** The pinning round-trip demonstration, including non-synchronization to a second client.
- **V-4:** The operator's recorded sign-off from live mapping.
- **V-5:** The repository's standing definition-of-done gate.

## 10. UX/operator gates

- **G-1:** The `UX gate` marker is `Yes`, and the live tuning loop is the gate itself: the dials are exposed, the operator maps in-game against the local development server, and iteration continues to sign-off. The session pauses for that loop before the pull request opens.
- **G-2:** If the configured layout cannot reach the specified feel, the session stops and presents the fallback recommendation with evidence for an operator decision rather than proceeding.

## 11. Baseline/hotspot boundary

Expected baseline effect is Neutral: a new off-main-thread module and a new seam,
with no measured surface widened. Production file and line counts rise as new
mapper code lands, which is feature growth. Planning must confirm against the live
baseline that none of AF-006, AF-007 or AF-008 counts a surface this session
touches, and that the new layout module does not accrete responsibilities that
would put it near a complexity threshold on arrival.

## 12. Close-out behavior

This session is the only session of sub-version 4.0.3.1, so it completes the
sub-version: it commits on the shared lifecycle branch, runs the tuning loop and
pauses for operator sign-off, then opens the sub-version pull request. It may
become `Complete` only once that pull request passes the external review gate and
merges. The map remains behind the development wall. On merge, the resolver
advances to sub-version 4.0.3.2.
