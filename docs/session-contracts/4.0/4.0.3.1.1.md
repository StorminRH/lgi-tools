## Session 4.0.3.1.1 — Deterministic layout kernel

**Sub-version:** 4.0.3.1
**Master plan:** `docs/VERSION_4_0_PLAN.md` §4.0.3.1
**UX gate:** No
**Execution profile:** Frontier autonomous coding agent
**Delivery unit:** One agent session, one shared sub-version branch, one sub-version PR
**Roadmap coverage:** §4.0.3.1 pure graph-to-positions seam, deterministic property suite and ELK-versus-fallback decision
**Internal phases:** 1. Define the pure seam and shared ordering inputs; 2. Test ELK radial behavior against the sticky-sector contract; 3. Select the engine and prove determinism, stability and no-overlap
**Split triggers:** ELK cannot satisfy sticky sectors and stability through documented options, requiring the operator to approve the designed fallback before integration

## 1. Objective

Select and prove the deterministic layout kernel before worker, canvas, pinning
or tuning concerns can obscure whether the algorithm meets the product contract.

## 2. Current context and dependencies

- **DEP-1:** Sub-version 4.0.2.3 shipped the reconciler and its graph facts.
- **DEP-2:** Decisions D1 and D2 require identical facts to produce identical positions with sticky creation-order sectors and no force layout.
- **DEP-3:** The master plan defines a compact compass-sector fallback behind the same seam if ELK cannot meet the required feel and stability.

## 3. Done conditions

- **DC-1:** One pure seam accepts graph facts and returns positions; no caller-specific state enters the calculation.
- **DC-2:** The selected engine produces identical positions for identical graphs.
- **DC-3:** Adding a leaf moves no existing node, and filling a sector moves only its sibling group.
- **DC-4:** Generated chains have no node overlap, and crossings are confined to loop-closing edges.
- **DC-5:** The engine decision and fallback disposition are recorded with current primary-documentation and property evidence.

## 4. In scope

- **IS-1:** Pure layout contract, sticky-sector model and loop treatment.
- **IS-2:** ELK feasibility work, fallback comparison and property tests.

## 5. Out of scope

- **OOS-1:** Worker and route integration, local pinning, dials and operator visual tuning, owned by 4.0.3.1.2.
- **OOS-2:** Motion, fog and edge styling.

## 6. Hard constraints

- **HC-1:** The seam is pure and remains the only position-computing authority.
- **HC-2:** Only synchronized creation order influences shared layout.
- **HC-3:** No force-directed algorithm is permitted.
- **HC-4:** ELK is not forced if the evidence favors the approved fallback.

## 7. Decisions the session plan must resolve

- **PD-1:** The exact graph and position contract.
- **PD-2:** The ELK algorithm/options experiment and deterministic ordering controls.
- **PD-3:** The objective evidence threshold for choosing ELK or the fallback.

## 8. Acceptance criteria

- **AC-1:** Pure-function tests show identical inputs produce identical positions — proving DC-1 and DC-2.
- **AC-2:** Leaf and sector-fill fixtures prove the required stability boundary — proving DC-3.
- **AC-3:** Generated-chain property tests prove no overlap and bounded crossings — proving DC-4.
- **AC-4:** A recorded comparison selects one engine without weakening any hard constraint — proving DC-5.

## 9. Verification

- **V-1:** Determinism, stability and generated-chain property output.
- **V-2:** Current primary-documentation evidence and engine comparison.
- **V-3:** The repository's standing definition-of-done gate.

## 10. UX/operator gates

- **G-1:** If ELK fails the property threshold, the session pauses for approval of the designed fallback before 4.0.3.1.2 begins.

## 11. Baseline/hotspot boundary

Expected baseline effect is Neutral. Planning must keep the pure kernel below
the universal complexity caps and avoid mixing worker or canvas ownership into it.

## 12. Close-out behavior

This is the first of two sessions in sub-version 4.0.3.1. It verifies and
commits on the shared branch without opening the sub-version pull request, then
hands off the approved engine to 4.0.3.1.2.
