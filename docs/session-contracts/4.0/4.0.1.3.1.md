## Session 4.0.1.3.1 — Client universe assets, wormhole codex and the first widget export

**Sub-version:** 4.0.1.3
**Master plan:** `docs/VERSION_4_0_PLAN.md` §4.0.1.3
**UX gate:** Yes
**Execution profile:** Frontier autonomous coding agent
**Delivery unit:** One agent session, one shared sub-version branch, one sub-version PR
**Roadmap coverage:** §4.0.1.3 client universe assets, §4.0.1.4 wormhole type codex, and §4.0.1.5 sites card widget export, merged by the approved delivery topology because the codex reuses the asset pipeline and the widget export is a small export plus one convention decision
**Internal phases:** 1. Build the versioned asset generation, serving and typed loader for the system directory and the stargate adjacency graph; 2. Derive the wormhole type codex through the same pipeline and conventions; 3. Settle the feature public-surface convention and export the sites card as the first embeddable widget without changing the standalone page
**Split triggers:** The feature public-surface convention cannot be settled without changing how existing features are imported repository-wide, which would exceed this session's approved scope and require operator direction

## 1. Objective

Give the map everything it needs to name a system, walk the gate graph, and know
what a wormhole type does — plus the first embeddable feature widget. This belongs
in sub-version 4.0.1.3 because all three outcomes are reference assets and export
conventions the map reads before the map exists, and the codex reuses the same
generation, versioning, serving and loader conventions the universe assets
establish.

## 2. Current context and dependencies

- **DEP-1:** The universe system data, including each system's class and security, and the stargate adjacency graph already exist in Neon from earlier shipped work; this session derives client assets from that shipped data rather than re-ingesting the static export.
- **DEP-2:** Decision D15 requires that any tool appearing on the map is built as a standalone feature first and exports a condensed embeddable widget; the sites card is the first instance and the props contract it establishes becomes the template every later widget follows.
- **DEP-3:** No feature in the repository currently exposes a public surface module; features are imported by deep path. The public-surface question is therefore a live convention decision, not a mechanical export.
- **DEP-4:** The sites card is already an independently mounted component consumed by more than one route, so the widget export builds on an existing component boundary rather than decomposing a page.
- **DEP-5:** The assets are consumed later by sub-version 4.0.2.3 for node labels and by sub-version 4.0.4.2 for jump classification and the fog halo; the codex is consumed by sub-versions 4.0.4.1 and 4.0.4.3; the widget props contract is consumed by sub-versions 4.0.3.3 and 4.0.4.3.
- **DEP-6:** Reference data derived from the static export must be verified against the authoritative current schema index at build time rather than from recalled attribute identifiers.

## 3. Done conditions

- **DC-1:** A versioned client asset maps each solar system identifier to its name, class and security, and a second versioned asset expresses the stargate adjacency graph; both derive from the shipped Neon universe data and are versioned per static-export release.
- **DC-2:** Both assets are served immutably cached, and a typed loader exposes lookups for name, class, security and neighbour sets, loading once per map session.
- **DC-3:** A versioned codex asset resolves each wormhole type to its total mass, maximum jumpable mass, mass regeneration, lifetime, size class and destination class, produced through the same pipeline and conventions as the universe assets.
- **DC-4:** Spot-check coverage proves known systems, known gate pairs, known wormhole-space classes, a regeneration-bearing wormhole type, and the untyped far-side wormhole code resolve correctly, and the generated asset sizes are reported.
- **DC-5:** The sites card is exported as an embeddable widget that renders from a site identifier and is constrained to fit a window container, with the standalone sites page visually unchanged and a single render core shared by page and widget.
- **DC-6:** A recorded convention governs how a feature exposes an embeddable widget, and the sites card export follows it.

## 4. In scope

- **IS-1:** Asset generation, versioning, serving and the typed loader for the system directory and the stargate adjacency graph.
- **IS-2:** The wormhole type codex asset and its loader, produced through the pipeline established for the universe assets.
- **IS-3:** Spot-check coverage and the generated asset size report for all three assets.
- **IS-4:** The feature public-surface convention decision and its recording.
- **IS-5:** The sites card widget export, its props contract, and the isolation render check.

## 5. Out of scope

- **OOS-1:** Per-system static wormhole assignments, which belong to sub-version 4.0.1.6, and system effects, which belong to a later version.
- **OOS-2:** Re-ingesting the static export source; the Neon universe layer already exists and is not rebuilt here.
- **OOS-3:** Rendering anything on a map canvas, and any `src/mapper/` code.
- **OOS-4:** The mapper side of the widget contract — window hosting belongs to sub-version 4.0.3.3 and the signature row hook belongs to sub-version 4.0.4.3.
- **OOS-5:** Any redesign of the sites card itself or of the standalone sites page.
- **OOS-6:** Retrofitting the public-surface convention onto other existing features.

## 6. Hard constraints

- **HC-1:** Static-export field and attribute identifiers are verified against the authoritative current schema index during the change, never taken from recalled values.
- **HC-2:** The assets are our controlled copies; external sources are refresh feeds only and are never runtime dependencies.
- **HC-3:** The widget is exported from the owning feature outward only. No mapper import exists yet and none is introduced here, because the permitted import direction runs from the mapper to features and never the reverse.
- **HC-4:** The standalone sites page and the widget share one logic and render core; they must not fork into two implementations.
- **HC-5:** Each asset declares its placement and refresh mechanism in the dataset registry alongside the change.

## 7. Decisions the session plan must resolve

- **PD-1:** The asset format and versioning scheme shared by all three assets, and whether the client loads them as bundled or fetched assets.
- **PD-2:** Whether the codex generation extends the universe asset generation path or runs beside it, with a separability judgement if it extends.
- **PD-3:** The feature public-surface convention — whether a feature gains an explicit public module, or whether the widget is exported through an agreed deep path — given no feature exposes one today and the answer becomes the template for every later widget.
- **PD-4:** The widget's props contract, including how a window container communicates its size constraint.
- **PD-5:** The current authoritative attribute identifiers for wormhole type mass, jumpable mass, regeneration, lifetime and destination class, resolved from the live schema index.

## 8. Acceptance criteria

- **AC-1:** Generating the assets from the shipped Neon universe data produces a system directory and an adjacency graph whose versions track the static-export release — proving DC-1.
- **AC-2:** The loader resolves a known system's name, class and security and a known system's neighbour set, loading the assets once per session, and the served responses carry immutable caching — proving DC-2.
- **AC-3:** The codex resolves a known wormhole type's full attribute set through the same loader conventions as the universe assets — proving DC-3 and PD-2's outcome.
- **AC-4:** Spot-check output covers known systems, known gate pairs, wormhole-space classes, a regeneration-bearing type and the untyped far-side code, and reports each generated asset's size — proving DC-4 and HC-1.
- **AC-5:** The widget renders correctly from a site identifier inside a constrained container while the standalone sites page renders unchanged, and both resolve to one shared render core — proving DC-5 and HC-4.
- **AC-6:** The recorded convention describes how a feature exposes an embeddable widget, and the sites card export conforms to it — proving DC-6.

## 9. Verification

- **V-1:** Spot-check coverage output for the directory, adjacency graph and codex, including the named edge cases.
- **V-2:** The generated asset size report for all three assets.
- **V-3:** An isolation render of the widget in a constrained container, and a before-and-after comparison of the standalone sites page.
- **V-4:** Dataset-registry declaration checks for the new assets.
- **V-5:** The repository's standing definition-of-done gate.

## 10. UX/operator gates

- **G-1:** The `UX gate` marker is `Yes` for one bounded check only: the operator confirms in a local browser that the widget renders correctly in isolation and that the standalone sites page is visually unchanged. The session pauses for that review before the pull request opens.

## 11. Baseline/hotspot boundary

Expected baseline effect is Neutral. Planning must verify against the live
baseline that the universe data modules this session reads from are not widened
by it, and that the widget export does not widen the sites feature's query
surface. The live baseline carries watch findings AF-006, AF-007 and AF-008 only;
none of their triggers counts a surface this session changes, and planning must
confirm that remains true after the export lands.

## 12. Close-out behavior

This session is the only session of sub-version 4.0.1.3, so it completes the
sub-version: it commits on the shared lifecycle branch, pauses for the operator
browser review named above, then opens the sub-version pull request. It may
become `Complete` only once that pull request passes the external review gate and
merges. It publishes no version record. On merge, the resolver advances to
sub-version 4.0.1.6.
