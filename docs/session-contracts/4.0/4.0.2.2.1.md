## Session 4.0.2.2.1 — Chain data model and authorization

**Sub-version:** 4.0.2.2
**Master plan:** `docs/VERSION_4_0_PLAN.md` §4.0.2.2
**UX gate:** No
**Execution profile:** Frontier autonomous coding agent
**Delivery unit:** One agent session, one shared sub-version branch, one sub-version PR
**Roadmap coverage:** §4.0.2.2 data model and authorization, kept separate from the reactive read path by the approved delivery topology because the authorization gate and its access projection are a materially different risk domain from presentation
**Internal phases:** 1. Land the per-map chain schema with its indexes and its join-key-only discipline; 2. Land the authorization gate called first in every public map function, with the regenerable access projection written one-directionally from the durable side; 3. Prove isolation, teardown and resynchronization, and live revocation eviction, and record the per-subscription cost budget
**Split triggers:** The access projection cannot be written one-directionally without a durable-side change that exceeds this session's approved scope, or proving live revocation eviction requires interface work this session does not own

## 1. Objective

Land the collaborative chain schema and the authorization gate that gates every
access to it, proven before any map pixel consumes them. This belongs in
sub-version 4.0.2.2 because decision D5 makes this gate the sole access path on
the collaborative side, and because a defect in the gate or its access projection
is a security defect that must be able to fail and be reverted independently of
any presentation work.

## 2. Current context and dependencies

- **DEP-1:** Sub-version 4.0.1.1 established the durable map and access tables, the single authorization helper, and the principal-resolution seam this session's projection writes from.
- **DEP-2:** Decision D3 places per-map mutable chain state on the collaborative side as the documented exception, keeps map metadata and access durable, and forbids any write from the collaborative side back to the durable side.
- **DEP-3:** Decision D4 requires fine-grained documents — one per system, connection, signature and note — so concurrent edits touch different rows and write conflicts stay rare.
- **DEP-4:** Decision D5 requires that the authorization gate is called first in every public map function, with no second access-check path.
- **DEP-5:** `docs/CONVEX.md` owns the collaborative platform's cost rules, conflict behavior and the established reference patterns this schema follows, including identity read from the verified token, a single generation-guarded batched apply, no client-posted authority, and a guard against no-op writes.
- **DEP-6:** The prior version's subscription-split lesson is binding: a payload read set must not be invalidated by unrelated bookkeeping writes, which is a property of how the schema separates hot from cold data.
- **DEP-7:** Sub-version 4.0.2.1 established the mapper host layer and the map route group this schema will eventually be read from.

## 3. Done conditions

- **DC-1:** The chain schema exists with one document per system, connection, signature and note, plus the access projection, every table indexed by map, and systems additionally indexed by map and system so automatic mapping upserts are idempotent.
- **DC-2:** A connection document carries its wormhole type, mass state, ship-size constraint, and its end-of-life moment stored as an absolute timestamp so remaining time is derived at display rather than flipped by a scheduler.
- **DC-3:** A signature document carries the soft-deletion shape that makes removal undoable.
- **DC-4:** The authorization gate is called first in every public map function, and an unauthorized caller is rejected.
- **DC-5:** Documents belonging to one map are invisible to queries for another map.
- **DC-6:** The access projection is regenerable and written in one direction only from the durable side on grant changes, and tearing it down and resynchronizing it restores correct access.
- **DC-7:** Revoking a user's access evicts that user's live subscription rather than leaving stale data readable.
- **DC-8:** The per-subscription cost budget for the chain read set is measured and recorded in the repository's short-term memory document.

## 4. In scope

- **IS-1:** The chain schema, its documents, and its indexes.
- **IS-2:** The authorization gate on the collaborative side and its use in every public map function.
- **IS-3:** The access projection, its one-directional write from the durable side, and its teardown and resynchronization behavior.
- **IS-4:** Fixture mutations sufficient to prove the schema and gate, and the coverage proving isolation, rejection, resynchronization and live eviction.

## 6. Hard constraints

- **HC-1:** Chain documents carry join keys only. No system name, class, effect or other reference detail is stored on the collaborative side; the client enriches from the versioned assets and the durable side.
- **HC-2:** No write flows from the collaborative side back to the durable side. The access projection writes in one direction only, driven from the durable side.
- **HC-3:** The gate is called first in every public map function. No second access-check path may exist.
- **HC-4:** End-of-life is stored as an absolute timestamp and never as a scheduled state flip.
- **HC-5:** Volatile bookkeeping must never land on a watched chain table, so an unrelated write cannot invalidate a chain payload read set.
- **HC-6:** The schema follows the established reference patterns recorded in the collaborative platform's owning document rather than introducing a new interaction shape.

## 7. Decisions the session plan must resolve

- **PD-1:** The role granularity carried in the projection documents, and how it maps onto the durable side's role model without duplicating its authority.
- **PD-2:** The soft-deletion shape for signatures that makes removal undoable without leaving unbounded tombstones.
- **PD-3:** The debounce threshold for last-seen bookkeeping, chosen so it satisfies the constraint against invalidating chain payload read sets.
- **PD-4:** The wormhole type representation on a connection — a stable code or a numeric identifier — given the codex and later observation emissions both consume it.
- **PD-5:** How the per-subscription cost budget is measured deterministically rather than estimated.

## 8. Acceptance criteria

- **AC-1:** The schema applies with one document per entity kind and the recorded indexes present, and a repeated automatic upsert against the map-and-system index produces one document rather than two — proving DC-1.
- **AC-2:** A connection document round-trips its type, mass state, ship-size constraint and absolute end-of-life moment, and remaining time is derived at read rather than stored — proving DC-2 and HC-4.
- **AC-3:** A soft-deleted signature can be restored to its prior state — proving DC-3.
- **AC-4:** An unauthorized caller is rejected by every public map function, and a review of those functions confirms the gate is the first call in each — proving DC-4 and HC-3.
- **AC-5:** A query issued for one map returns no document belonging to another map — proving DC-5.
- **AC-6:** Tearing down the access projection and resynchronizing it from the durable side restores correct access for every principal — proving DC-6 and HC-2.
- **AC-7:** Revoking access while a subscription is live evicts that subscription rather than continuing to serve chain data — proving DC-7.
- **AC-8:** A chain payload document is byte-identical after an unrelated bookkeeping write, and the measured per-subscription read cost is recorded — proving DC-8 and HC-5.
- **AC-9:** An inspection of every chain document confirms it stores join keys only, with no reference detail, completing the schema shape DC-1 requires — proving DC-1 and HC-1.
