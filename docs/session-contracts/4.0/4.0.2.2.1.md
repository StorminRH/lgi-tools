## Session 4.0.2.2.1 — Chain schema and authorization gate

**Sub-version:** 4.0.2.2
**Master plan:** `docs/VERSION_4_0_PLAN.md` §4.0.2.2
**UX gate:** No
**Execution profile:** Frontier autonomous coding agent
**Delivery unit:** One agent session, one shared sub-version branch, one sub-version PR
**Roadmap coverage:** §4.0.2.2 chain entity schema, indexes, gate contract and map isolation
**Internal phases:** 1. Land the fine-grained chain schema and indexes; 2. Land the gate-first fixture surface; 3. Prove entity invariants, authorization rejection and map isolation
**Split triggers:** The gate cannot expose a stable minimum role claim without first deciding the durable projection mechanism owned by 4.0.2.2.2

## 1. Objective

Establish the fine-grained collaborative chain model and the single gate every
public map function must call before the durable access projection is connected.

## 2. Current context and dependencies

- **DEP-1:** Sub-version 4.0.1.1 shipped durable map/access authority and the principal-resolution seam.
- **DEP-2:** Decisions D3 and D4 place chain facts in fine-grained Convex documents while keeping map metadata and access durable.
- **DEP-3:** Decision D5 requires one gate called first in every public map function.
- **DEP-4:** `docs/CONVEX.md` owns identity, conflict, no-op-write and hot/cold read-set rules.

## 3. Done conditions

- **DC-1:** Systems, connections, signatures and notes exist as separate map-indexed documents, with systems also indexed by map and system.
- **DC-2:** Connections carry type, mass, ship-size and absolute EOL state; signatures carry reversible soft deletion.
- **DC-3:** Gate-first fixture functions reject unauthorized callers and isolate one map from another.
- **DC-4:** Chain documents carry join keys only and volatile bookkeeping cannot invalidate watched payload documents.

## 4. In scope

- **IS-1:** Chain entity definitions, indexes and invariant tests.
- **IS-2:** The collaborative gate contract and gate-first fixture functions.
- **IS-3:** Authorization rejection, idempotent system upsert and map-isolation proof.

## 5. Out of scope

- **OOS-1:** The durable-to-Convex access projection, resynchronization and revocation, owned by 4.0.2.2.2.
- **OOS-2:** Production subscriptions, authoring mutations and all user interface.

## 6. Hard constraints

- **HC-1:** Documents carry join keys only and EOL is an absolute timestamp.
- **HC-2:** No write flows from Convex to Neon.
- **HC-3:** The gate is the first call in every public fixture function and no second access path exists.
- **HC-4:** Unrelated bookkeeping never changes a watched chain payload document.

## 7. Decisions the session plan must resolve

- **PD-1:** The stable wormhole type representation shared by the codex and observation stream.
- **PD-2:** The reversible signature tombstone and bounded cleanup shape.
- **PD-3:** The minimum projected role claim the gate accepts without duplicating durable authority.
- **PD-4:** The debounce boundary that keeps last-seen bookkeeping out of payload invalidation.

## 8. Acceptance criteria

- **AC-1:** Schema evidence shows every entity and required index, and repeated map/system upsert remains singular — proving DC-1.
- **AC-2:** Connection and signature fixtures round-trip their required states — proving DC-2.
- **AC-3:** Unauthorized and cross-map fixture reads fail while authorized same-map reads succeed — proving DC-3.
- **AC-4:** Inspection and coverage show join-key-only documents and unchanged payload bytes after bookkeeping — proving DC-4.

## 9. Verification

- **V-1:** Schema, index and idempotent-upsert evidence.
- **V-2:** Gate rejection and map-isolation coverage.
- **V-3:** Payload-invalidation evidence and the repository's standing definition-of-done gate.
