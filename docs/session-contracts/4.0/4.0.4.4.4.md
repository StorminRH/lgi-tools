## Session 4.0.4.4.4 — Atlas landing catalogue

**Sub-version:** 4.0.4.4
**Master plan:** `docs/VERSION_4_0_PLAN.md` §4.0.4.4
**UX gate:** Yes
**Execution profile:** Frontier autonomous coding agent
**Delivery unit:** One agent session, one shared sub-version branch, one sub-version PR
**Roadmap coverage:** §4.0.4.4 pre-map entry surface: authorized map catalogue, create-card handoff, no-map routing
**Internal phases:** 1. Land the no-map routing branch and the authorized catalogue grid; 2. Land card access affordances and bounded chain summaries; 3. Wire the create card and prove empty state, archived exclusion and navigation
**Split triggers:** The bounded per-map chain summary cannot respect collaborative read budgets without changing the shipped chain schema, or the no-map routing branch cannot keep the declared route classification honest.

## 1. Objective

Opening Atlas without a selected map presents an authorized map catalogue —
named, access-labeled, clickable map cards plus one create card — instead of a
nameless empty canvas, completing sub-version 4.0.4.4's map-management story at
the version's entry surface.

## 2. Current context and dependencies

- **DEP-1:** Session 4.0.4.4.1 shipped the creation dialog, first-run handoff and creation rate guard.
- **DEP-2:** Session 4.0.4.4.2 shipped the single durable server-read authorized map listing and the switcher that consumes it.
- **DEP-3:** Session 4.0.4.4.3 shipped archive; an archived map is already absent from every listing consumer.
- **DEP-4:** Sub-version 4.0.4.1 shipped the set-home first-run prompt that creation lands on.
- **DEP-5:** Decision D13 keeps every map route behind the development wall with no public navigation link until wall-drop.
- **DEP-6:** The no-map entry always lands on the catalogue; automatic resume of a last-used map is deliberately excluded and would be a future explicit affordance.

## 3. Done conditions

- **DC-1:** Opening the map route without a selected map always shows the landing catalogue — never an empty canvas — while a selected map opens the unchanged full canvas.
- **DC-2:** The catalogue lists exactly the unarchived maps the user may view, through the same single durable server-read listing the switcher consumes.
- **DC-3:** Each map card communicates name, visibility, the viewer's role, relative recency and a bounded chain summary, degrading to metadata-only when the collaborative backend is unavailable.
- **DC-4:** Activating a map card opens that map's full canvas.
- **DC-5:** A visually distinct create card opens the shipped creation dialog, and a successful creation lands on the new map's set-home prompt.
- **DC-6:** A user with zero maps sees only the create card and one short hint.

## 4. In scope

- **IS-1:** The no-map entry routing branch and the landing catalogue surface.
- **IS-2:** Map cards, access affordances, bounded chain summaries and the create-card handoff.

## 5. Out of scope

- **OOS-1:** The creation dialog, switcher, access editor and archive lifecycle themselves, shipped by 4.0.4.4.1 through 4.0.4.4.3.
- **OOS-2:** Resume-last-map behavior, public navigation links and wall removal.
- **OOS-3:** Intel or activity content on cards beyond the bounded chain summary.

## 6. Hard constraints

- **HC-1:** One authorized-list read serves the landing and the switcher; no second listing logic exists, and neither ever reads the collaborative access projection.
- **HC-2:** Chain facts stay collaborative: card summaries introduce no denormalized durable columns and no collaborative-to-durable write path.
- **HC-3:** The landing composes at the application layer; the mapper host layer gains no application-page responsibility.
- **HC-4:** The route's declared render classification stays honest and the canvas path gains no server-side collaborative preload.
- **HC-5:** The landing is a catalogue, not a tutorial; simplicity-through-automation bounds card content and empty states.

## 7. Decisions the session plan must resolve

- **PD-1:** The exact bounded per-map chain-summary read — root identification, count sourcing and its per-card read budget.
- **PD-2:** The no-map branch mechanics that preserve the route classification and give a taller-than-viewport grid honest scroll inside the full-viewport frame.
- **PD-3:** The card affordance vocabulary for visibility, role and grant breadth within existing card and pill primitives.

## 8. Acceptance criteria

- **AC-1:** No-map entry renders the catalogue and a selected map renders the unchanged canvas — proving DC-1.
- **AC-2:** The catalogue and the switcher present the same authorized map set for the same user, and an archived map appears in neither — proving DC-2.
- **AC-3:** Cards show name, visibility, role, recency and a chain summary, and degrade to metadata-only without the collaborative backend — proving DC-3.
- **AC-4:** Card activation opens the correct map's canvas — proving DC-4.
- **AC-5:** The create card runs dialog, creation and set-home handoff end to end — proving DC-5.
- **AC-6:** A zero-map user sees only the create card and hint — proving DC-6.

## 9. Verification

- **V-1:** Routing and catalogue-listing evidence, including archived exclusion and degraded mode.
- **V-2:** Creation-handoff and card-navigation demonstration.
- **V-3:** Operator review and the repository's standing definition-of-done gate.

## 10. UX/operator gates

- **G-1:** The operator reviews the landing grid, card affordances, create-card flow and navigation into a map in local browsers before the sub-version pull request opens.

## 11. Baseline/hotspot boundary

Expected baseline effect is Neutral. The landing consumes auth-adjacent
app-layer composition (AF-008 named) without modifying it; planning must avoid
widening AF-006–AF-008 and must verify the chain-summary read against the
standing collaborative I/O budget.

for v4.0. It completes the shared branch after 4.0.4.4.3, verifies, pauses for
operator review, and opens the sub-version pull request. After merge, every
