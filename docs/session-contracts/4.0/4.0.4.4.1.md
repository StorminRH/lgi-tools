## 1. Objective

Give maps their full management story in one continuous build: create a valid
empty map atomically and open it at the shipped home prompt; let authorized
users switch maps without stale flashes; let owners manage character and corp
access through the sole authority path; close a map safely through archive,
grace and a bounded resumable purge with no instant-destroy path; and present
an authorized landing catalogue — named, access-labeled, clickable map cards
plus one create card — whenever Atlas opens without a selected map. This is
the sole session of sub-version 4.0.4.4 and the final roadmap session of the
version.

- **DEP-2:** Sub-version 4.0.2.2 shipped the one-way collaborative access projection and its revocation behavior.
- **DEP-3:** Sub-version 4.0.4.1 shipped the first-run home prompt that creation lands on.

## 3. Done conditions

- **DC-1:** One small dialog accepts a name and private/corp visibility.
- **DC-2:** One durable transaction writes the map and owner access row, then the one-way projection is written and the map opens at the home prompt.
- **DC-3:** A new map contains zero collaborative chain documents.
- **DC-4:** No map-count cap exists, while the existing rate guard blocks a scripted burst and not human use.
- **DC-5:** The current map name opens a durable server-read switcher.
- **DC-6:** Switching retargets every subscription without flashing the previous map.
- **DC-7:** Owners can grant character and corp principals viewer, editor or owner access; non-owners cannot edit access.
- **DC-8:** Revocation evicts a live viewer end to end.
- **DC-9:** A corp member can open a corp-visible map and a non-member cannot.
- **DC-10:** Archiving immediately removes a map from switchers and remains owner-restorable during grace.
- **DC-11:** No instant hard-delete path exists for a living chain.
- **DC-12:** After grace, a resumable sweep purges every collaborative document in bounded batches.
- **DC-13:** Complete collaborative removal is followed by the durable tombstone.
- **DC-14:** Opening the map route without a selected map always shows the landing catalogue — never an empty canvas — while a selected map opens the unchanged full canvas.
- **DC-15:** The catalogue lists exactly the unarchived maps the user may view, through the same single durable server-read listing the switcher consumes.
- **DC-16:** Each map card communicates name, visibility, the viewer's role, relative recency and a bounded chain summary, degrading to metadata-only when the collaborative backend is unavailable.
- **DC-17:** Activating a map card opens that map's full canvas.
- **DC-18:** A visually distinct create card opens the creation dialog, and a successful creation lands on the new map's set-home prompt.
- **DC-19:** A user with zero maps sees only the create card and one short hint.

## 6. Hard constraints

- **HC-1:** Partial durable map creation is impossible.
- **HC-2:** A new map holds no chain documents.
- **HC-3:** The creation guard is invisible to normal users and is not a bespoke counter.
- **HC-4:** One authorized-list read serves the landing and the switcher; no second listing logic exists, and neither ever reads the collaborative access projection.
- **HC-5:** The access editor uses the existing settings slot and sole authority path.
- **HC-6:** Switching cannot expose stale content from the prior map.
- **HC-7:** Purge begins only after grace and no instant hard delete exists.
- **HC-8:** Purge batches respect current collaborative operation limits and resume safely.
- **HC-9:** The durable row is tombstoned only after collaborative deletion completes.
- **HC-10:** Chain facts stay collaborative: card summaries introduce no denormalized durable columns and no collaborative-to-durable write path.
- **HC-11:** The landing composes at the application layer; the mapper host layer gains no application-page responsibility.
- **HC-12:** The route's declared render classification stays honest and the canvas path gains no server-side collaborative preload.
- **HC-13:** The landing is a catalogue, not a tutorial; simplicity-through-automation bounds card content and empty states.
