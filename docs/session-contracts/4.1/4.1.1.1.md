## Session 4.1.1.1 — Seats stay put

**Sub-version:** 4.1.1
**Master plan:** `docs/VERSION_4_1_PLAN.md` §4.1.1
**UX gate:** Yes
**Execution profile:** Frontier autonomous coding agent
**Delivery unit:** One agent session, land each Ordered work step on development
**Roadmap coverage:** §4.1.1 lock-on-draw seats, stub and static-ghost identity, Auto layout and unlock-to-drag removal
**Internal phases:** 1. Remember first seats for stubs and static ghosts across paste, identify, and resolve; 2. Remove Auto layout and unlock-to-drag; 3. Prove already-drawn nodes hold still and complete the UX look
**Split triggers:** Locking seats requires a new synced position model or replaces compass-tree with a different layout philosophy

## 1. Objective

Once a node is drawn, it keeps that seat through paste, identify, and resolve.
Stub becoming real is an identity swap on those coordinates. Auto layout and
unlock-to-drag leave Atlas. This is the seat half of 4.1; chrome waits on it.

## 2. Current context and dependencies

- **DEP-1:** Shipped Atlas compass layout and stub layout (`src/mapper/layout/`,
  `src/mapper/chain/stub-layout.ts`) allocate sequential negative compass ids
  today and re-post layout when the stub fingerprint changes.
- **DEP-2:** Authored-system seats already protect through the reconciler and
  user placement; stubs and static ghosts do not share that lock.
- **DEP-3:** `useSystemStaticSlots` and `believedHoles` feed drawn static stubs
  into the same layout path as scanned stubs.
- **DEP-4:** `atlas.autoLayout` (default true) and unlock-to-drag on the canvas
  still exist in settings and ChainLive.
- **DEP-5:** Standing decisions D1–D3 and the version Still-true layout rules
  bind this session.

## 3. Done conditions

- **DC-1:** A scanned stub’s first painted seat is the seat it keeps until it
  dies or becomes the real system.
- **DC-2:** Becoming real is an identity swap on those coordinates; the real
  system does not take a new compass child slot.
- **DC-3:** Static ghosts follow the same first-paint lock.
- **DC-4:** Pasting another wormhole does not move authored systems or
  already-seated stubs or ghosts.
- **DC-5:** The Auto layout setting and the unlock-to-drag path are gone from
  Atlas settings and from the canvas. Camera follow and click-focus stay.
- **DC-6:** Overlap after first paint is accepted; nothing already on screen
  moves to fix it.

## 4. In scope

- **IS-1:** Stub and static-ghost layout identity across paste, identify,
  resolve, and static accounting.
- **IS-2:** Resolve / identify keeping the drawn seat (identity swap, not a
  new child slot).
- **IS-3:** Removal of `atlas.autoLayout` and local drag / re-lock snap,
  including leftover preference rows when the control is deleted.
- **IS-4:** Layout tests that prove already-drawn nodes do not move when a
  sibling appears or a stub becomes real.
- **IS-5:** Sub-version `APP_VERSION` bump and the first
  `content/changelog/v4.1.md` entry for this land sequence.

## 5. Out of scope

- **OOS-1:** Disc widgets, intel card copy, k-space title text, hub math,
  region or ship-name client assets.
- **OOS-2:** A new layout philosophy. Compass-tree stays.
- **OOS-3:** Re-adding hand placement or any hidden dial that restores Auto
  layout or unlock-to-drag.
- **OOS-4:** Changing paste, jump, or scanner identify product behavior beyond
  seat stability.
- **OOS-5:** Leftover Atlas tickets that are not seat lock or Auto
  layout / drag cleanup.

## 6. Hard constraints

- **HC-1:** Positions stay local and unsynced. Shared facts sync; layout and
  motion stay local.
- **HC-2:** Compass-tree layout stays deterministic for the same graph and
  seats.
- **HC-3:** First paint may place a new node. After that, nothing already on
  screen moves. Camera follow moves the view, not the seats.
- **HC-4:** Fallow zones stay deny-by-default. No new cross-layer exceptions.
- **HC-5:** Atlas connection language stays the glossary in
  `src/data/maps/connection-door-types.ts`.

## 7. Decisions the session plan must resolve

- **PD-1:** How a stub’s first seat is remembered across paste, static
  accounting, and resolve without re-feeding a new layout id that changes the
  picture.
- **PD-2:** What leftover Auto layout preference rows do when the control is
  deleted.

## 8. Acceptance criteria

- **AC-1:** After a stub’s first paint, paste that adds a sibling leaves that
  stub’s coordinates unchanged — proving DC-1 and DC-4.
- **AC-2:** Resolve or identify that turns a stub into a real system keeps the
  drawn coordinates; no new compass child slot appears for that system —
  proving DC-2.
- **AC-3:** Static ghosts keep first-paint seats through paste and identify
  the same way scanned stubs do — proving DC-3 and DC-4.
- **AC-4:** Atlas settings no longer expose Auto layout, and the canvas no
  longer unlocks nodes for drag or re-lock snap; camera follow and click-focus
  still work — proving DC-5.
- **AC-5:** Layout proofs cover sibling appearance and stub-becomes-real
  without moving already-drawn nodes; overlap after first paint is left as
  painted — proving DC-6 and IS-4.

## 9. Verification

- **V-1:** Layout proofs for seat stability through paste, identify, and
  resolve.
- **V-2:** Settings and canvas proofs that Auto layout and unlock-to-drag are
  gone while camera follow and click-focus remain.
- **V-3:** Visual look on a paste-then-identify chain, then the dedicated
  UX Ordered-work step (`ux-check` plus operator disposition).

chrome or intel surfaces in this session.

`Complete` after the last Ordered work step of this contract, including G-1
and the UX Ordered-work step. Promote starts at 80 app-facing files versus

version’s last session; archive waits on 4.1.2.
